# 真实接口验证

> 2026-08-02 · 对应 `test/integration/test_public_apis.py`

到 P5 为止，全部 313 条测试都是密闭的：假响应对象、httpretty、本地 socket。这是合入门禁该有的样子——但它也意味着**每一种响应形状都是我们自己挑的**。挑得再全，也只覆盖得到我们想得到的情况。

所以拿框架去打了一批真实的第三方接口。

---

## 为什么是包管理器仓库

候选里大部分公共测试接口（httpbin、jsonplaceholder、postman-echo 等）在本环境被出网策略挡掉了。但这反而逼出了更好的选择：

| | 包管理器仓库 | 常见"测试用"接口 |
|---|---|---|
| 需要密钥/配额 | 否 | 部分需要 |
| schema 稳定性 | 高（下游生态依赖它） | 中 |
| 是不是"真实系统" | **是**——每天承载真实流量 | 多为回声服务 |
| 响应形状 | 我们无法左右 | 我们请求什么它回什么 |

最后一行是关键：回声服务返回的是**我们自己发过去的东西**，它验证不了解析器面对陌生结构的表现。

选定四个：`pypi.org`、`registry.npmjs.org`、`proxy.golang.org`（另有 `index.crates.io` 备用）。

---

## 验证结论

| # | 验证点 | 用的接口 | 结果 |
|---|---|---|---|
| 1 | 大型嵌套 JSON：属性访问 + 键访问 + 嵌套 list + schema 校验 | PyPI `/pypi/requests/json` | ✅ |
| 2 | **Python 命名法表达不了的键**：`dist-tags`（连字符）、`_id` | npm `/express` | ✅ |
| 3 | 非 JSON 响应体（`text/plain`）：原样返回 str，JSON 断言给出可读失败而非抛穿 | Go proxy `@v/list` | ✅ |
| 4 | 状态码真的被判定：404 必须失败 | PyPI 不存在的包 | ✅ |
| 5 | TLS 校验是真的在校验：换成无效 CA bundle 即连接失败 | PyPI | ✅ |
| 6 | 连接失败与"响应不符合预期"可区分，且不归咎被测系统 | 被策略拒绝的主机 | ✅ |
| 7 | 读超时 | PyPI + 1ms 读预算 | ❌ **发现缺陷** |

第 2 条正是旧 namedtuple 解析器的死穴——连字符不是合法标识符，那个实现根本承载不了这个键。真实接口不会迁就 Python 的命名规则。

## 发现的缺陷：读超时被报成连接失败

### 现象

```
scenario                      raised exception        isinstance(exc, Timeout)
裸 requests                   ReadTimeout             ✅
挂上本框架的 retry adapter    ConnectionError         ❌
即使 max_retries=0            ConnectionError         ❌
```

### 成因

挂载 Retry adapter 后，urllib3 把读超时包成 `MaxRetryError(reason=ReadTimeoutError)`，requests 再把 `MaxRetryError` 统一映射成 `ConnectionError`。于是 `isinstance(exc, requests.exceptions.Timeout)` **从挂上 adapter 那一刻起就静默失效了**——而本框架给每个 session 都挂 adapter。

后果不算严重（两者都是 `TransportError`，归因结论一致），但归因报告会说错原因：「连不上」和「对方太慢」是两回事，前者查网络，后者查对端负载。

### 单测为什么没抓住

原来的用例是往假 session 里直接塞一个 `ConnectTimeout`：

```python
@pytest.mark.parametrize('recording', [requests.exceptions.ConnectTimeout('slow')], indirect=True)
def test_timeout_becomes_framework_error(self, recording):
    ...
```

假 session 绕过了真实 adapter，**urllib3 的包装从来没发生过**。mock 把 bug 藏住了。

### 修法

`translate_error()` 里加一层解包（`.reason` / `.args` / `__cause__` / `__context__`），认 urllib3 的超时类型；并把超时判定排在 `ConnectionError` 之前，否则被包装过的超时永远先命中后者。

**修的过程中又踩了一脚**：第一版直接判 `isinstance(exc, urllib3.exceptions.TimeoutError)`，结果**连接被拒绝也成了超时**——urllib3 声明的是 `NewConnectionError(ConnectTimeoutError, HTTPError)`，一个瞬间失败的 ECONNREFUSED 在类型上属于 `ConnectTimeoutError`。所以判定收窄成 `ReadTimeoutError`/`ConnectTimeoutError` 且显式排除 `NewConnectionError`。

这一脚是被自己写的那条"别把连接失败误判成超时"的守卫用例当场踩出来的——**先写守卫再改实现，值在这里**。

### 回归用例

补在 `test/testtransport/test_transport.py::TestTimeoutThroughTheRealAdapter`：起一个只完成 TCP 握手、之后一个字节都不发的本地监听端口，请求走**真实 adapter、真实 urllib3、真实 socket**。全程 loopback，不出网，仍然属于零网络依赖。

四条：
- 读超时被判为超时（`max_retries` 取 0 和 2 各一次）
- 控制用例：确认 requests 此刻确实抛的是 `ConnectionError`——哪天它改回抛 `ReadTimeout`，这条会提醒解包逻辑已成死代码
- 连接被拒绝仍然是 `HttpConnectionError`（防止修过头）
- 端到端走装饰器路径

变异测试：把解包逻辑去掉，3 条失败；把 `NewConnectionError` 的排除去掉，守卫那条失败。都不是假绿。

## 顺带修掉的两处

**1. `test_http_get.py` 并非真的密闭。** 它用 httpretty 拦 `httpbin.org`，但 requests 会读环境里的 `HTTPS_PROXY`，转而向代理开 CONNECT 隧道——httpretty 不认这个，请求就漏到真实网络上去了。在有代理的环境里必挂，在 CI 上恰好没代理才一直是绿的。改成 `trust_env = False`。

**2. `rm -rf ai/ && pytest` 这道门禁此前是虚的。** CI 里连 `test/testai` 一起删了再跑——那当然是绿的。现在只删 `src/ipandora/ai`，`test/testai` 自己 `importorskip` 跳过，门禁才真的在验证那条保证。

> 小坑一则：`importorskip` 最初放在 `test/testai/conftest.py`。conftest 的导入时机早于任何测试模块，`ipandora.utils.log` 在那时绑定的 `sys.stdout` 与测试运行时看到的不是同一个对象，导致两条 stdout 相关的用例失败。移进测试模块内即可。

## 第二轮：断言层

第一轮只压了传输层和解析层。断言层当时全是**通过**的用例——而通过的断言几乎说明不了什么，真正要看的是**失败长什么样**，在没人写过 fixture 的数据上。

又查出三处。

### 缺陷 1：一条断言失败打出 195,529 字符

```python
assert_all(json_equals(r, 'releases', 'nope'))   # PyPI 的 releases 有 163 个版本
```

`Check.expr` 把整个 `releases` 原样 `repr()` 进了报错。这不是观感问题：这段文字会**原封不动**流进控制台、HTML 报告、以及失败归因的 prompt——最后那个是按 token 计费的。

而 `ai/triage.py` 里那条注释写着「Failure messages are already trimmed by the assertion layer」——**当时是假的**。它现在才成真。

修法：`brief()` 统一处理证据里的值，超过 240 字符截断，并在后缀里带上真实体积（`dict of 163, 195426 chars`）——"这个字段是空的还是巨大的" 仍然答得出来。195,529 → 383。

### 缺陷 2：`data.items.0` 被当成字符串键

真实数组随处可见，而 `.0` 是绝大多数人写下标的方式。旧实现只认 `[0]`，`.0` 被解析成键 `'0'`，报错是：

```
at 'info.classifiers': expected an object, found list
```

——这句话把人往**反方向**指。现在裸数字段按落脚点决定读法：站在 list 上是下标，站在 dict 上是键（数字形状的键在真实文档里同样常见，两种读法都得成立）。走错方向时也补了提示（`use an index like [0] to enter a list`）。

### 缺陷 3：含点的键根本无法寻址

PyPI 用版本号做 key：`releases['2.32.0']`。路径按 `.` 切分，这个字段**压根够不着**。npm 的 `dist-tags` 能用只是因为它恰好不含点。

补了引号段语法，两种引号都行：

```
releases['2.32.0'][0].filename
headers["x-request-id"]
```

### 顺带：修 bug 时自己引入了一个

加完截断后扫了一遍脱敏链路——**截断把密钥切一半，脱敏就不认了**，前 20 个字符明文进了报告，而改动之前这个值是完整 `***REDACTED***` 的。脱敏规则匹配的是完整凭据形状（64 位十六进制、JWT），拦腰砍断就不匹配了。

修法：截断点若落在一段不透明 token 中间，就把已保留的那半段一起丢掉——宁可少显示几个字符。回归用例把 0~299 全部截断位点扫了一遍，任意位点下泄漏残片长度均为 0。

### 验收

- 断言层单测 46 → 62 条，四处修复各做变异测试：还原旧行为后对应用例确实失败
- `test/integration` 8 → 17 条，新增的都是**失败信息质量**：聚合输出、路径断点定位、schema 定位、非 JSON 上的断言、`require` 的 skip 语义

### 没改的两处

- **`$gt` 打在版本号字符串上**报 `could not convert string to float: '2.34.2'`。泄漏了比较器内部实现，但信息足够定位，且真要支持版本号比较是另一个话题。
- **脱敏会把内容哈希也 mask 掉**（`blake2b_256` 的 64 位十六进制值）。这是 `redact.py` 写明的**有意取舍**——「宁可过度脱敏：错masked一个无害值代价是重跑一次，泄漏的凭据收不回来」。包仓库这类以哈希为数据的接口会因此损失部分证据，取舍权在使用方。

## 怎么跑

默认跳过——它们需要网络，且可能因为不属于我们的原因而失败：

```bash
IPANDORA_INTEGRATION=1 pytest test/integration -v
```

不进合入门禁，只在改动传输层/解析层/断言层之后手动跑一次。
