## P1 · 内核基础能力

**这是"先做好基础测试能力"的主体。** 不依赖业务域，可与 P0 部分并行。

按"挡不挡得住真实测试"排序：

### 1.1 断言层 ✅ 已完成

**改造前：完全不存在。** 全 `src/` 无 `raise_for_status`；`status_code` 唯一用途是给日志上色。**接口返回 500，测试照常 PASS。**

已按原方案 Part 2.3 建成 `core/assertion/`：

| 文件 | 内容 |
|---|---|
| `check.py` | `Check` 数据类 + `Source` 常量（api/schema/derived/authz/onchain） |
| `collector.py` | `assert_all` 收集器、`require` 前置条件 |
| `http.py` | `status_ok` / `status_is` / `header_is` / `json_has` / `json_equals` / `json_matches` / `schema_conforms` |
| `jsonpath.py` | 点号+下标路径解析，失败时给出停在哪一段 |

```python
from ipandora.core.assertion import assert_all, status_ok, json_equals

assert_all(
    status_ok(resp),                      # 没有这行，500 就是 PASS
    json_equals(resp, 'data.id', 1),
    json_equals(resp, 'data.name', 'alice'),
)
```

**三个关键设计**

1. **Check 是值不是异常** —— 构造失败的 Check 不抛，因此一次运行能看到全部失败而不是第一个。`assert_all` 才是判定者，抛标准 `AssertionError`（pytest / RF 都能原生渲染）。
2. **`require` 与 `assert_all` 分家** —— 前置不满足走 skip 不走 fail。原方案 Part 2.1 指出混淆这两者是长期运行套件最大的噪音源。
3. **绕开 `fetch_all()`** —— 断言直接读原始响应体。`ResponseHandler` 对单对象负载返回 `['code','data']`（键名）、对 null/标量抛 `TypeError`（见 [`01`](./01-现状评估与起点决策.md) 第 3.3 节），断言层不能建在这之上。`jsonpath.py` 只认 plain dict/list，也因此不受 `json_to_obj` 的 namedtuple 降级影响——含连字符或 Python 关键字的键都能正常断言。

**复用**：`json_matches` 复用了 `utils/match.py` 的 `Compare` 比较器分发（`$gt`/`$in`/`$contains`/`$startWith`/`$eq`/`$notIn`），未另造一套。比较器全部保持确定性、离线。

**验收**：46 条针对断言层的测试全绿，零网络依赖；并已接入既有 `test/testhttp/test_http_get.py`（该测试此前完全不检查状态码）。

### 1.2 传输层重写 ✅ 已完成（auth 除外）

| 问题 | 改造前 | 现在 |
|---|---|---|
| TLS | 所有 HTTPS 强制 `verify=False` | ✅ **默认 `True`**，调用方可显式 `verify=False` 退出 |
| 超时 | 默认 0 且从不生效 → 无限等待 | ✅ 默认 `(10s 连接, 30s 读取)`，**每个请求都有界** |
| 重试 | 无 | ✅ 指数退避；**仅幂等方法**（POST/PATCH 不重试，避免重复提交） |
| 错误语义 | 连接错误裸抛，无上下文 | ✅ `HttpTimeoutError` / `HttpConnectionError`，带 url/method/elapsed |
| 连接池 | 仅 requests 默认 | ✅ `pool_maxsize` 可配 |
| auth | `set_auth` 无调用方 | ⬜ **未做**，见下方说明 |

新增 `core/protocol/http/transport.py`：`TransportPolicy` 数据类 + `build_adapter()` + `mount()` + `translate_error()`。全部经 `Runtime.Http` 读 `conf/config.yaml` 的 `http:` 段。

**`@api.http` / `@api.mark` 装饰器外观完全未变**——换的只是底下的实现。

**几个设计决定**

- **重试只覆盖幂等方法**（GET/HEAD/PUT/DELETE/OPTIONS/TRACE）。重放 POST 可能造成重复提交，需要重试的话由调用方显式声明。
- **只重试 429/502/503/504**。500 是真实缺陷，重试它只会把确定的失败伪装成偶发。
- **`raise_on_status=False`**——让响应走到断言层判定，而不是在 adapter 里炸掉。
- **传输错误与"响应不符合预期"分开**。前者压根没有响应可断言，因此抛异常而非返回 Check；且同时继承 `requests` 对应异常，既有的 `except requests.exceptions.Timeout` 不受影响。

**顺带修掉**（`SessionManager` 就在传输路径上，重写挂载逻辑时一并处理）：

- check-then-act 移入锁内——此前两个线程可能各建一个 session，其中一个连同 cookie 被丢弃
- `acquire()`/`release()` 改为 `with`——此前中间抛异常会**永久死锁** RLock
- `current_thread().getName()` → `.name`（3.10 起废弃）

**未做：auth 扩展点**。`set_auth` 至今无任何调用方，接它需要先确定认证形态（bearer / basic / 签名），而这取决于真实业务域——留待 P2 随 `biz/` 包一起定。这是有意保留的缺口，不是遗漏。

**验收**：22 条传输层测试全绿，零网络依赖。其中 TLS 默认值与 retry adapter 挂载两条做过**变异测试**——改回旧行为后测试确实失败，确认非假绿。

### 1.3 响应解析修复

实测缺陷（见 [`01`](./01-现状评估与起点决策.md) 第 3.3 节）：

| 输入 | 当前 | 目标 |
|---|---|---|
| `{"code":0,"data":{...}}` | 返回 `['code','data']`（键名） | 返回业务数据 |
| `{"code":0,"data":null}` | `TypeError` | `None` |
| `{"code":0,"data":5}` | `TypeError` | `5` |
| 含连字符/关键字的键 | 静默降级成 dict，下游 `AttributeError` | 类型稳定 |
| 非 JSON（HTML/二进制） | 行为不一致 | 明确且一致 |

**原则：不静默降级。** 当前 `responsehandler.py:31-37` 把异常吞进 `logger.debug` 并改变返回类型——同一个方法的返回类型取决于响应内容长什么样，这比抛异常更难排查。

### 1.4 全局状态清理

- `Runtime.Case.steps`（`runtime.py:298-305`）：进程级全局 dict + 单一全局 key + 破坏性 `pop` 读取 → 改为运行上下文绑定
- `SessionManager`（`session.py:76-86`）：check-then-act 移入锁内；`acquire()`/`release()` 加 `try/finally`（当前任何异常都会永久死锁）
- `Runtime` 各 classproperty 的进程级懒缓存 → 明确生命周期

### 验收

- [ ] 一组针对**本地 mock server** 的框架自测，覆盖 1.1~1.4 每一条
- [ ] **零网络依赖**——当前唯一的测试打真实 httpbin.org，不可接受
- [ ] 一个返回 500 的接口，测试**必须 FAIL**（当前会 PASS）
- [ ] 一个挂起的接口，在超时后**失败而非挂死**
- [ ] `pytest -n 4` 并行跑同一套件，结果稳定

## P2 · 业务语义层

> ⚠️ **依赖真实业务域。** 见本文末尾"开放依赖"。

按原方案 Part 2 实施，此处只列顺序与关键约束。

### 2.1 Fixture（工程量最大）

- 账号池 + **借出加锁**（否则并行跑 nonce 直接撞）
- `ensure_*` **幂等归位**（跑两次结果一致）
- `reclaim` 回收 → 账号从消耗品变可循环资产
- **前置不满足要 SKIP 不能 FAIL**——原方案 Part 2.1 指出这是自动化跑久了最大的噪音源
- teardown 覆盖所有副作用
- 余额/资源告警

### 2.2 Flow

依赖链：`P1 传输层` → `client 生成（OpenAPI）` → `flow`

关键约束（原方案 Part 2.2）：链式返回 `self`；上下文走 `self.ctx`（`build()`/`send()` 应无参）；路径分支用策略模式不用 if/else；**不做 fallback**；负向场景走显式 override 口。

### 2.3 领域 Invariant

起步 5 条即可（原方案 Part 3.2）。**最省的起点：把已有测试脚本里的 assert 抽出来，合并同类项。**

> 这一步依赖既有脚本资产。若 pandora 仓库中有可复用的用例/断言，需在此前完成对比——见"开放依赖"。

### 验收

- [ ] 五条用例能并行跑十次，资源不漂移
- [ ] 前置不满足时是 SKIP 不是 FAIL
- [ ] 词汇表自检通过：用现有 flow+invariant 符号，能写出需求文档里每条验收标准

### 3.2 MCP stdio server

先做两个：`run_tests` + `explain_failure`。

**输出必须分叉**：给人的是 HTML 报告，给 agent 的是结构化摘要 + `run_id`。把 pytest 原始日志返给 agent 会直接淹掉 context。

> 原方案 Part 8 主张"MCP 不要放最后"，理由是越早暴露越早发现哪些 tool 真需要。本计划把它放在 P1 之后而非最前，原因是 `run_tests` 需要先有**值得跑的用例**和**判得出对错的断言**——在 P1 完成前，MCP 能暴露的只是一个 500 会 PASS 的套件。这是对原方案的一处有意偏离。

## 与原方案的差异说明

本计划基于 [`00-原始设计方案.md`](./00-原始设计方案.md)，有两处有意偏离，均已在上文标注理由：

| 差异 | 原方案 | 本计划 | 理由 |
|---|---|---|---|
| `core/protocol` 处置 | 列入"留" | **重写** | 实测成熟度 2/10：无断言层、`verify=False`、无超时、响应解析错误 |

新增了原方案未覆盖的 **P0 清理阶段**——原方案假定了一个健康的起点，实测不成立。
