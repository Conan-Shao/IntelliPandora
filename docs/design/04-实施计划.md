按"挡不挡得住真实测试"排序：

### 1.1 断言层 ✅ 已完成

**改造前：完全不存在。** 全 `src/` 无 `raise_for_status`；`status_code` 唯一用途是给日志上色。**接口返回 500，测试照常 PASS。**

已按原方案 Part 2.3 建成 `core/assertion/`：

| 文件 | 内容 |
|---|---|
| `check.py` | `Check` 数据类 + `Source` 常量（api/schema/derived/authz/onchain） |
| `collector.py` | `assert_all` 收集器、`require` 前置条件 |
| `http.py` | `status_ok` / `status_is` / `header_is` / `json_has` / `json_equals` / `json_matches` / `schema_conforms` |
| `jsonpath.py` | 点号+下标路径解析，失败时给出停在哪一段 |

```python
from ipandora.core.assertion import assert_all, status_ok, json_equals

assert_all(
    status_ok(resp),                      # 没有这行，500 就是 PASS
    json_equals(resp, 'data.id', 1),
    json_equals(resp, 'data.name', 'alice'),
)
```

**三个关键设计**

1. **Check 是值不是异常** —— 构造失败的 Check 不抛，因此一次运行能看到全部失败而不是第一个。`assert_all` 才是判定者，抛标准 `AssertionError`（pytest / RF 都能原生渲染）。
2. **`require` 与 `assert_all` 分家** —— 前置不满足走 skip 不走 fail。原方案 Part 2.1 指出混淆这两者是长期运行套件最大的噪音源。
3. **绕开 `fetch_all()`** —— 断言直接读原始响应体。写这一层时 `ResponseHandler` 会把单对象负载拆成字段值、对 null/标量抛 `TypeError`（见 [`01`](./01-现状评估与起点决策.md) 第 3.3 节），断言层不能建在这之上。`jsonpath.py` 只认 plain dict/list，因此也不受 `json_to_obj` 当时 namedtuple 降级的影响。

> 这些解析缺陷已在 **1.3** 修复。但断言层继续直接读原始响应体——判定"对错"不应该依赖另一层的解析约定，这个解耦本身是对的，不因下游修好而回退。

**复用**：`json_matches` 复用了 `utils/match.py` 的 `Compare` 比较器分发（`$gt`/`$in`/`$contains`/`$startWith`/`$eq`/`$notIn`），未另造一套。比较器全部保持确定性、离线。

**验收**：46 条针对断言层的测试全绿，零网络依赖；并已接入既有 `test/testhttp/test_http_get.py`（该测试此前完全不检查状态码）。

### 1.2 传输层重写 ✅ 已完成（auth 除外）

| 问题 | 改造前 | 现在 |
|---|---|---|
| TLS | 所有 HTTPS 强制 `verify=False` | ✅ **默认 `True`**，调用方可显式 `verify=False` 退出 |
| 超时 | 默认 0 且从不生效 → 无限等待 | ✅ 默认 `(10s 连接, 30s 读取)`，**每个请求都有界** |
| 重试 | 无 | ✅ 指数退避；**仅幂等方法**（POST/PATCH 不重试，避免重复提交） |
| 错误语义 | 连接错误裸抛，无上下文 | ✅ `HttpTimeoutError` / `HttpConnectionError`，带 url/method/elapsed |
| 连接池 | 仅 requests 默认 | ✅ `pool_maxsize` 可配 |
| auth | `set_auth` 无调用方 | ⬜ **未做**，见下方说明 |

新增 `core/protocol/http/transport.py`：`TransportPolicy` 数据类 + `build_adapter()` + `mount()` + `translate_error()`。全部经 `Runtime.Http` 读 `conf/config.yaml` 的 `http:` 段。

**`@api.http` / `@api.mark` 装饰器外观完全未变**——换的只是底下的实现。

**几个设计决定**

- **重试只覆盖幂等方法**（GET/HEAD/PUT/DELETE/OPTIONS/TRACE）。重放 POST 可能造成重复提交，需要重试的话由调用方显式声明。
- **只重试 429/502/503/504**。500 是真实缺陷，重试它只会把确定的失败伪装成偶发。
- **`raise_on_status=False`**——让响应走到断言层判定，而不是在 adapter 里炸掉。
- **传输错误与"响应不符合预期"分开**。前者压根没有响应可断言，因此抛异常而非返回 Check；且同时继承 `requests` 对应异常，既有的 `except requests.exceptions.Timeout` 不受影响。

**顺带修掉**（`SessionManager` 就在传输路径上，重写挂载逻辑时一并处理）：

- check-then-act 移入锁内——此前两个线程可能各建一个 session，其中一个连同 cookie 被丢弃
- `acquire()`/`release()` 改为 `with`——此前中间抛异常会**永久死锁** RLock
- `current_thread().getName()` → `.name`（3.10 起废弃）

**未做：auth 扩展点**。`set_auth` 至今无任何调用方，接它需要先确定认证形态（bearer / basic / 签名），而这取决于真实业务域——留待 P2 随 `biz/` 包一起定。这是有意保留的缺口，不是遗漏。

**验收**：22 条传输层测试全绿，零网络依赖。其中 TLS 默认值与 retry adapter 挂载两条做过**变异测试**——改回旧行为后测试确实失败，确认非假绿。

### 1.3 响应解析修复 ✅ 已完成

| 输入 | 改造前 `fetch_all()` | 现在 |
|---|---|---|
| `{"code":0,"data":{"id":1,"name":"alice"}}` | `[1, 'alice']` 拆成字段值 | ✅ `[{'id':1,'name':'alice'}]` |
| `{"code":0,"data":null}` | `TypeError` | ✅ `[]` |
| `{"code":0,"data":5}` | `TypeError` | ✅ `[5]` |
| `{"data":"hello"}` | 逐字符拆开 | ✅ `['hello']` |
| 含连字符/关键字的键 | 静默降级成 dict，`filter()` 随即 `AttributeError` | ✅ 类型恒定，可正常 filter |
| 非 JSON（HTML/二进制） | 包成假对象 | ✅ 原样返回 str / bytes |

**两处根因**

1. **`target` 无差别迭代** —— 只有 list 本身就是"多个条目"，其余都是"一个条目"，null 是"零个条目"。提取为 `as_item_list()`。
2. **`json_to_obj` 的 namedtuple 降级** —— 键名含连字符或是 Python 关键字时 namedtuple 构造失败，被 `except` 吞掉退化成 dict，**解析结果的类型取决于响应键名长什么样**，下游 `filter()` 在这些对象上 `AttributeError`。

改用 `JsonObject(dict)`——一个支持属性访问的 dict：

```python
resp.data.origin          # 既有 API，不变
resp.data['x-req-id']     # namedtuple 永远做不到的键
```

**类型恒定，降级这个概念本身消失了。** 且 `isinstance(resp.data, dict)` 成立，`_asdict()` 保留以兼容既有调用方。

**顺带修掉**

- `fetch_one()` 无数据时返回 `[]` → 改为 `None`（要一个条目却拿到空列表，读起来像"这就是你的条目，它是个列表"）
- `__len__` 调用消耗性的 `fetch_all()` —— **`len()` 有副作用**，且会清掉已应用的 filter；`__next__` 每次迭代调三次。改为非消耗性读取
- 缺失字段的 `AttributeError` 现在会列出可用字段名

**验收**：41 条解析测试全绿；既有 `response.data.origin` 用法完全不受影响。

### 1.4 全局状态清理 ✅ 已完成

**`Runtime.Case`** —— 步骤记录原本是进程级全局 dict + **单一进程级** case 名，任何并发下所有线程的步骤都记到"最后一个被设置的"用例名下。且 `steps` 读取是破坏性 `pop`：第一个读的人把它清空，第二次读静默返回 `[]`。

改为 **thread-local**，读取非破坏性；要取走用 `drain_steps()`，清理用 `clear()`。

**`MultiHandle`** —— 缓冲区是**类级属性，被所有实例共享**，且生产者与后台线程无锁并发读写，并发 put/flush 会丢条目。

- 缓冲区改为**每实例**，用锁保护；批次在锁内取出、上传在锁外做
- `while True: sleep(1)` 忙等改为 `Event.wait()`，线程可停止且 `stop()` 立即生效
- `atexit` 注册加了去重 —— 此前两个 `__init__.py` 各注册一次，同一个 handler 注册了两遍

> 注：`MultiHandle` 的实际上传逻辑在源码里是注释掉的，所以它目前只批不传。并发仍然照修 —— **恰好休眠的坏并发依然是坏并发**，而且一旦有人取消注释就会踩到。

**`Runtime` 配置懒缓存** —— 每个配置项首次读取后进程级 memo。正常运行没问题，但一个测试改了配置就会泄漏给后面所有测试，且重新赋值 `Runtime.settings` 对已读过的项无效。

新增 `Runtime.reset()`：从**导入时快照的真实默认值**恢复（不是按类型猜空值），支持整体或按段 `Runtime.reset('Http')`。快照会跳过 `threading.local` 等活状态。

我自己在 1.2 写的传输层测试就因为这个泄漏必须套 `try/finally`，现在换成了 `reset_runtime` fixture。

**验收**：19 条全局状态测试全绿；全量套件连跑 3 次结果一致（无测试间泄漏）。thread-local 与 per-instance 缓冲两条做过**变异测试**。

> 变异测试期间发现自己写的两条测试是假绿：一条 `assert len(uploadItem(force=True) or ...) == 0` 恒真（`uploadItem` 返回 `False`）；另一条读回自己刚写的值，而全局态下读写会跟随**同一个**错误的 case 名，因此读回来照样相等。都已改成能真正判伪的断言。

## P3 · 入口层 ✅ 已完成（provision / impact 除外）

### 3.1 runner 改为可库调用 ✅ 已完成

```python
from ipandora.core.runner import run, explain

result = run('test/testassertion', env='dev')
result.ok            # bool
result.summary()     # 裁剪过的 dict，可直接给 agent
explain(result.run_id)   # 完整 traceback，按需取
```

新增 `core/runner/`：`api.py`（`run` / `explain`）、`result.py`（`RunResult` / `CaseResult`）、`collector.py`（pytest 插件）、`store.py`（按 run_id 归档）。

MCP 的 `run_tests` / `explain_failure` / `list_runs` 全部走它，**不再 subprocess 调 pytest 解析 stdout**——那是原方案 Part 4 明确反对的做法，也是上一轮的实现方式。

**输出分叉**（原方案 Part 4/5 的要求）：`summary()` 给 agent，只带失败用例名 + 断言消息 + `detail_hint`；完整 traceback 留在 run store，由 `explain_failure(run_id)` 显式取。实测同一次失败运行：summary 836 字符 vs explain 2916 字符。

断言层在这里回报了一次——`assert_all` 的失败消息本身是结构化的，直接进 summary 就是可执行的信息：

```
[FAIL] 请求成功 (2xx) (api) | status = 500
[FAIL] data.id == 1 (api) | data.id = 7 (expected 1)
```

**实现中发现并修掉的三个真问题**

1. **重复调用会崩** —— pytest 默认 `prepend` 导入模式按 basename 索引 `sys.modules`，第二次跑另一个目录下同名的 `test_api.py` 会 `import file mismatch` 中止收集。而"可被反复库调用"正是这一层存在的理由。改用 `--import-mode=importlib`。
2. **选择器写错会静默报成功** —— 不存在的路径会 fallback 成 `-k` 表达式，匹配不到任何用例，pytest 退出码 5，而 `ok` 仍是 `True`。**打错一个字就等于"全部通过"**。现在退出码 2/3/4/5 一律转成 `collect_error`，`ok=False`。
3. **stdout 污染 MCP 协议** —— stdio 传输下 stdout 就是 JSON-RPC 流。pytest 的进度输出、以及框架自己的 logger（`log.py` 用的是 `StreamHandler(sys.stdout)`）都会插进协议消息中间，直接断连。实测泄漏 172 字节。现在 `run(quiet=True)` 重定向 pytest 输出，`serve()` 在 stdio 模式下调 `log_to_stderr()`。

### 3.2 MCP 能力面

| tool | 状态 |
|---|---|
| `run_tests(selector, env)` | ✅ 走库调用，返回裁剪摘要 |
| `explain_failure(run_id)` | ✅ 完整现场 |
| `list_runs(limit)` | ✅ 最近的 run_id |
| `get_test_report(xml)` | ✅ 保留 |
| `provision(spec)` | ⬜ 依赖 P2 的 `core/fixture` |

> 原方案 Part 8 主张"MCP 不要放最后"，理由是越早暴露越早发现哪些 tool 真需要。本计划把它放在 P1 之后而非最前，原因是 `run_tests` 需要先有**判得出对错的断言**——在 P1 完成前，MCP 能暴露的只是一个 500 会 PASS 的套件。这是对原方案的一处有意偏离。

## P4 · 失败归因 ✅ 已完成（LLM 部分默认关闭）

**关键设计：分类由规则做，LLM 只加散文。** 这是原方案推论①「能被规则解决的，别请模型」的直接应用——归因的核心价值是分类，而分类有明确签名，规则做得又快又准又免费。

### 规则归因（`core/triage/`，始终开启，零成本）

| 类别 | 含义 | 归咎于被测系统？ |
|---|---|---|
| `defect` | 断言失败，系统返回了错的值 | ✅ |
| `contract` | **只有** schema 检查失败 → 接口变了 | ✅ |
| `environment` | 传输失败，压根没拿到响应 | ❌ 什么都没测到 |
| `data` | 前置不满足（`require` skip） | ❌ |
| `harness` | setup/teardown 炸了，测试自身坏了 | ❌ |
| `unknown` | 签名不认识——**不猜** | — |

**`blames_system_under_test` 这个区分是全部意义所在**：把"连不上服务器"和"服务器答错了"混为一谈，是让人不再看红灯的最快方式。

断言层在这里第二次回报——`Check.src`（api/schema/derived/authz/onchain）是现成的信号：全是 `schema` 就是契约漂移，`derived` 就是业务逻辑错。这个维度在断言时就记下了，归因时白拿。

### LLM 归因（`ai/triage.py`，默认关闭）

只做一件事：把多条失败的**共同根因**用自然语言说一句。**它不决定类别。**

架构上的难点是保证3（`core/` 不得 import `ai/`）——归因在 core，LLM 在 ai。解法是注册表：`core/triage/hooks.py` 拥有插槽，`ipandora.ai.enable()` 往里注册。core 不知道 ai 存在；没注册时 `analyze()` 返回空串，这正是 `rm -rf ai/` 之后的状态。

### 五条保证的验收结果

- [x] `pip install intellipandora` 不装任何 LLM SDK（`extras_require`）
- [x] 默认配置 `ai.enabled: false`
- [x] **`core/` 不 import `ai/`** —— CI 静态检查，改成 AST 解析（见下）
- [x] **`rm -rf src/ipandora/ai/ && pytest` 全绿**（212 passed）
- [x] 预算闸生效；provider 故障/未装 SDK/未配置 全部 fail-open 返回空串，**测试结论不受影响**
- [x] 成本随失败数而非测试规模增长：**全绿的运行 0 次调用**；25 条失败也只调 1 次（每次运行一次，不是每条失败一次）

### 实现中发现并修掉的两个真问题

1. **`max_calls_per_run` 无法设为 0** —— classproperty 用 `if not self._x` 判空，把配置的 0 当成"未设置"再读回默认 20。**预算闸最严格、最有用的那个值恰恰设不进去**。改用 `is None` 哨兵。这和 1.2 修过的 `verify` 是同一类 falsy 陷阱。
2. **分层检查是文本 grep，会误报** —— `core/triage` 的文档里必然要提到 `ipandora.ai`（它拥有 ai 要插的那个钩子），旧的 grep 把散文当成 import 报错。改成 **AST 解析真实 import 语句**，另加一条正则兜住 `importlib.import_module('ipandora.ai...')` 这种动态形式。两种变异都验过能抓住。

### 未做

**报告摘要**（把结构化结果转成人话）留着。它和失败归因共用同一条通路，等报告层（`core/report/`）从 `utils/robotlogparser.py` 提取重构时一并做更合理。
