# 现状评估与起点决策

> 2026-08 · 基于 commit `34eaeed`（改造前的仓库状态）的实测审计

---

## 结论先行

**起点选 IntelliPandora，但不是在它上面做增量改造，而是把它当作"容器"重写内核。**

两句话解释这个区别：

- **容器保留**：仓库、PyPI 包名 `intellipandora`、`src/` 布局、架构分层意图、`@api.http` 装饰器的**外观设计**、pluggy 插件机制。
- **内核重写**：`core/protocol` 的传输层与响应层。原始设计方案说这一块要"留"——但实测下来，**它恰恰是全仓库质量最差的部分**。

这不是唱衰。装饰器 ergonomics 和 `@api.mark` 端点间接寻址是真正的好想法，值得保留；问题在于它们底下几乎没有可用的实现。

## 一、起点：pandora vs IntelliPandora

| | pandora | IntelliPandora |
|---|---|---|
| 定位 | 更早的同类框架，功能重叠 | 现役 |
| 可见性 | 私有仓库 | 公开，已发布 PyPI |
| 在架构图中的角色 | `business_flow.png` 里被列为 **Runner 之一**（与 RobotFramework、main 函数并列） | 图中的"集成框架"本体 |
| 活跃度 | — | 2024-05 ~ 2024-07，16 次提交后停滞 |

**判定：无争议选 IntelliPandora。** 两者功能重叠时，没有理由回退到更早的一版；且架构图本身已经把 pandora 定位为执行入口而非框架主体。

> **待补**：pandora 仓库当前无访问权限，以上基于项目作者描述与架构图推断。若其中存在可复用的资产（尤其真实业务用例、断言积累），需要在 P0 阶段前补一次对比——原始设计方案里"从现有脚本抽 assert 得到 invariant v0"这一步，依赖的正是这类资产。

## 二、真正的问题：改造还是重写

起点定了，下一个问题才是关键。原始设计方案 Part 6.1 给出了砍/留/加清单：

- **砍**：`core/engine/generate`、RobotFramework 适配、UI/算法域、`run/` 脚手架
- **留**：`core/protocol`、`core/base`、`utils`、`conf`
- **加**：`core/fixture`、`core/invariant`、`core/triage`、`mcp/`

把这份清单对到实际代码量上：

| 区域 | LOC | 清单归属 | 实测状态 |
|---|---|---|---|
| `core/engine/generator` | 2737 | 砍 | 最大单块；也是全部模型债与死代码的来源 |
| `core/protocol` | 1313 | **留** | **成熟度 2/10（详见第三节）** |
| `utils` | 942 | 留 | 可信 |
| `common` | 631 | 留 | 可信 |
| `core/schedule` | 586 | 留 | 含全局可变状态问题 |
| `core/base` | 581 | 留 | 可信 |
| `run` | 480 | 砍 | — |
| `core/engine/crypto` | 405 | — | 自洽可用 |
| `core/plugin` | 229 | 留 | 机制可用 |
| **合计** | **8415** | | |

**矛盾点**：清单里唯一要"留"的核心能力（`core/protocol`），是实测质量最低的部分。砍掉 `generator` 和 `run` 之后，剩下约 5200 LOC，其中真正承载"接口自动化能力"的只有那 1313 行——而它需要重写。

**所以答案是"以 IntelliPandora 为容器重写内核"，而不是"在 IntelliPandora 上增量加功能"。**

## 三、`core/protocol` 实测缺陷

以下每条均**直接验证**，非静态推测。行号对应 `34eaeed`。

### 3.1 所有 HTTPS 强制关闭证书校验

`core/wrapper/requestwrapper.py:82-84`：

```python
# deal with parameters `verify` which controls TLS certificate.
if 'https' in self.request_proxy.path and 'verify' not in self.params:
    self.params.update({'verify': False})
```

除非调用方显式传 `verify`，**每一个 HTTPS 请求都跳过证书校验**。这既是安全问题，也意味着框架永远发现不了证书过期/配置错误这类线上事故。

### 3.2 没有任何断言层——500 静默通过

全 `src/` 搜不到 `raise_for_status`。`status_code` 在整个代码库里的唯一用途是给日志上色（`core/protocol/http/model/data/responseobject.py:73-74`）。

**后果**：接口返回 500，测试照常 PASS，除非用例作者手写 `assert response.response.status_code == 200`。这是当前最大的能力缺口——**框架不具备"判定对错"的能力**。

### 3.3 响应解析对常见结构返回错误数据

实测（`ResponseHandler.fetch_all()`）：

| 输入 | 期望 | 实际 |
|---|---|---|
| `{"code":0,"data":{"id":1,"name":"alice"}}` | 业务数据 | `['code', 'data']` ← **返回的是键名** |
| `{"code":0,"data":null}` | `None` 或空 | `TypeError` |
| `{"code":0,"data":5}` | `5` | `TypeError` |

根因在 `core/protocol/http/model/handler/responsehandler.py:161-169` 无差别迭代。另外 `json_to_obj`（同文件 `:26-58`）在遇到 Python 关键字或含连字符的 JSON 键时，namedtuple 构造失败被 `except` 吞掉并**静默降级成 dict**——同一个方法的返回类型取决于响应的键名长什么样，下游 `filter()`（`:241`）随即在这些降级对象上 `AttributeError`。

### 3.4 默认无超时

`core/protocol/http/model/option/apioption.py:22` 默认 `_timeout = 0`，仅在真值时生效；而 `requestwrapper.py:73` 的 `build()` 从不调用 `set_timeout`。

**结果：所有请求无限等待。** 一个挂起的接口挂死整个套件。

### 3.5 其余

- **无重试/退避**：全 `src/` 无 `retry`、`backoff`、`max_retries`、`HTTPAdapter`。
- **auth 形同虚设**：`optioninterface.py:72` 的 `set_auth` **没有任何调用方**；无 bearer/basic/OAuth/签名助手。
- **无法流式处理**：`responseobject.py:87,162` 急切读取 `.text`/`.content`，`stream=True` 失效，大响应全量进内存。
- **插件钩子是只读的**：`PluginManager.run('request'|...)` 的返回值被丢弃，插件无法改写或中断请求。

### 3.6 全局可变状态破坏并行

`core/schedule/runtime.py:298-305`：

```python
@classproperty
def steps(self) -> List:
    return self._case_steps.pop(self.cur_case_name, [])
```

`_case_steps` 是**进程级全局 dict**，键是**单一全局** `_cur_case_name`，且读取是**破坏性 `pop`**。多线程或 locust 模式下，请求步骤会记到最后一次设置的用例名下，且读一次就没了。

`core/schedule/session.py:76-86` 的 `SessionManager` 也有问题：check-then-act 在锁外；`acquire()`/`release()` 没有 `try/finally` 包裹——**任何异常都会永久死锁该 RLock**。

`pytest-xdist` 靠进程隔离能绕过，真正的进程内并发不行。

## 四、代码健康度

### 4.1 死代码：39 个模块从未被 import

最值得注意的一处：`core/engine/generator/service/robotcaseservice.py`（10KB）**没有任何调用方**，而它是 `model/handler/robotrenderer.py` 的唯一导入者。

**即：新版 Robot 渲染路径写完了，从来没接上；实际在跑的是 legacy 版本。** `robotprovider.py:8-11` 用的是 `RobotCaseLegacy` / `RobotSuiteLegacy` / `RobotRendererLegacy`。

### 4.2 双份数据模型并行存活

`model/data/case.py`（215 行）与 `model/data/testcase.py`（212 行）是近乎逐字的分叉，`Project`/`Module`/`Submodule`/`Tag`/`TagCategory` 五个类**字节级相同**。

要命的是两边都在用：

- 用 `case.py`：`testcaserepository`、`teststeprepository`、`testcasetagsrepository`、`attachmentrepository`、`modulerepository`、`testcaseserivce`
- 用 `testcase.py`：`tagrepository`、`projectrepository`、`tagcategoryrepository`、`submodulerepository`

**`modulerepository` 返回 `case.Module`，`submodulerepository` 返回 `testcase.Submodule`——同一张表两个类。** 这是全仓库最大的单点债务：调用方无法确定拿到的是哪一个。

### 4.3 曾经进入 release 的崩溃 bug

`34eaeed`（即 v1.1.0 发布状态）中，`teststeprepository.py:9` 从 `data.testcase` 导入 `TestStep`，函数体却用 `Step`；`testcasetagsrepository.py:10` 同类问题。**这两个模块 import 即崩溃**，且随版本发布了出去。

没有 CI 是根因——见 4.5。

### 4.4 公开仓库中的硬编码凭据

`core/schedule/runtime.py:279-285`：

```python
report_host = 'https://xxxx.com'
# report_host = 'http://10.40.56.199:31000'
user_name = 'ficus-ci'
password = '<已redact，见该文件实际内容>'
```

按该密码串做 `git log -S` 检索，显示引入于 `554f09f`（"first commit to git hub"）——**存在于每一个已发布的提交和每一个 PyPI 分发包中**。另有两个前雇主内网域名泄漏：`internal-mirrors.yitu-inc.com`（`runtime.py:281` 注释）、`zentao.i5cnc.com`（`programhandler.py:158`）。

项目作者已确认该凭据**已失效/从来不是真实凭据**，因此无需紧急轮换。但仍需清理，并加 pre-commit 扫描防止再次发生——因为机制本来就有：`runtime.py:66-70` 已支持 base64+AES 解密配置项，只是 `Runtime.Host` 没用。

### 4.5 测试与 CI

- 原始仓库**只有 1 个真实测试**（`test/testhttp/test_http_get.py`），且依赖真实网络（打 httpbin.org）。
- **无任何 CI**：无 `.github/`、无 `.gitlab-ci.yml`、无 `Jenkinsfile`。
- `Makefile` 的 test 目标指向 `tests/`，实际目录是 `test/`——**从未跑通过**。
- 生成器、repository、service、protocol、crypto、schedule 层（约 90% 代码）零测试覆盖。

### 4.6 打包与环境

- **`python_requires='>=3.7'` 是错的**：`testcaseserivce.py:176` 使用 PEP 604 联合类型 `int | list[int]`，且全仓库无 `from __future__ import annotations`，因此在 3.7–3.9 上 import 即 `TypeError`。**真实下限是 3.10。**
- **`SSHLibrary` 未声明**：`programhandler.py:9` 导入，但不在 `requirements.txt`/`setup.cfg` 中——`pip install intellipandora` 后该模块必然 ImportError。
- `setup.py:71` 同时提供 `scripts=` 和 `entry_points`，重复。

### 4.7 一致性

- 文件名拼写错误：`testcaseserivce.py`（应为 service），且被 3 个模块导入。
- `runtime.py` 是全仓库**唯一使用 Tab 缩进**的文件（356 行 Tab，其余文件全部 4 空格）。
- 同一个类里混用 `camelCase`（`getMetaData`）与 `snake_case`（`get_test_case_by_id`）。

### 4.8 总体配比

| | 占比 | 说明 |
|---|---|---|
| 生产质量 | ~20% | `common/`、`utils/`、`core/base/classwrap/` |
| 原型 | ~55% | generator/repository/service 栈：能跑，无测试，双模型，`return -1` 错误信号 |
| 死代码或损坏 | ~25% | 39 个孤儿模块、未接上的"新版"渲染路径、错误的 Python 下限 |

## 五、一个高杠杆发现

第 4.1、4.2 节的问题——**39 个孤儿模块、双份数据模型、legacy 双路径——全部集中在 `core/engine/generator` 及其 repository 栈内**。

而原始设计方案本来就要砍掉这一块。

> **归档 generator 这一个动作，同时消灭最大的模型债、legacy 债和绝大部分死代码。**
>
> 代码量从 8415 LOC 降到 5372 LOC（126 → 92 个模块），且剩下的全部可信。

这应该是 P0 的第一个动作——它不是"顺便清理"，而是**用一个已经决定要做的决策，一次性解决三类最难缠的债务**。

## 六、三张清单

### 留（不动或小修）

| 内容 | 理由 |
|---|---|
| 仓库、PyPI 包名 `intellipandora`、`src/` 布局 | 布局正确，包名已占位 |
| 架构分层意图 | `framework_architecture.jpg` 的"框架核心/业务工程"与原始设计方案的"内核/业务包"是同一个划分，方向本来就对 |
| `@api.http` / `@api.mark` 装饰器**外观** | ergonomics 是真正的好想法，端点间接寻址解耦了环境与用例 |
| pluggy 插件机制（`core/plugin`） | 机制可用；需修钩子返回值被丢弃的问题 |
| `core/engine/crypto` | 405 LOC，自洽，有明确的 ABC+Factory 结构，可作为其他模块的范式 |
| `utils/`、`common/`、`core/base/classwrap/` | 审计认定的生产质量部分 |

### 归档（移出主干，保留在 tag/分支，不物理销毁）

| 内容 | LOC | 理由 |
|---|---|---|
| `core/engine/generator` 全栈 | 2737 | 原方案要砍；连带解决双模型、legacy、孤儿模块三类债 |
| RobotFramework 适配 | — | 关键字驱动用户群消失；且降低 agent 生成用例的质量 |
| `run/` 脚手架子命令 | 480 | agent 不需要 scaffold |
| MySQL 用例库 + 报表平台线 | — | 与"垂直优先"定位冲突，转入长期路线图 |

### 重写（保留外观，替换实现）

| 内容 | 重写内容 |
|---|---|
| `core/protocol/http` 传输层 | 默认超时、重试/退避、`verify` 默认 True、连接池配置、可用的 auth |
| `core/protocol/http` 响应层 | 正确处理单对象/null/标量/非 JSON/特殊键名；不再静默降级 |
| **断言层（新建）** | `Check` 对象 + `assert_all` 收集器——当前完全不存在 |
| `core/schedule/runtime.py` 全局状态 | 去掉进程级可变缓存与破坏性读取，支持并行 |
