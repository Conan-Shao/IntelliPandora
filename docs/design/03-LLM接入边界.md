# LLM 接入边界

> 本文回答一个具体约束：**LLM 接入口是好东西，但因为成本，不能默认对所有人开放。基础自动化能力才是主体，LLM 接入是规划。**
>
> 这不只是"加个开关"的问题——开关是约定，约定会被绕过。本文给出的是**结构性保证**：让"不花钱"成为默认且难以意外破坏的状态。

---

## 一、核心原则

> **LLM 只出现在"编写时"和"运行后"，绝不出现在"运行时"。**

这条原则同时来自两个方向，因此格外可靠：

- **成本方向**（本文出发点）：运行时是唯一会被高频、大规模、无人值守触发的时机。放在这里，成本随测试规模线性增长且不可控。
- **质量方向**（[`00-原始设计方案.md`](./00-原始设计方案.md) Part 0 推论①）："能被规则解决的，别请模型。" LLM 有幻觉、有延迟、有抖动——把它放进断言路径，等于用不确定的东西去判定确定性的事。

两个方向指向同一个结论。

---

## 二、三层时机与成本模型

| 时机 | 是否用 LLM | 干什么 | 成本随什么增长 |
|---|---|---|---|
| **编写时**<br>（写用例 / flow / invariant 草稿） | ✅ 用，但在框架之外 | agent 读词汇表 → 写文件 | 人 × 编写次数 |
| **运行时**<br>（执行用例、断言判定） | ❌ **绝不** | —— | **恒为 0** |
| **运行后**<br>（失败归因、报告摘要） | ⚠️ 可选，**默认关** | triage、explain_failure | 失败数（可设上限） |

### 关键结论

> **成本不随测试规模增长。**
>
> 一天跑 10000 次用例、0 次失败 → **LLM 调用 0 次，成本 0**。

这正面回答了成本顾虑。展开说三点：

**1. 编写时的成本不由框架承担。**
用例由 agent（Claude Code 等）读着 flow/invariant 词汇表直接写文件产生——这发生在开发者自己的订阅额度内，框架不代付、不代管。而且原始设计方案 Part 4 明确要求"生成用例不做成 MCP tool"，正好保证了这条：**框架里根本没有"生成用例"这个能力，也就没有对应的成本入口。**

**2. 运行时零成本是硬约束，不是优化目标。**
见第三节的五条结构性保证。

**3. 运行后成本与失败数挂钩，且有上限。**
归因只在失败时触发。稳定的套件失败少，成本自然低；套件不稳定时成本会上升——但那时该修的是套件，而且有预算闸兜底。

## 三、五条结构性保证

不靠"记得关掉"，靠架构让它默认关闭且不易破坏。

### 保证 1：安装时不带 LLM SDK

```python
# setup.py
extras_require={
    'ai':  ['anthropic'],   # 或其他 provider
    'mcp': ['mcp'],
}
```

`pip install intellipandora` → **不安装任何 LLM SDK**。
想用的人显式 `pip install intellipandora[ai]`。

这条保证了：**默认安装的用户，机器上连调用 LLM 的代码都没有。**

### 保证 2：默认配置关闭

```yaml
# conf/config.yaml
ai:
  enabled: false        # 默认关
  provider: null        # 不配则任何调用直接 no-op
  max_calls_per_run: 20 # 预算闸
```

配置缺失、provider 未配、`enabled: false` —— 三种情况都走同一条 no-op 路径，不报错、不重试、不静默降级成别的行为。

### 保证 3：`core/` 不得 import `ai/`

依赖方向单向：

```
ai/  ──依赖──▶  core/          ✅ 允许
core/ ──依赖──▶ ai/            ❌ 禁止
```

这条用 CI 静态检查强制（一条 grep 即可），不靠人自觉。

它保证了：**核心测试能力在物理上不可能触发 LLM 调用。**

### 保证 4：可删除性验收

```bash
rm -rf src/ipandora/ai/ && pytest      # 必须全绿
```

这条与原始设计方案 Part 1.1 对 MCP 的检验标准完全对称：

```bash
rm -rf src/ipandora/mcp/ && pytest biz/<域>/cases   # 必须全绿
```

两条标准表达同一件事：**MCP 是入口，LLM 是增强，都不是能力本身。**

**这条应该作为 CI 的一个 job 常驻**，否则迟早有人写出让核心依赖 `ai/` 的代码。

### 保证 5：预算闸 + fail-open

- **单次运行调用上限**：超过 `max_calls_per_run` 后停止调用，报告里标注"归因因预算上限截断"。
- **fail-open**：LLM 不可用（超时、限流、没配 key）时，**测试结果不受影响**——归因失败只是少一段分析文字，不能让一个本该 PASS 的用例变成 FAIL，也不能让 FAIL 变成 ERROR。

> 注意这里是 **fail-open**，与前面几条的"默认关闭"方向不同但不矛盾：
> 默认关闭是为了**不产生成本**；fail-open 是为了**LLM 故障不污染测试结论**。
> 一个管钱，一个管可信度。

## 四、"编写时"用 LLM 的正确形态

这一层不需要框架做什么，但需要框架**提供好的词汇表**——这是原始设计方案 Part 3.3 的核心洞察：

> **词汇表大** → AI 在造句，产出接近你自己写的
> **词汇表空** → AI 在造词，每个用例重新发明 HTTP 调用和断言

所以框架对"编写时 AI"的贡献方式是**间接的**：

| 框架做什么 | 效果 |
|---|---|
| 提供 `flows.py` 的方法签名 | AI 知道怎么走流程，不自己拼 HTTP |
| 提供 `invariants.py` 的判定函数 | AI 知道有哪些"对"可用，不临时发明 assert |
| 提供 `fixtures.py` 的状态构造 | AI 知道怎么拿资源，不自己造数据 |

**框架不需要内置任何 LLM 调用，就能让 AI 生成用例的质量大幅提升。** 这是成本最低的 AI 化路径——它的成本是零。

> 原始设计方案 Part 3.3 还有一条反直觉但重要的建议：**不要把 `openapi.yaml` 喂给 AI**。给了它就会绕过 flow 直接拼请求，反而退化。限制反而提升质量。

分支 `claude/ai-test-framework-iteration-29yom6` 上已有一次提交，完成于收到原始设计方案之前。它有三处直接违反本文原则，需要返工。**如实记录，不掩盖。**

| 内容 | 违反了什么 | 处置 |
|---|---|---|
| `Compare.cmp_semantic`<br>（`utils/match.py`） | **运行时断言里调 LLM**——违反核心原则与保证 3 | **删除** |
| `create_test_case` MCP tool<br>（`core/mcp/server.py`） | 原方案 Part 4："生成用例不做成 MCP tool" | **删除** |
| `run_test_suite` MCP tool | 原方案 Part 4："MCP 不要 shell 调 pytest 再解析 stdout"——当前实现正是 `subprocess.run(['pytest', ...])` + 解析 stdout | **重做**为 `core/runner/api.py` 库调用 |
| `list_test_cases` / `get_test_report` MCP tool | 依赖将被归档的 generator/MySQL 栈 | 随 generator 归档而移除 |
| `AIProviderABC` / `AIProviderFactory`<br>（`core/engine/ai/`） | 抽象本身没问题 | **保留**，迁到 `ai/`，改为服务运行后归因；补上保证 1/2/5 |
| `Runtime.Ai` / `Runtime.Mcp` 配置类 | —— | **保留**，`ai.enabled` 默认改为 `false` |
| `teststeprepository` / `testcasetagsrepository` import 修复 | —— | 随 generator 归档，修复自然失效 |

**为什么 `cmp_semantic` 是最需要删的一个**：它看起来最"AI 化"，实际最危险——它让每一次断言都可能变成一次付费的、有延迟的、结果不稳定的网络调用。一个跑 500 条用例的套件，可能产生 500 次 LLM 调用，且断言结果不可复现。这与"基础自动化能力优先"完全相反。

## 六、LLM 能力路线图（P4 之后）

在保证 1~5 成立的前提下，按价值排序：

| 能力 | 时机 | 价值 | 成本特征 |
|---|---|---|---|
| **失败归因**（`explain_failure`） | 运行后 | 高——失败分类 flaky/环境/数据/真 bug，是规模化的前提 | 与失败数挂钩 |
| **报告摘要** | 运行后 | 中——把结构化结果转成人话 | 每次运行 1 次 |
| **invariant 候选起草** | 编写时 | 中——AI 起草，人审定稿（原方案 Part 3.2 强调 invariant 必须人写） | 在开发者订阅内 |
| **接口 diff → 影响面**（`impact`） | 编写时/CI | 中——但原方案建议粒度停在 endpoint→consumer，别做全量 AST | 低频 |

**都不在 P0~P3 范围内。** 基础能力（断言层、fixture、可靠传输）没做完之前，做这些没有意义——归因需要有可归因的失败，而当前框架连 500 都判不出来。

---

## 七、一句话

> **框架的 AI 化程度，不由它内置多少 LLM 调用决定，而由它给 AI 提供了多好的词汇表决定。**

最好的 AI 化路径成本是零：把 flow、invariant、fixture 写好，让 agent 有东西可调用。
