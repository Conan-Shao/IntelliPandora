# 目标架构

> 本文不重复论述架构原则——那些在 [`00-原始设计方案.md`](./00-原始设计方案.md) 里已经讲透。
>
> **本文的职责是把那份方案落到 IntelliPandora 的真实路径上**：哪些目录已经存在、哪些要新建、哪些要重写，以及从现状到目标态的差距在哪。

---

## 一、先说一件事：新方案不是推翻原架构

仓库里已有的架构图 `docs/dev/static/framework_architecture.jpg` 画了两层：

```
业务工程   ← Test Case / Library(接口定义, 报告, 数据上报) / DATA
─────────
框架核心   ← Interface / SessionManage / Business Provider(protocol, driver) / library(plugin, report)
```

原始设计方案 Part 1.1 的分层是：

```
业务包     ← client(生成) / flow / fixture / invariant
─────────
框架内核   ← protocol / fixture机制 / invariant基类 / runner / report / triage
```

**这是同一个划分。** 原架构在两年前就把"框架给机制、业务给语义"的边界画对了。

新方案改的不是分层，是**业务层里放什么**：

| 位置 | 原架构 | 新方案 | 变化性质 |
|---|---|---|---|
| 业务层数据 | `DATA`（yaml 数据文件） | 删除，改为 fixture + 用例参数 | **推翻** |
| 业务层接口定义 | 手写 `http/grpc 接口定义` | 从 OpenAPI 生成 `client.py` | 改进 |
| 业务层编排 | （无此概念） | `flow.py` | **新增** |
| 业务层判定 | （散在用例的 assert 里） | `invariant.py` | **新增** |
| 入口 | Runner（RF / main / pandora） | Runner + **MCP** | **新增** |

只有 `DATA` 那一条是推翻——原始设计方案 Part 1.3 的理由是："AI 生成用例时 yaml 数据文件反而是障碍，它得同时改代码和数据文件，还得保持对应。"

**结论：这是一次架构补完，不是重来。** 这一点对判断工作量很重要——分层不用重新设计，只需要填充和替换。

## 三、三大构件落到本仓库

原始设计方案 Part 2 详述了 fixture / flow / invariant 的设计。这里只记录**与现状的接口点**。

### 3.1 Fixture

**现状：完全不存在。** 仓库里没有任何 setup/teardown、资源池、隔离概念。距离最近的东西是 `core/schedule/session.py` 的线程级 session 复用——但它本身有缺陷（见 `01` 第 3.6 节：check-then-act 在锁外、`release()` 无 `try/finally`）。

**含义**：这是纯新建，也是原始设计方案 Part 8 里估时最长的一块（"几天，难点在回滚策略"）。它不依赖现有代码，因此**不受 protocol 重写阻塞，可以并行推进**。

**唯一的现存约束**：账号池需要加锁，而 `SessionManager` 的锁用法是个反面教材，新代码不要照抄。

### 3.2 Flow

**现状：不存在，但底座在。** flow 依赖一个可靠的 client 调用层——那正是重写后的 `core/protocol` 要提供的。

**依赖顺序**：`protocol 重写` → `client 生成` → `flow`。这条链决定了 flow 不能最先做。

### 3.3 Invariant

**现状：不存在，但有一处可复用的基础设施。**

`utils/match.py` 的 `DictMatcher` / `Compare` 已经是一套 `$op → cmp_<op>` 的通用分发机制（`match.py:71`），支持 `$gt` / `$in` / `$notIn` / `$contains` / `$startWith` / `$eq`。

这套机制**可以作为通用 invariant 的底层比较器复用**——但要注意：

> ⚠️ 上一轮往这里加过一个 `cmp_semantic`（调 LLM 做语义判断）。**该方法需删除**——它把 LLM 放进了运行时断言路径，违反成本边界原则。详见 [`03-LLM接入边界.md`](./03-LLM接入边界.md)。

**分层归属**（照搬原始设计方案 Part 2.3）：

- 通用层 → `core/invariant/`：`value_conserved`、`schema_conforms`、`pagination_complete`、`idempotent`、`authz_denied`、`monotonic`
- 领域层 → `biz/<域>/invariants.py`：只有业务自己知道的判定

## 四、两条启动链路

原始设计方案 Part 4 定义了人/CI 与 agent 两条入口共用内核。落到本仓库的关键改造：

```
链路 A（人 / CI）              链路 B（agent）
pytest biz/<域>/cases          mcp.run_tests(selector)
        │                              │
        └──────────┬───────────────────┘
                   ▼
        core/runner/api.py : run(selector, env) -> RunResult
                   │
     fixture → client → flow → invariant → teardown → triage
```

**关键改造点：`core/runner/api.py` 必须是可库调用的函数，不是 CLI 包装。**

> ⚠️ 上一轮的 MCP `run_test_suite` 用 `subprocess.run(['pytest', path])` 再解析 stdout——**这正是原始设计方案 Part 4 明确反对的做法**（"MCP 不要 shell 调 pytest 再解析 stdout"）。需按上图重做。

### MCP 能力面

按原始设计方案 Part 5，四个 tool：

| tool | 状态 |
|---|---|
| `run_tests(selector)` | 🔄 重做为库调用 |
| `explain_failure(run_id)` | 🆕 依赖 `core/triage` |
| `provision(spec)` | 🆕 依赖 `core/fixture` |
| `impact(diff)` | 🆕 P4+ |

> ⚠️ 上一轮实现的 `create_test_case` MCP tool **需删除**。原始设计方案 Part 4 的理由："agent 本来就有文件读写能力，直接写文件更可控——能 review diff、能 git 管理。做成 tool 反而让用例凭空出现在看不见的地方。"

## 五、分层是否正确：可执行的检验标准

原始设计方案给了一条检验标准，本仓库照用，并补一条对称的：

```bash
# 标准一（原方案 Part 1.1）：MCP 是入口不是能力
rm -rf src/ipandora/mcp/ && pytest biz/<域>/cases   # 必须全绿

# 标准二（本文补充，见 03 号文档）：LLM 是可选不是依赖
rm -rf src/ipandora/ai/ && pytest                    # 必须全绿
```

两条标准表达同一件事：**MCP 和 LLM 都是"入口"和"增强"，不是"能力本身"。** 能力必须完整地活在 `core/` 和 `biz/` 里。

如果任一条不成立，说明能力写错了地方。

## 六、当前最大的能力缺口

把目标架构和现状对齐后，按"挡不挡得住真实测试"排序：

| 缺口 | 现状 | 后果 |
|---|---|---|
| **1. 无断言层** | 全 `src/` 无 `raise_for_status`；500 静默通过 | **框架不具备判定对错的能力**——这是最致命的 |
| **2. 无 fixture** | 完全不存在 | 无法保证测试起点确定，无法并行 |
| **3. 传输层不可靠** | 无超时、无重试、`verify=False` | 一个挂起接口挂死套件；发现不了证书问题 |
| **4. 响应解析错误** | 单对象返回键名，null/标量抛异常 | 拿不到正确数据，断言无从谈起 |
| **5. 全局状态破坏并行** | `Runtime.Case.steps` 破坏性读取 | 并发下数据串号 |

**1、3、4、5 都不依赖业务域，可以立即开工**——这正是"先做好基础自动化能力"的具体内容。2 需要真实业务场景才能设计对回滚策略。

## 七、开放依赖

原始设计方案全篇以 **Web3 钱包**（BSC、gasless、tokenPay、bundle、KMS signer）为垂直域。但：

- 该业务的 **OpenAPI spec 不在本仓库**
- 测试环境、账号池、链上环境（fork/anvil）均未接入
- pandora 仓库当前无访问权限，无法确认是否有可复用的既有用例

**影响范围**：

| 阶段 | 是否受阻 |
|---|---|
| P0 清理止血 | ❌ 不受阻 |
| P1 内核基础能力 | ❌ 不受阻 |
| P2 业务语义层（fixture/flow/领域 invariant） | ✅ **受阻，需要真实 spec 与环境** |
| P3 入口层 | 部分受阻（`run_tests` 需要有用例可跑） |

因此 [`04-实施计划.md`](./04-实施计划.md) 把 P0/P1 排在前面——它们是**纯内核工作，不等任何外部输入**。
