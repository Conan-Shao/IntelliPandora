# 测试报告

> 2026-08-02 · 对应 `src/ipandora/conf/static/report.html` 与 `core/evidence/`

## 起因

对比了另一个 agent 产出的 e2e 报告之后，差距很清楚——但**大部分不是 CSS 问题，是数据根本没被采集**。

框架当时的报告只有：用例名、状态、耗时、一段失败文本、归因分类。而运行过程中其实产生了远比这多的事实：

- 每个 `Check` 自带 `name` / `ok` / `expr` / `src`（判定维度）
- 每次 HTTP 调用都知道自己的请求头、请求体、状态码、响应头、响应体、耗时

**这些全被扔掉了**，报告再从 pytest 交回的那一段字符串里重新解析。所以报告只能说"这条挂了"，说不出别的。

---

## 补的三层

### 一、证据采集（`core/evidence/`）

一个被动的记录器：断言层交出 `Check`，传输层交出请求/响应，runner 的 pytest 插件在 setup 时开槽、teardown 时收走。

三条硬约束：

1. **绝不改变结论。** 记录器里任何异常都被吞掉——报告的 bug 不允许把绿的跑成红的。
2. **线程本地。** 用例会并行跑，证据记到别的用例名下比没有证据更糟——它会把人指向无辜的代码。
3. **交出即遗忘，不做归档。** 这条是被自己写的测试打出来的（见下）。

`setup` 而不是 `call` 开槽，是因为 fixture 也发请求，而 fixture 挂掉恰恰是最需要看它请求了什么的时候。

### 二、断言缺口（`gap()`）

```python
assert_all(
    status_ok(r),
    json_equals(r, 'data.status', 'SUCCESS'),
    gap('收款方余额实际增加', 'balanceOf(recipient) 前后差值 —— 未校验', src=Source.ONCHAIN),
)
```

`gap` 声明的是**这条用例应该判、但没有判**的东西。它不是通过，不是失败，两边都不能算：

- 传给 `assert_all` 是安全的，永远不会让运行失败
- 不计入"通过 N 条"——`5 通过` 读起来很扎实，`5 通过 · 3 未覆盖` 读起来才是实情
- 报告里单独成色（琥珀），并在末尾按名称聚合，带出现次数

**为什么必须手写声明**：没有任何运行能报告"一条没人写过的断言"。这和 `Status.GAP` 的道理一样——缺口是关于套件的陈述，不是关于被测系统的。

### 三、覆盖矩阵

套件在模块级声明坐标轴，用例用 `@pytest.mark.dims(...)` 落位：

```python
COVERAGE = [{'id': 'registry', 'title': 'registry × 校验维度', ...}]

@pytest.mark.dims(registry='pypi', dimension='authz')
def test_越权读取他人的包(self):
    ...
```

**空格子是这东西存在的全部理由**——它是一个没人写过用例的组合，而任何"结果列表"都不可能显示它。轴必须独立于用例声明，正是因为运行只知道自己跑过什么，永远不知道自己缺什么。

格子取该格里最差的用例状态：有失败即红，全是 skip 即琥珀，无用例是虚线空心。

## 报告本身

一次真实运行（10 条用例打 PyPI / npm / Go proxy）的结构：

| 区块 | 回答的问题 |
|---|---|
| 结论章 | 通过多少、通过率、几条无结论、几处未覆盖 |
| **覆盖矩阵** | **哪些组合根本没测** |
| **判定构成 · 按维度** | **这个套件到底判了什么**——数的是断言不是用例 |
| 失败归因 | 几条指向被测系统，几条是环境/数据 |
| 什么都没测到 | 被通过率排除掉的那些，单独列出 |
| 用例明细 | 每条的判定清单 + 每次 HTTP 往返 |
| 断言缺口汇总 | 下一轮该补什么，按出现次数排 |

几个刻意的选择：

- **判定构成按 `src` 维度拆开**。一个套件可以每条用例都绿，却只产出 `api` 类判定——那说明它只验证了"接口答了"，没验证"答得对"。这个条形图让这件事一眼可见，不用翻任何一条用例。演示套件里 `derived` 那一行是 `0✓ 3!`——三处缺口，零个判定。
- **每次请求带完整现场**：请求/响应头与体、状态码、耗时、瀑布条、`copy as curl`。复现失败是任何人拿到报告后做的第一件事。
- **失败原文默认收起**。上面的判定清单已经是结构化的同一份信息，原文只在需要贴给别人时展开。
- **深浅色都做**。报告会被分享、被打印、被在手机上打开。

## 三处踩过的坑

### 1. 截断打在美化前面，JSON 就再也排不了版

`_clip` 先切、`pretty` 后排——切完的片段已经不是合法 JSON，`json.loads` 必失败，渲染只能退回打印一整行几千字符。**在报告里看到才发现**，代码上完全看不出问题。

改成先 `json.dumps(..., indent=2)` 再切，并且切在换行处——半行 JSON 读起来像损坏，不像截断。

### 2. 记录器按 nodeid 归档 = 跨运行串数据

写了一条"不许串"的测试，直接挂了：期望 2 条判定，实到 14 条。

原因：**pytest 的 nodeid 是相对 rootdir 的**，同一个文件跑两次 nodeid 完全一样。记录器把跑完的用例按 nodeid 存进进程级字典，第二次运行 `end()` 时就和上一次的合并了。

这不是测试的怪癖——**MCP server 正是一个长期驻留、反复调 `run_tests` 的进程**。每份报告都会带上前一份的判定，且无上限增长。

改法：`end()` 交出证据并清空，不留归档。归档这个设计本身就是错的。

### 3. 浅色模式下 7% 的红叠在白底上是脏灰

深色面板上 `rgba(255,112,96,.07)` 是恰到好处的一层红，同样的值铺在白色上就是一片脏灰——**恰好是读者会自动忽略的那个色**。浅色模式单独给了实色底。

## 安全面

报告展示的内容大幅变多，而这些内容全部来自被测系统，所以转义面也大幅变大。

- `highlight_json` 是整个报告**唯一**自己拼 HTML 的地方（Jinja 的自动转义对 `Markup` 不生效）。它对每一段——命中的 token 和 token 之间的空隙——都过 `html.escape`。
- 测试按面枚举：失败文本、判定名与证据、请求/响应体、请求/响应头、URL、`copy as curl` 的属性值。少转义一处就在这里挂，而不是在别人的浏览器里。
- `copy as curl` 用 `shlex.quote`，测试用 `shlex.split` 反解回 argv 断言——要保证的性质不是"引号怎么打的"，而是**元字符必须落在某一个参数里面，永远不能变成语法**。
- 证据和其他所有字段一样走构建期脱敏。请求头里那个 `Authorization` 是每次调用都带的，演示套件里故意塞了一个 `Bearer sk-live-…`，报告里是 `***REDACTED***`。

## 怎么产出（这才是重点）

报告一直是 HTML，但此前要拿到它得自己写三步 Python——runner、builder、renderer。**一份没人能一步产出的报告，就是一份没人产出的报告**。

现在是一条命令：

```bash
ipandora run test/api/                       # 跑完即出 HTML + JSON，并归档
ipandora run test/api/ -e staging --title "回归"
ipandora run "test_pay and not slow"         # 非路径按 -k 表达式处理
ipandora run test/api/ -d ./out --no-archive # 直接写到指定目录，不进历史
```

终端只打结论，路径在最后：

```
  FAIL  4 passed, 4 failed, 2 skipped
  通过率 50.0% · 1.99s · run-20260802-162807-107
  判定 14 通过 · 8 失败 · 7 未覆盖
  覆盖 包仓库 · registry × 校验维度 7/12
  2 条什么都没测到，不计入通过率

  报告  ~/.ipandora/reports/run-20260802-162807-107/report.html
  历史  ~/.ipandora/reports/index.html
```

**退出码是运行的结论，不是报告的**——套件挂了就得让调用它的 shell 挂，否则 CI 会在红的时候变绿。

## 每次执行都留档

`~/.ipandora/reports/`（可用 `IPANDORA_REPORTS_DIR` 或 `-d` 改）：

```
index.html            历史页
index.json            每次运行一条记录
run-20260802-.../     该次的 report.html + report.json
```

单份报告只回答"这次怎么样"。人真正带到测试套件面前的问题基本都是比较型的——**刚才是不是我弄坏的、这条是不是一直在飘、通过率在往哪走**——而这些，一份会被下次运行覆盖的文件一个都答不了。

历史页给三样东西：通过率趋势条、每次运行一行（可点进完整报告）、以及**相对上一次新增的失败与已修复的用例，按 nodeid 列出**。最新一次若有回归则自动展开。

这个对比**必须在归档时算**，不能读的时候再算：等更早那次被清理掉，就再也重建不出来了。保留最近 50 次——报告带着请求与响应体，不小。
