# CR10 代码审查（2026-11-06）

范围：D7 跨服务链路（PR #56）。涉及：

- `core/tracing.py`；
- HTTP 层的注入点：发出、重放、失败请求的证据；
- `concurrently()` 共享 trace；
- 报告里的链路链接。

合入后审查，修复单独开 PR。

## 结论

确认 2 条缺陷。测试在 `test/testtracing/test_tracing.py::TestCr10`，修复前都失败。

| # | 问题 | 后果 | 修复 |
|---|---|---|---|
| 1 | 用例写在会话（session）上的 `traceparent` 有时被框架覆盖 | 框架只在请求自己没写 Content-Type 时，才把会话的请求头复制进请求。请求写了 Content-Type，框架就在请求级加上自己的 `traceparent`；发送时请求级优先，用例自己的被换掉，证据里记的也是框架的 | 会话上已有 `traceparent` 时视为用例自己的，不再加 |
| 2 | 报告从 JSON 重建时（`ipandora merge`、`build_from_dict`），`trace_url` 原样进了链接 | 分片文件里写一个 `javascript:` 地址，合并后的报告里就是一个可点击的脚本链接。自动转义拦不住这种地址；只有经过 `tracing.link()` 的地址才检查过 | 模板里的链接一律经 `web_url` 过滤，只保留 http(s) 地址。不合格的 trace id 照常显示，只是不加链接 |

**核实后没有问题**：

- 随机的 32 位十六进制 trace id、`traceparent` 头、URL 里的 trace id 都不会被凭据遮盖规则误伤，报告里显示的就是实际值。
- socket 请求（`SocketRequest`）有自己的 `handle_response`，不经过注入点，不会被塞进 `headers` 参数。
- 每个请求有自己的请求头对象，加上的 `traceparent` 不会留到下一个请求。
- 框架关闭链路时，`concurrently()` 仍会为用例生成 trace id。它只存在证据里，不发出去，也不进报告。

**说明，不改**：

- urllib3 的自动重试（幂等方法，最多 2 次）沿用同一个请求头，所以几次重试是同一个 span。重试发生在连接层，框架看不到每一次。
- 采样标志固定为 1。压测（Locust）里打开链路，每个请求都会被要求采样。手册里已写明，按需在压测环境里关闭。
