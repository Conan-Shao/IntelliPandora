# CR6 代码审查（2026-11-06）

范围：E1 补上的编码 agent 评分器（`core/eval/coding.py`、`ipandora eval code`，PR #48）。合入后审查，修复单独开 PR。

## 结论

确认 2 条缺陷，都会让评分器被它要评的 agent 绕过；另有 3 处加固。每条都有测试（`test/testeval/test_coding.py::TestCr6`），在修复前的代码上全部失败。

| # | 问题 | 后果 | 修复 |
|---|---|---|---|
| 1 | 判定清单（`conf/judgements.json`）从 agent 改过的工作目录里读 | agent 把用例改弱，再顺手重新生成判定清单，`not_weakened` 就没有可比的东西，照样通过。编码 agent 最常见的捷径正是改测试，这条检查本来就是为它设的 | 给了 `base` 时，判定清单按 `base` 那次提交里的样子读（`committed()`，`git show`）；`ipandora eval code --base ... --baseline ...` 同样如此。文件在那次提交里不存在时直接报错 |
| 2 | 运行用例的子进程在工作目录里启动，工作目录又在模块搜索路径上 | 工作目录里放一个 `sitecustomize.py`，解释器启动时就会执行它，抢在我们之前打印一行伪造的结果：不通过的用例被报成通过 | 子进程在一个空的临时目录里启动，忽略 `PYTHON*` 环境变量（`-E`），启动完成后才切到工作目录、加入搜索路径。变异测试的子进程同样处理 |

**加固**：

- **决定用例怎么运行的文件**：conftest.py、sitecustomize.py、`*.pth`、pytest.ini、pyproject.toml、setup.cfg、tox.ini 里的代码运行在报告结果的进程里，conftest 的钩子可以把红的改成绿的，或者让每个变异都"被抓住"。进程隔离挡不住它，所以把它当成改动范围的问题：`harness_untouched()`，给了 `base` 时默认检查，任务确实需要改 conftest 时用 `allow_harness=True` / `--allow-harness-changes`。
- **用例根本没有加载目标文件**：比如导入的是装在环境里的那一份。这时每个变异都"存活"，得分 0%，看起来是用例写得差，其实是环境的问题。现在每个目标文件先做一次探测：换成一导入就失败的文件，用例还通过，就直接说明"用例没有从工作目录加载它"。
- git 没有响应（60 秒超时）时给出说明，而不是一段调用栈。

**核实后不成立**：运行用例会不会在工作目录里留下文件，让随后的 `changes()` 把它们算成 agent 的改动？不会：运行器在 `persist=False` 下不写工作目录，字节码也不写。
