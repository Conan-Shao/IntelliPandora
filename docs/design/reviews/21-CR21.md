# CR21 代码审查（2026-11-07）

范围：D4c——tc netem 故障后端（`core/netem.py`，#96）。合入后审查，修复单独开 PR。

## 结论

确认 1 条缺陷。回归测试修复前失败（`test/testfaults/test_netem.py::TestCr21::test_a_run_killed_while_the_helper_runs_leaves_a_marker`）。

| # | 问题 | 后果 | 修复 |
|---|---|---|---|
| 1 | 标记文件在 tc 设好之后才写。设 tc 要起一个辅助容器，通常要一秒左右 | 这一秒里运行被杀掉（单条用例超时、CI 作业被取消、Ctrl-C），容器上留下一个 netem qdisc，却没有标记：之后的清理找不到它，故障一直生效到容器重启，后面的运行都在延迟或丢包下跑，还不知道为什么 | 先写标记（记下"打算加上的"），再设 tc；设失败时恢复原来的 qdisc，也把标记改回原来的内容（没有了就删掉）。清理时删一个其实没加上的 qdisc 不算错 |

**核实后没有问题**：
- 同一个容器上的几个故障合成一个 netem，撤销一个按剩下的重建，最后一个撤销时删除；加不上时恢复到之前生效的那些。
- 撤销时容器已经不在、或者 qdisc 已经没了，不报错；清理同样。
- 运行结束时主进程清理：并行运行时故障是 worker 进程加的，那时 worker 已经退出，按"已经不在的进程"清掉。
- 证据、标记、锁、开关都由 `faults.injected()` 负责，和其他后端一致。

**记下、不改的**：
- 同一个容器用名字和用 ID 写成两个目标时，锁和标记也是两份，两条用例可能同时往它上面加。用例里统一用名字即可（compose 的服务名是固定的）；要根治得在注入前把名字解析成 ID，多一次 `docker inspect`。
- 目标容器上如果已经有用户自己设的根 qdisc（比如 tbf 限速），注入会替换它，撤销后它不会回来。测试环境里一般没有；手册里写明 netem 接管根 qdisc。
- 第一次注入时如果本机还没有辅助镜像，`docker run` 会先拉取，这段时间算在用例里。CI 作业里先 `docker pull`；手册建议同样做。
