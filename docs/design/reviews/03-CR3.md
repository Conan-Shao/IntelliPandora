# CR3 代码审查（2026-11-06）

范围：A2（并行下的登录共享与账号池）、L2（`cases()` 数据驱动）、L3（`ipandora check layout`）。依据：[决策 14](../decisions/14-技术方案与实施计划.md) 的审查节点。L3 的 PR 合入前审查，问题和修复放在同一个 PR 里。

## 结论

共 20 条。以下按后果分组，都已修复，每条有测试。

## 会让结论出错

| # | 问题 | 修复 |
|---|---|---|
| 1 | 账号池的租约用 `account:<账号>` 作锁名，和用例的 `@pytest.mark.resource('account:vip')` 是同一把锁。租约占到运行结束，标了这个资源的用例全部等到超时，连租到这个账号的 worker 自己也拿不到 | 租约换用独立的前缀 `ipandora-account-lease:` |
| 2 | 共享登录上调用 `auth.forget()` 没有效果：缓存标为过期后，下一次从共享文件读回的还是同一个版本、同一个未过期的凭据，没有重新登录 | `forget()` 记下作废的版本号，读共享文件时跳过这个版本 |
| 3 | `auth.store()`（以及基于它的 `web.share_with_api`）只写本进程缓存，单会话账号的其他 worker 继续用旧登录，而旧登录已经被新登录顶掉 | 共享时在文件锁内写共享文件，版本号沿用文件里的 |
| 4 | 共享目录只由 `ipandora run` 创建，直接 `pytest -n 4 -p ipandora.core.runner.plugin` 时没有目录，`single_session` 悄悄失效，worker 互相踢下线 | 目录由插件在主进程创建（xdist 的 worker 继承环境变量），运行结束由插件删除 |
| 5 | 一个身份同时在账号池里又声明了 `single_session`（`single_session = True` 时就是这样），所有 worker 读到第一个 worker 用它租到的账号登录的凭据，账号池形同虚设 | 池里的身份不共享 |
| 6 | 用例的 `dims` 只取最近的一个标记：函数上有 `@pytest.mark.dims(channel='api')` 时，`cases()` 每一行自己的 `dims` 全部丢失，覆盖矩阵看不到它们 | 模块、类、函数、参数行的 `dims` 依次合并，越具体的越优先 |
| 7 | `Case` 的字段和 dict 的方法同名时读到的是方法：CSV 里叫 `items`、`values`、`get` 的列，`case.items` 是一个绑定方法，拿去比较永远不相等 | 字段优先于同名的 dict 方法 |
| 8 | `_find` 一路向上找到文件系统根，找不到还会按当前目录再找一次：项目外的 `~/data/users.yaml` 会悄悄成为用例的输入 | 只找到项目根（有 `pytest.ini`、`pyproject.toml`、`setup.cfg`、`tox.ini` 或 `.git` 的目录）为止 |
| 9 | CSV 某行字段比表头多（值里有没加引号的逗号），多出来的字段被 `csv.DictReader` 放在键 `None` 下，随后排序字段名时崩溃，或者整行被错位读入 | 指出哪一行字段多了 |
| 10 | `dims: {role: null}` 写成了字符串 `'None'`，覆盖矩阵里多出一个叫 None 的角色 | 空值的维度不写 |

## 并行与串行不一致

| # | 问题 | 修复 |
|---|---|---|
| 11 | 账号比 worker 少时，没租到账号的 worker 等别人归还；但租约要到运行结束才释放，只能等满超时（默认 300 秒）后失败 | 启动时发现账号不够立即报错，说明要加账号或减少 worker |
| 12 | 串行运行也把凭据写进共享文件，没有必要地把凭据落盘 | 只在 xdist 的 worker 里共享，串行运行凭据留在内存 |
| 13 | 租约和共享登录的等待上限读自己的环境变量和默认值，与 `@pytest.mark.resource` 的设置不一致 | 共用插件的 `RESOURCE_TIMEOUT_VAR` 与默认值 |

## 崩溃与误导

| # | 问题 | 修复 |
|---|---|---|
| 14 | `single_session = 'admin'` 被当作字母集合：`'ad'`、`'min'` 也算单会话，`'admin'` 反而按包含关系判断 | 字符串表示一个身份名 |
| 15 | 分层检查只认 `time.sleep`、`sleep`、`page.wait_for_timeout` 这几种写法：`import time as t; t.sleep(1)`、`asyncio.sleep`、页面类里的 `self.page.wait_for_timeout` 都漏掉 | 按最后一段名字匹配 `sleep`、`wait_for_timeout` |
| 16 | `expect` 按最后一段名字匹配，pexpect 的 `child.expect(...)` 被当成判定 | 只认裸调用的 `expect(...)`（Playwright 的用法） |
| 17 | `tests/conftest.py` 里 import `requests` 被报出来，而登录提供者通常就写在那里 | `tests/` 下的 `conftest.py` 不检查这一条 |
| 18 | 项目自己的相对导入 `from .requests import x` 被当成 import 了第三方的 `requests` | 相对导入不算 |
| 19 | `pages/` 里 sleep 的提示是"用 `eventually()`"，而 `eventually()` 是给用例用的；页面类该用 Playwright 的等待 | 提示按层给出：用例用 `eventually()`，页面用 `locator.wait_for()` 或 `page.wait_for_url()` |
| 20 | `cases()` 用 `inspect.stack()` 找调用者，它会读取栈上每一帧的源码，收集阶段每调用一次就读一遍 | 改为只取调用者的那一帧 |

测试：`test/testauth/test_parallel_auth.py`（`TestCr3`，以及 `TestSingleSession` 里串行运行与私有目录两条）、`test/testcases/test_cases.py`（`TestCr3` 与 dims 合并）、`test/testlayout/test_layout.py`（`test_cr3_rule_edges`）。第 4、5 条的测试在修复前的代码上失败。
