# CR11 代码审查（2026-11-06）

范围：D5 依赖环境编排（`core/stack.py`、运行器里留存服务日志的钩子、归因规则、报告的服务日志、测试镜像的登记）。合入后审查，修复单独开 PR。

## 结论

确认 2 条缺陷，另有 1 处加固。每条都有测试（`test/teststack/test_stack.py::TestCr11`，修复前全部失败；第 1 条用真实 Docker 复现）。

| # | 问题 | 后果 | 修复 |
|---|---|---|---|
| 1 | compose 项目名只取文件名（`compose.yaml` → `compose`）。同一个进程里，不同目录下同名的两个文件是同一个项目 | `shop/compose.yaml` 和 `payment/compose.yaml` 都用会话级 fixture 起：第二个 `up` 加入了第一个项目，先关掉的那个把两套服务一起删了，另一套用例连不上服务，被归为"环境" | 项目名加上文件绝对路径的哈希；同一组文件同时起两套时再加序号 |
| 2 | 用例失败时留存服务日志，这段代码在 `pytest_runtest_makereport` 里运行，只捕获了 `StackError` 和 `OSError` | 其他异常（比如 docker 输出了意料之外的内容）在钩子里抛出，pytest 报 INTERNALERROR，整个会话结束，后面的用例都没跑 | 钩子里捕获所有异常，只记一条警告：证据缺了不能影响运行 |

**加固**：取日志时只取时间窗内的最后 80 行（`logs --since … --tail 80`），不再先把整段日志读进内存再截取。日志多的服务在长用例里可能有几十 MB。

**核实后没有问题**：
- 起环境失败时，`StackError` 的消息（含服务日志）先去凭据再抛出；测试里故意打印的 `password=…` 不出现在消息里。
- 清理只删本机、进程已不在的项目；并行的 worker 互相看得见对方的项目，但对方进程还在，不会删。
- `up` 中途被 Ctrl-C（`KeyboardInterrupt`）打断时，`__enter__` 里的 `except BaseException` 照样 `down`。
- 报告从 JSON 重建时，服务日志的文本再过一遍去凭据；它只作为文本渲染（自动转义），不生成链接。
