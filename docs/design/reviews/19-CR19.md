# CR19 代码审查（2026-11-07）

范围：M5 Android 全部三块——M5a `core/android.py`（#89）、M5b 模拟器验收（#90）、M5c Appium 准入与实测对比（#91，含 npm 准入门禁）。合入后审查，修复单独开 PR。

M5c 的 CI 首跑已经顺带暴露并修掉了两个问题（#91 内）：logcat 证据只留最后 300 行，`am crash` 之后重启的 App 把 FATAL EXCEPTION 挤了出去；对比脚本计时没计到 uiautomator2 的查找（`exists` 是惰性的）。下面是在那之后审查出来的。

## 结论

确认 4 条缺陷。每条的回归测试在修复前失败。

| # | 问题 | 后果 | 修复 |
|---|---|---|---|
| 1 | 用例的日志窗口从 `date +%s` 开始，精确到秒，写成 `N.000`。窗口最多早开一秒 | 上一条用例在同一秒里把 App 弄崩，这条用例 `logcat -T` 读到那次崩溃：一条无辜的用例被判**产品缺陷、高置信**——归因里最不该出的那种错 | `date +%s.%N` 取到毫秒（截断不进位：早开几微秒碰不到上一条用例，晚开可能漏掉启动即崩溃）；`date` 不支持 `%N` 的老设备退回整秒。模拟器验收里核对真实设备确实给出纳秒 |
| 2 | `assert android(text='欢迎').exists` 失败时没有任何控件诊断，走"普通 assert 不成立"那条规则 | 用户手册自己示范的写法，选择器写错时被判为**产品缺陷**（中置信；记成判定时是高置信），而同样的错用 `click()` 写就会判成选择器的问题 | 用例期间找不到控件的查找（`exists` 为假、`wait()` 为假）记下来，不算失败——可能只是在找一个可选的弹窗；用例因 assert 失败时，assert 的文字里带引号出现了哪次查找的名字（pytest 会展开成 `<Device>(text='欢迎')`），就拿失败那一刻的控件树诊断那次查找，和 `click()` 失败一样判。名字不在 assert 里的查找不算（测试里有，模拟器验收里也有） |
| 3 | `update_locks.py` 的 npm 安全截止时间用字符串比较取较晚者 | `--cutoff 2026-10-29T06:00:00+08:00`（UTC 的 28 日 22 点）按字符排在 `2026-10-29T00:00:00Z` 后面，被当成更晚的截止时间，安全修复反而被冷静期挡回去 | 解析成时刻再比较 |
| 4 | `NPM_LICENSE_OVERRIDES`（锁文件里没写许可证、人工核对过的包）按包名登记，不分版本 | 这些包以后的版本换了许可证，仍按旧版本的人工核对放行 | 按 `名字@版本` 登记，升级后要重新核对 |

**核实后没有问题**：
- 并行时每台设备一把锁，锁在用例期间持有、拆卸时先停 App 再释放；锁拿不到时的失败信息被归为环境问题，不会误判。
- `app_events` 只认被测包（含 `包名:子进程`）的崩溃，别的 App 崩溃不算；包名没配时什么都不认。
- 证据各项单独取，截图失败不影响日志；凭据在写入证据前脱敏。
- npm 锁文件门禁：可选依赖（sharp 的 LGPL libvips）不装也不检查；打包在驱动里的包随驱动的 sha512 核对；`npm ci --ignore-scripts` 不执行任何安装脚本。每日扫描对 npm 锁文件的 `npm audit` 与 pip-audit 共用例外表，过期一样拦。
- 对比脚本每个结果都核对；两边轮流、每块开始前停掉对方的设备端服务。截图一项两边交回的东西不同（uiautomator2 解码成图像，Appium 是 PNG 字节），已在脚本和决策 14 里写明。

**记下、不改的**：
- `relevant()` 按子串认包名，`com.example.shop` 也会带上 `com.example.shopping` 的行。只是证据多几行，不影响判定（判定用 `app_events`，按包名精确匹配）。
- 对 XPath 的 `exists` 没有做第 2 条的处理，只覆盖了 `d(...)` 选择器；XPath 的 `get()` 失败照旧诊断。
