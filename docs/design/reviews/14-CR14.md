# CR14 代码审查（2026-11-07）

范围：E8 测试生成任务的 F→P 判分器和 task.yaml 加载器（`core/eval/testgen.py`），E9 的判分器自检、运行记录、失败归因（`testgen.selfcheck`、`core/eval/records.py`、`Trial.ended`）。判分器是使用方数据集结论的根基：判错一条，整份评测报告就错。合入后审查，修复单独开 PR。

## 结论

确认 4 条缺陷。每条都先复现、再修，回归测试在修复前全部失败（`test/testeval/test_testgen.py::TestCr14`）。

| # | 问题 | 后果 | 修复 |
|---|---|---|---|
| 1 | 修复前失败的异常是 `NameError`、`ImportError` 一类时，一律算弱复现，不看异常是谁抛的 | bug 本身就是源码里拼错的名字（`return a + offest`）时，agent 写对了测试也判不过 F→P。使用方的规则写的是"被测代码自己抛出的异常算有效复现" | 记录里本来就有异常发生的位置：从工作区里测试文件以外的文件抛出的，算有效复现；测试自己抛的、收集失败、找不到 fixture，仍是弱复现 |
| 2 | 找"修复前已有哪些测试"时，先把测试文件恢复成基线再收集；agent 删掉的测试文件随之恢复回来，之后没有再删 | 工作区和 agent 留下的样子不一样，判分之后多出一个 agent 删掉的文件 | 收集完，把 agent 删掉的文件重新删掉 |
| 3 | 结果写在环境变量指定的文件里；agent 的 conftest 或测试代码和 pytest 在同一个进程里，能读到这个路径，也能改记录 | 一个只写了 `assert True` 的测试，加十几行 conftest 在会话结束时把记录改成"修复前失败、修复后通过"，就判成了 F→P | 三层：插件一加载就从环境里取走路径；记录要和 pytest 自己的退出状态、进程的退出码对得上，对不上就判"结果被改动"；agent 的测试文件里定义了 pytest 钩子（`pytest_*` 函数或 `hookimpl`）就不判分，记为 `tampering` |
| 4 | 断言检查只看测试函数自己的源码 | 断言写在同一个文件的辅助函数里（`check(value)` 里 `assert`）时，被报成零断言 | 顺着调用同一文件里的函数找（可以多层） |

**第 3 条的边界**：测试代码和判分在同一个 Python 进程里，进程内的代码原则上什么都能改，这三层是提高门槛，不是隔离。已写进 `docs/guide/eval.md`：要的是不可伪造的结论，就让判分容器只跑判分，并在报告里抽查轨迹。

**核实后没有问题**：
- 越界改动只恢复测试以外的文件；agent 改的源码不参与判定，越界只记一次。
- 修复后连跑 3 次，任何一次不过即为 flaky，不算 F→P。
- 变异只在 fix.patch 改到的函数里做，先用"导入即失败"的探针确认测试确实从工作区加载被测文件。
- `selfcheck` 每一项前后都把工作区恢复到基线，忽略文件（editable 安装的元数据）不删。
- `records` 里 `over_budget` 只是标记，不改变结论。
