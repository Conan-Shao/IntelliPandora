# CR4 代码审查（2026-11-06）

范围：E1（Inspect 路径：`inspect_log`、`inspect_scorer`、`ipandora eval inspect`，以及 `inspect_ai` 的组件准入）。依据：[决策 14](../decisions/14-技术方案与实施计划.md) 的审查节点。E1 的 PR 合入前审查，问题和修复放在同一个 PR 里。

## 结论

确认 3 条缺陷，都已修复并有测试；另有 1 处加固、1 处怀疑但核实后不成立。

| # | 问题 | 后果 | 修复 |
|---|---|---|---|
| 1 | 版本清单里的沙箱写的是 `str(spec)`，其中有 compose 文件的绝对路径 | 同一个沙箱在笔记本和 CI 上被当成不同的资源，和别处写的基线比较时一律"不可比"，门禁形同虚设 | 只记类型和配置文件名：`docker:compose.yaml` |
| 2 | 被取消、出错中断、还在运行的 Inspect 日志照常读入 | 没跑的样本不在配对比较里，不算失败：跑了一半的运行可能被判为"和基线无法区分"而通过门禁，还能被写成基线 | `inspect_log.incomplete()` 列出未完成的任务；`ipandora eval inspect` 照常出报告，但退出码为 1，并拒绝用它写基线 |
| 3 | `inspect_scorer` 把样本 metadata 里的 `budget` 读进任务，却没有任何地方判它 | 看起来有预算约束，实际没有 | 不再读入；Inspect 路径的预算就是 Inspect 自己的上限，读日志时判定（手册写明） |

**加固**：数据集哈希改为与样本顺序无关（排序后再算）。核实时 Inspect 自己会按样本排序，没能复现顺序不同导致哈希不同，但哈希不应依赖这一点。

**核实后不成立**：任务级的上限（`Task(time_limit=...)`）也进了日志的 `eval.config`，版本清单里有，比较时会发现上限变了。

测试：`test/testeval/test_inspect.py` 的 `TestCr4`。第 1、2 条的测试在修复前的代码上失败（第 1 条比较的是两台机器上的同一个沙箱）。
