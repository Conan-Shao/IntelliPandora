# 16 · 测试报告改版

> 2026-11-05 · 设计稿经确认后实现。用法见 [`docs/guide/reports.md`](../../guide/reports.md)。

## 1. 要解决的问题

改版前的报告，在一份 10 条用例的样例套件上：

| 现象 | 问题 |
|---|---|
| 右上角大字 `5/10 FAIL` | 命令行说 `6 passed`。pytest 把那条什么都没判定的用例也记作 passed；报告不算它。读者不知道该信哪个数 |
| `覆盖 0/0` | 套件声明了 `COVERAGE = [{'role': [...], 'channel': [...]}]`，但报告只认带 `x` / `y` 的完整写法，别的写法静默画成空矩阵。"0/0" 读起来像"没什么要覆盖的"，和作者的意思正相反 |
| 没有一句结论 | 要读完所有区块才能判断"这次能不能放行" |
| 归因只给计数 | `1 data, 3 defect`，看不到每条的依据和下一步 |
| 归因依据是英文 | 其余界面是中文 |

## 2. 首屏回答一个问题：这次通过能不能信

从上到下：结论 → 指标卡 → 这次新红的 → 按归因分组的需要看的用例 → 判定变化 → 覆盖与判定构成 → 用例明细 → 缺口汇总。

**结论分四种**，由固定模板根据计数拼出，不经过 LLM，和退出码同源：

| 结论 | 条件 | 退出码 |
|---|---|---|
| 可以放行 | 全部通过，没有需要复核的 | 0 |
| 通过，但需要复核 | 没有失败，但判定变弱且没开门禁、有未判定的用例、或没有一条给出结论 | 0 |
| 不能放行 | 有失败；或 `--fail-on-weakened` 且判定变弱 | 1 |
| 没有跑起来 | 收集失败或没有用例 | 1 |

"通过，但需要复核"这一档是这个框架和 pytest 的区别所在：退出码是 0，但报告不说"可以放行"。

**通过率写明分子分母**（`62.5% = 5 / 8`），并说明跳过与未判定不进分母。

## 3. 框架不是平台：和什么比

设计稿第一版有"和上一次比""最近 8 次趋势""连续失败 N 次"。评审意见：框架不是平台，不应该有运行记录。改为：

1. **对比基线**，始终有（只要有基线文件）。基线随代码提交，本机和 CI 得到同样的答案。基线只记录通过和跳过的用例，所以"基线里通过、这次失败"就是新红的，不需要任何历史。
2. **对比一次运行**，可选：`--compare-with` 传入的 report.json 优先；没传时，找本机报告存档里同一选择器、同一环境的上一次运行，并标明"本机缓存"；都没有就不显示。
3. **不画趋势，不统计连续失败次数。** 这是平台或 CI 的事，它们可以读 report.json 和 JUnit XML。

本机报告存档（`~/.ipandora/reports`，最多 50 次）在改版前就有，这次没有删：它是"本机缓存"的来源。报告本身不依赖它。

## 4. 一份报告能不能覆盖所有类型

HTTP、Web、App、图像比对的数据是同一个结构：用例 → 判定（带来源）→ 证据。骨架统一，只有证据块不同（请求与响应、截图与 trace 与定位器判断、金样与差异图）。M5 的 App 只需要加一个证据块。

agent 评测结构不同（见 `13` §5、§6）：单位是"任务 × k 次试验"，结论是"变好 / 变差 / 无法区分"，判定里有要分开展示的模型评委，证据是轨迹。设计稿第 6 张画了评测视图，用来验证骨架：

| 骨架位置 | 功能测试 | 评测 |
|---|---|---|
| 结论 | 能否放行 | 比基线变好、变差，或无法区分 |
| 指标卡 | 结果、判定强度、未判定、缺口、覆盖 | 成功率及区间、pass^k、部分分、判定来源、成本 |
| 对比基线 | `judgements.json` | 逐题成绩基线 |
| 按归因分组 | 产品缺陷、测试数据…… | agent、基础设施、任务、评分器、待人工阅读 |
| 证据 | HTTP、截图、差异图 | 轨迹时间线、终态、逐条判定 |

结论：骨架撑得住，需要三处数据模型上的准备——对比单位要能是任务、`verdict` 要允许多于两种结论、判定要能按"确定性 / 模型评委"分开。这次实现了 `view` 字段（目前只有 `tests`）和可扩展的 `verdict.status`；评测视图在 E0 时接数据。

## 5. 实现

| 位置 | 内容 |
|---|---|
| `core/report/model.py` | `verdict`、`pass_rate_basis`、`attention`（按归因分组）、`view`；`coverage_axes()` 接受简写，无法识别时给出原因 |
| `core/runner/inventory.py` | `against()`：按基线拆分这次的失败 |
| `core/report/compare.py` | 对比传入的报告或本机存档；索引里的路径不得指向存档之外 |
| `core/triage/` | 归因依据和下一步改为中文；类别仍是英文代码，另有中文显示名 |
| `conf/static/report.html` | 重写：浅色与深色、手机宽度可用、单文件离线 |
| `ipandora run` | `--compare-with`；命令行摘要首行即结论 |
| MCP | `run_tests` 返回 `newly_failing`；`build_report` 接受 `compare_with`，返回 `verdict` |

report.json 只新增字段：`view`、`verdict`、`pass_rate_basis`、`against_baseline`、`against_run`。已有字段含义不变。

## 6. 顺带发现的问题

本地用 pytest 9.2 跑测试时发现：没装 pytest-xdist（`parallel` 是可选组）时，**每次运行都会失败**，报 `unknown hook 'pytest_testnodedown'`。原因是收集器用 `hasattr(config.hook, ...)` 判断 xdist 是否加载，pytest 9.2 对任何名字都返回真。CI 没发现，因为锁文件装了 xdist，且固定在 pytest 9.1.1。改为 pluggy 文档里的做法：`@pytest.hookimpl(optionalhook=True)`，始终注册。`test/testrunner/test_without_xdist.py` 覆盖它。
