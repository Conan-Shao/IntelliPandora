# Part 0 · 核心判断

One dev 时代,产出成本趋零,**验证成本不变**。瓶颈从"写"移到"信任"。

单人全栈最大的结构性风险是没有第二双眼睛。质量保障的定位因此变成:提供一套独立的、机器可判定的验证系统,而不是人肉复核。

## 三条推论

**① 能被规则解决的,别请模型。**
L0 契约层(schema、边界、错误码)用 OpenAPI 驱动的确定性工具生成,质量高于 LLM 且不会幻觉。AI 的位置在规则表达不了的地方。

**② 用例是消耗品,fixture 和 invariant 是资产。**
生成成本归零后,测试脚本不再值得维护;接口变了就重新生成。真正进代码审查的是 fixture 和 invariant。

**③ 框架的用户变成了 agent。**
产品形态从「框架 + CLI」变成「框架 + MCP 能力面」。这是唯一一个真正的架构决策,其余都是它的推论。

## 分层模型

```
L0  契约层     spec 驱动,工具生成,零数据,每次 PR 全量跑
L1  单接口语义  边界 / 错误码 / 权限矩阵,半生成,人审断言
L2  业务链路    多步有状态,手工设计,数量控制在两位数
L3  不变量      属性 / 蜕变测试,守恒律,AI 起草人审
```

L0 靠 spec,L3 靠 AI + 人,L1 是两者结合,L2 靠人的判断力。
**时间应该几乎全花在 L2 和 L3。**

# Part 1 · 架构

## 1.1 职责边界

| 层 | 写什么 | 谁维护 | 变更频率 |
|---|---|---|---|
| 框架内核 | 协议驱动、fixture 生命周期、invariant 基类、runner、report、triage | 你,不含业务 | 稳定 |
| 业务包 | client(生成)、flow、fixture、invariant | 每条产品线自己 | 中 |
| 用例 | 编排 + 断言组合 | AI 生成 | 高,消耗品 |
| MCP | 参数解析 → 调 core → 裁剪结果 | 你,~150 行 | 稳定 |

> **检验标准:把 `mcp/` 整个删掉,`pytest biz/wallet/cases` 应该毫发无伤。**
> 如果删了就残废,说明业务能力写错地方了。

## 1.2 目录结构

```
intellipandora/              ← pip 包,通用内核
  core/protocol/             HttpClient 基类:重试、超时、脱敏、录制
  core/fixture/              @fixture、账号池、teardown 栈、并发隔离
  core/invariant/            Check 对象、assert_all 收集器、通用不变量
  core/runner/api.py         run(selector, env) -> RunResult(可被库调用)
  core/report/               HTML 渲染
  core/triage/               失败分类规则
  mcp/server.py              四个 tool

biz/wallet/                  ← 业务包
  openapi.yaml               唯一真相源
  client.py                  生成物,含 URL 和 pydantic 模型
  flows.py                   SendFlow —— 多接口编排
  fixtures.py                账号池、gasless_wallet
  invariants.py              领域不变量
  cases/test_send.py         用例

conf/{dev,prod}.yaml         ← 环境(base_url、账号池配置)
```

## 1.3 各类信息的归属

| | 在哪 | 谁写 | 变更频率 |
|---|---|---|---|
| URL / 接口定义 | `biz/<域>/client.py` | 从 OpenAPI 生成 | 接口变才变 |
| 环境配置 | `conf/<env>.yaml` + 环境变量 | 人,一次性 | 极少 |
| 业务数据 | 用例参数 + fixture | AI / fixture 构造 | 每个用例 |
| 密钥 | KMS / 环境变量,**永不进 git** | 运维 | — |

**不要 yaml 数据文件。** 那是关键字驱动时代的产物,AI 生成用例时反而是障碍——它得同时改代码和数据文件,还得保持对应。

## 1.4 密钥处理

把签名做成接口,让框架永远拿不到密钥材料:

```python
class Signer(Protocol):
    def sign(self, digest: bytes) -> bytes: ...

class LocalSigner(Signer):    # fork 环境,anvil 公开助记词
class KmsSigner(Signer):      # 生产,只发 digest,收签名
```

```python
@fixture
def signer(env):
    if env == "fork":  return LocalSigner(ANVIL_KEYS[0])
    if env == "prod":  return KmsSigner(os.environ["KMS_KEY_ID"])
```

私钥不进 git、不进 fixture 代码、不进配置文件、不进报告、不进日志。加 pre-commit hook 扫 `0x[a-fA-F0-9]{64}`。

# Part 2 · 三个核心构件

## 2.1 Fixture —— 前置状态的构造与还原

本质不是"新建",是**保证起点确定**。

生产环境用**专用账号池 + 幂等归位**:

```python
@fixture
def gasless_wallet(pool):
    w = pool.acquire(tag="no-native")      # 加锁独占,解并发
    ensure_balance(w, USDT, min="10")      # 幂等收敛,不够才补
    assert_balance(w, BNB, 0)              # gasless 场景必须无原生币
    yield w
    reclaim(w)                             # 转回来,余额守恒
    pool.release(w)
```

### 账号池规划

数量取决于**并行度**,不是用例数。5~10 个起步。按前置条件打 tag:

```
acc-01..03   有 USDT 有 BNB      # 原生币支付路径
acc-04..06   有 USDT 无 BNB      # gasless 路径,不能有 BNB
acc-07       低余额               # 余额不足的负向用例
acc-08..09   收款方               # 专门收钱,负责转回来
```

### 五条实操要点

1. **收款方也用自己的号** — 钱能转回来,账号从消耗品变成可循环资产
2. **借出必须加锁** — 否则并行跑 nonce 直接撞。文件锁 / Redis 都行
3. **前置不满足要 SKIP 不能 FAIL** — 否则分不清"代码坏了"和"号没钱了",这是自动化跑久了最大的噪音源
4. **teardown 比 setup 更重要** — 固定账号的致命问题是状态漂移,跑三十次环境就烂了
5. **加余额告警** — CI 跑完检查一次,推到 Telegram

### fork 环境的定位

不是替代账号池,是补充。用于真账号造不出的破坏性场景:余额刚好不够、gas 暴涨、合约 revert、并发竞态。

## 2.2 Flow —— 多接口编排

> **只负责"调了什么、拿到什么",不负责"这样对不对"。**

```python
flow = SendFlow(client, wallet, pay_with="PAY_USDT")   # 场景在构造时定
flow.parse(to=R, amount="0.5") \
    .pick_gas() \
    .build().sign().send().wait_receipt()
```

### 设计要点

**链式返回 self** — 读起来是一句话。

**上下文自动流转** — `tokenPayContextId`、`digest`、`txHash` 全走 `self.ctx`,不从外面传。`build()` / `send()` 无参是设计正确的信号。

**额外责任:抓快照** — 余额前后、原始 options 列表。只有 flow 在正确时机能抓到,这是余额类断言写得出来的前提。

```python
def parse(self, to, amount, asset="USDT"):
    r = self.c.parse_transaction(...)
    self.ctx.parse = r
    self.ctx.balance_before = self._snapshot_balances(to)   # 关键
    return self
```

**pay_with 是场景维度,不是方法参数** — 它决定策略(单笔 / bundle)、决定账号组、决定断言集,构造时就定下来。

**不做 fallback** — 选不到 `FUNDING_ACCOUNT` 就是 None,这本身是测试结果;悄悄退回第一个选项等于把 bug 藏了。

```python
def pick_gas(self, pay_with=None):
    pay_with = pay_with or self.pay_with
    opts = self.c.gas_account_list(self.w.chain, pay_with).options
    self.ctx.gas_options = opts                       # 原始列表留着,可断言
    self.ctx.gas = first(o for o in opts if o.type == pay_with)   # 可能是 None
    return self
```

**路径分支用策略模式** — 不在 flow 里 if/else:

```python
class NativeStrategy:  def build(self, c, ctx): return c.build_transaction(...)
class BundleStrategy:  def build(self, c, ctx): return c.bundle_build(...)
STRATEGIES = {"NATIVE": NativeStrategy(), "PAY_USDT": BundleStrategy()}
```

**负向场景走显式 override 口** — 保持正常路径签名干净:

```python
def build(self, override: dict = None):
    req = self._build_req()
    if override: req = req.model_copy(update=override)
```

### 参数分类

| 类别 | 例子 | 谁给 |
|---|---|---|
| 依赖 | client、wallet、signer | fixture |
| 意图 | to、amount、asset | 用例常量 |
| 选择 | pay_with、strategy | parametrize |

判断标准:**换环境会变的进 fixture,换用例会变的进方法参数。**
`chainId`、`from`、`base_url`、私钥一个都不该出现在方法签名里。

`amount` 用 `str` 不用 `float`,这条别妥协。

## 2.3 Invariant —— 什么叫对

返回 `Check` 对象而非 raise,这样一次跑完所有断言。

```python
@dataclass
class Check:
    name: str      # 中文,给人看
    ok: bool
    expr: str      # 失败时的证据,不用翻日志
    src: str       # onchain / api / schema / derived / authz
```

### 通用层(内核,所有域复用)

```python
value_conserved(flow, sender_delta, recipient_delta)
schema_conforms(resp, "AssetListResp@v3")
pagination_complete(pages, total)
idempotent(fn, times=3)
authz_denied(fn, as_user="other")
monotonic(timestamps)
```

### 领域层(business,别人没有)

```python
def bundle_order_correct(flow):
    types = [i.type for i in flow.ctx.signing_inputs]
    return Check("先付费后转账",
        ok=types.index("TOKENPAYTX") < types.index("USERTX"),
        expr=f"order = {types}", src="derived")

def fee_within_cap(flow, cap):
    fee = D(flow.ctx.gas.tokenPay)
    return Check("手续费在上限内", ok=fee <= D(cap),
        expr=f"{fee} ≤ cap {cap}", src="derived")
```

### 断言集跟着场景走

```python
CHECKS = {
  "NATIVE":          [single_tx_only, native_balance_sufficient],
  "PAY_USDT":        [bundle_order_correct, nonce_contiguous, fee_within_cap],
  "FUNDING_ACCOUNT": [funding_account_debited, no_onchain_fee],
}
assert_all(*COMMON_CHECKS, *CHECKS[pay_with])
```

> **这层是 QA 真正的产出**——不可外包、不可生成、不会过时。只增不减,越积越值钱。

# Part 3 · 用例与 AI 分工

## 3.1 用例形态

```python
@pytest.mark.parametrize("chain,pay_with", [
    (56,"NATIVE"), (56,"PAY_USDT"), (56,"FUNDING_ACCOUNT"),
    (1,"NATIVE"),  (1,"PAY_USDT"),
])
def test_send(chain, pay_with, wallet_pool, recipient, client):
    flow = SendFlow(client, wallet_pool.for_scenario(pay_with), pay_with)
    flow.parse(to=recipient, amount="0.5").pick_gas()
    require(gas_option_available(flow, pay_with))     # 不满足 → 后续 BLOCKED
    flow.build().sign().send().wait_receipt()

    assert_all(*COMMON_CHECKS, *CHECKS[pay_with])
```

三样**不该**出现在用例里:HTTP 细节、新写的断言、数据准备。

用例里只有**组装**,没有**发明**。

## 3.2 AI 分工表

| | 谁做 | 性质 | 成本 |
|---|---|---|---|
| client | 工具生成(datamodel-code-generator)+ AI 补语义 | 确定性 | 一次性,半天 |
| flow | AI 起草,你审 | 机械劳动 | 低频,半天一版 |
| **invariant** | **你写,AI 起草候选** | **领域知识** | **持续,增量** |
| 用例 | AI 生成 | 消耗品 | 每次重新生成 |
| fixture | 你写 | 一次性工程 | 几天,难在回滚 |

### 为什么 invariant 必须人写

AI 能写 `assert receipt.status == 1`,但写不出「代付手续费不能超过 0.15 USDT」——这个 `0.15` 不在任何 spec 里,在风控规则里、在上次线上事故的复盘里。

同理写不出「TOKENPAYTX 必须排在 USERTX 前」,因为它不知道顺序错了会导致什么。

**但成本比想象的低:**
- 通用的那批放内核,一次写完所有域复用
- 领域的那批,起步只要 5 条(bundle 顺序、nonce 连续、手续费上限、余额守恒、订单终态),一下午
- 之后是增量:每次事故补一条,每次读需求补一条,一年三十条

**最省的起点:把已有测试脚本里的 assert 抽出来,合并同类项,就是第一版 invariant 库。** 这些判断你脑子里早就有了,只是散在各处没沉淀成函数。

## 3.3 词汇表原则

「词汇表」= AI 写用例时可调用的、已存在的符号集合。

```python
# flows.py 提供的"动词"
SendFlow(...).parse() .pick_gas() .build() .sign() .send() .wait_receipt()

# invariants.py 提供的"判断词"
value_conserved / bundle_order_correct / nonce_contiguous / fee_within_cap

# fixtures.py 提供的"名词"
gasless_wallet / native_wallet / recipient / wallet_pool
```

**词汇表大** → AI 在造句,产出接近你自己写的
**词汇表空** → AI 在造词,每个用例重新发明 HTTP 调用和断言

### 喂给 AI 的上下文顺序

1. `invariants.py` 全文 — 有哪些判定可用
2. `flows.py` 的方法签名 — 怎么走
3. 一到两个已有用例作为范式
4. 需求描述

> **不要给 `openapi.yaml`。** 给了它就会绕过 flow 直接拼请求,反而退化。限制反而提升质量。

### 词汇表完备性自检

写完 flow 和 invariant 后问一句:

> 用这些符号,能不能把需求文档里每条验收标准都写出来?

写不出来的地方就是缺口——那里需要补一个 invariant,而不是让 AI 临时发明断言。

# Part 4 · 两条启动链路

```
链路 A(人 / CI)
$ pytest biz/wallet/cases -k send --env=prod
  → conftest 注册 domain、加载 conf
  → 收集 + 参数化展开
  → 【共用内核】
  → HTML 报告(给人看)

链路 B(agent)
"跑一下 BSC 的 send 用例"
  → mcp.run_tests(selector)          stdio 子进程
  → core/runner 以库方式调用          不 fork 新逻辑
  → 【共用内核】
  → 结构化摘要 + run_id(给 agent 看)

共用内核:
fixture 借号归位 → client → flow 编排 → invariant 判定 → teardown → triage
```

## 两个实现要点

**MCP 不要 shell 调 pytest 再解析 stdout。**
把 runner 做成可被库调用的 `run(selector, env) -> RunResult`,pytest 插件和 MCP tool 都调它。

**输出必须分叉。**
把 pytest 原始日志返给 agent 是最常见的错误,几千行直接淹掉 context。

## 用例在哪

两条链路跑**同一批**用例,都是 `biz/wallet/cases/` 下的普通 Python 文件,没有第二套。

生成用例**不做成 MCP tool** — agent 本来就有文件读写能力,直接写文件更可控:能 review diff、能 git 管理。做成 tool 反而让用例凭空出现在看不见的地方。

# Part 5 · MCP 能力面

stdio 起步,不需要服务。

```python
@mcp.tool()
def provision(spec: str) -> dict:
    """按描述构造测试状态,返回句柄和清理 token"""

@mcp.tool()
def run_tests(selector: str) -> dict:
    """执行用例,返回结构化摘要"""

@mcp.tool()
def explain_failure(run_id: str) -> dict:
    """归因 + 最小复现 curl"""

@mcp.tool()
def impact(diff: str) -> list:
    """接口 diff → 受影响用例集"""
```

## 返回设计

```python
{
  "run_id": "run-20260731-1147",
  "summary": "5 passed, 1 failed",
  "failures": [{
     "case": "WK-SEND-BSC-GAS-ACCOUNT",
     "step": "gas/account/list",
     "expected": "options[] 含 FUNDING_ACCOUNT",
     "actual": "options[] = [] code=100002001"
  }],
  "detail_hint": "调 explain_failure(run_id) 取完整现场"
}
```

## 设计原则

- **粗粒度** — 不暴露 `list_test_files` 这类内部结构
- **返回摘要不返回原始日志** — 细节走二次调用
- **docstring 就是 prompt** — 模型靠它决定调不调、怎么传参,写得比业务代码还认真
- **危险操作标注** — 造数据、写生产的 tool 在描述里说明

## 何时升级 HTTP 服务

三个条件满足才升级:
1. 别人(开发、其他 agent)要用,不只是你
2. 执行必须在特定环境(CI runner、内网)
3. 需要审计谁跑了什么

同一份代码换传输层,业务逻辑一行不动。所以这不是需要提前决策的架构问题。

## 完整闭环

```
1. impact(diff)                → 受影响的 3 个用例
2. provision("有余额的BSC钱包")  → 状态句柄
3. run_tests(那 3 个)           → 1 个失败,摘要
4. explain_failure(run_id)     → 归因 + 可复现 curl
5. agent 改代码,回到 3
```

> **这个循环里没有你。** 从"跑测试的人"变成"提供质量能力的人"。

# Part 6 · IntelliPandora 改造

## 6.1 砍 / 留 / 加

**砍:**
- `core/engine/generate` 模板代码生成 → 交给 LLM
- RobotFramework 适配 → 关键字驱动的用户群消失了,且降低 agent 生成质量
- UI / 算法域 → 先归档,收敛到 API
- `run/` 的脚手架子命令 → agent 不用 scaffold

**留:**
- `core/protocol` — 底座
- `core/base`、`utils`、`conf`

**加:**
- `core/fixture` — 账号池 + 生命周期 + 并发隔离(最大工程量)
- `core/invariant` — 把 common 断言重构成可组合组件
- `core/triage` — 失败归因
- `mcp/` — 四个 tool

## 6.2 定位:架构通用 ≠ 定位通用

通用性还在,但**不再稀缺**——适配和胶水的成本已经塌了,一个人让 agent 写个协议驱动一小时的事。不稀缺的东西不能当价值主张。

```
通用内核    protocol / fixture 机制 / invariant 框架 / MCP 协议
    ↑ 可复用、可迁移、可给别的产品线
垂直能力包  web3: fork 管理、链上不变量、bundle 断言、订单交叉校验
    ↑ 差异化、抄不走
```

内核保持通用,但**叙事和第一个能力包必须垂直**。

先做透一个场景,内核会被真实需求逼成通用的,而不是设计出来的通用。第二个能力包的成本会低很多。

## 6.3 别人怎么接

只写业务包,内核和 MCP 一行不动:

```python
# biz/earn/__init__.py
register_domain("earn", EarnDomain(client=..., fixtures=..., invariants=...))
```

MCP 按注册表分发,它不需要知道 earn 是什么。

| | 是什么 | 成本 |
|---|---|---|
| spec 导出 | 接口长什么样 | 半天,生成 client,白送 L0 契约测试 |
| 领域 fixture | 怎么造状态、怎么还原 | 几天,难点在回滚策略 |
| 领域 invariant | 什么叫对 | 持续,只增不减 |

# Part 7 · 报告设计

原报告只证明了"接口都通了",没证明"这笔钱动对了"。四处结构改动:

**① 业务断言层** — 把散在 step 里的 capture 提炼成可判定断言,并显式标出 MISSING 的洞。

**② 覆盖矩阵** — 链 × Gas 路径、接口 × 校验维度。价值不在展示跑过的用例,在于**那个空格子**。用例列表永远暴露不了没写的东西,矩阵会把它画出来。

**③ 每个 step 携带完整 HTTP 现场** — headers / body / response + copy as curl。失败步骤一键复制在终端重放。

**④ 数据与渲染分离** — harness 只产 JSON,模板不动。

信息架构:**摘要在外,现场在内,按需展开**。这和 MCP tool 的返回设计是同一件事。

状态区分:
- `gap` = 没写这条断言
- `BLOCKED` = 写了但前置失败没跑到
- `SKIPPED` = 前置条件不满足(环境问题,不是代码问题)

脱敏必须在 harness 侧写 JSON 之前做完,不能靠渲染层遮——报告会被下载、转发、进 CI artifact。

# Part 8 · 分阶段落地计划

## Phase 1 — 立即见效(1 周)

| 任务 | 产出 | 备注 |
|---|---|---|
| Schemathesis 接 spec | L0 契约测试基线 | 一两天,零数据依赖 |
| 从现有脚本抽 assert | invariant 库 v0 | 合并同类项即可 |
| client 生成 | `biz/wallet/client.py` | datamodel-code-generator |

**验收:** L0 用例进 CI,每次 PR 全量跑。

## Phase 2 — 核心工程(2~3 周)

| 任务 | 产出 | 备注 |
|---|---|---|
| 账号池 + 借还锁 | `core/fixture/pool.py` | 解并发 |
| ensure_* 归位 | 幂等收敛 | 解当前数据卡点 |
| reclaim 回收 | 余额守恒 | 账号变可循环资产 |
| 余额告警 | Telegram 推送 | 复用现有通道 |

**验收:** 五条 send 用例能并行跑十次,余额不漂移。

## Phase 3 — 语义层(1~2 周)

| 任务 | 产出 |
|---|---|
| SendFlow 编排 | `biz/wallet/flows.py`,AI 起草 |

**验收:** 报告里 MISSING 归零,词汇表自检通过。

## Phase 4 — Agent 接入(1 周)

| 任务 | 产出 |
|---|---|
| runner 改成可库调用 | `core/runner/api.py` |
| MCP stdio server | `run_tests` + `explain_failure` 先做两个 |
| 摘要裁剪 | 结构化返回,不吐原始日志 |

**验收:** 对话里说"跑一下 send 用例"能跑通并拿到可读摘要。

> **MCP 不要放最后。** 它决定这套东西是"一个人的工具"还是"团队的基础设施",越早暴露越早发现哪些 tool 是真需要的。

## Phase 5 — 规模化(持续)

| 任务 | 说明 |
|---|---|
| triage | 失败分类:flaky / 环境 / 数据 / 真 bug,定位到 commit。规模化前必须有 |
| impact | 接口级调用链。粒度停在 endpoint → consumer,**别做全量 AST 函数级** |
| 流量录制回放 | 重构场景 ROI 最高,和 AI 无关 |
| fork 环境 | 破坏性场景补充 |

### 调用链数据源(三路合并)

- **静态** — OpenAPI/proto + 网关路由 + 前端调用点
- **动态** — 测试/线上调用日志(跨服务真实链路,最准)
- **人工** — 核心资金链路手工标注,少而精

仓库别复制进 vault,用 submodule 或只读 sync,只存抽取出的结构化产物。

# 附录 · 检查清单

## 分层是否正确

- [ ] 删掉 `mcp/`,pytest 链路毫发无伤
- [ ] 用例里没有 HTTP 细节、没有新写的断言、没有数据准备
- [ ] `build()` / `send()` 无参
- [ ] 方法签名里没有 `chainId` / `base_url` / 私钥
- [ ] 没有 yaml 数据文件

## Fixture 是否可靠

- [ ] 账号借出加锁
- [ ] `ensure_*` 幂等,跑两次结果一致
- [ ] 收款方是自己的号,钱能转回
- [ ] 前置不满足 SKIP 而非 FAIL
- [ ] teardown 覆盖所有副作用
- [ ] 余额告警已接通

## Invariant 是否足够

- [ ] 通用层在内核,领域层在业务包
- [ ] 返回 Check 而非 raise
- [ ] `expr` 字段能独立说明失败原因
- [ ] 需求文档每条验收标准都有对应 invariant
- [ ] 报告里 MISSING 为零

## 安全

- [ ] 私钥走 KMS 或环境变量
- [ ] 报告脱敏在写 JSON 前完成
- [ ] pre-commit hook 扫私钥模式
- [ ] `signedTx` / 助记词 / 签名原文均已脱敏
