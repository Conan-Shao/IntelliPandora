# 第三方组件安全准入与漏洞扫描（专项）

> 2026-11-05 · 框架设计和实现中引入的**每一个**基础组件、第三方组件，都要先过安全准入，进来之后持续做漏洞扫描。本专项排在所有新组件引入之前，即 `14` 的 M0。
>
> 依据：测试框架会进 CI，拿着测试账号和密钥，在被测环境里执行代码；agent 评测还会在沙箱里运行外部的 agent 二进制。它是投毒的高价值目标，见 `10`「方向一：测试框架自身的安全（防投毒）」。

## 1. 结论与现状

**今天实测的基线**（pip-audit 2.10.1，查询 PyPI / OSV 漏洞库）：

| 范围 | 结果 |
|---|---|
| 运行时依赖：内核 8 个 + `[ai]` `[mcp]`，含传递依赖 | **0 个已知漏洞** |
| 工具链：开发环境里的 pip 24.0、setuptools 79.0.1 | **pip 6 个、setuptools 2 个**已知漏洞，均有修复版本。setuptools 还参与打包，见 §6 |
| 计划引入的组件，含传递依赖：xdist、filelock、Playwright、pytest-playwright、uiautomator2、Appium 客户端、Pillow、pixelmatch、imagehash、scikit-image、RapidOCR、inspect-ai、inspect-swe | **0 个已知漏洞** |
| 许可证（PyPI 元数据） | 全部是宽松许可：MIT、Apache-2.0、BSD、ISC、MIT-CMU |

**现存的问题**，都要在 M0 修掉：

| # | 问题 | 风险 |
|---|---|---|
| 1 | `requirements.txt` 已过时且不锁版本：还列着 1.11.0 已删掉的 robotframework、pymysql、six、pendulum、websockets 等，共 21 个包，`make install` 会全部装上 | 依赖瘦身在开发环境上等于没做；不锁版本意味着装到什么版本取决于安装时间 |
| 2 | CI 引用 GitHub Actions 用的是标签（`actions/checkout@v4`），没有固定到提交 SHA | 标签可以被改指向。2025 年 tj-actions 被篡改，就是利用这一点在大量仓库的 CI 里窃取密钥 |
| 3 | CI 里**没有任何依赖漏洞扫描**，也没有开启 Dependabot | 漏洞公开之后没人知道 |
| 4 | 计划组件中有三个的最新版刚发布几天：filelock 4.2.9（1 天前）、Appium-Python-Client 6.1.4（3 天前）、inspect-ai 0.3.287（5 天前） | 恶意版本通常在发布后几天内才被发现并撤下，这时立刻采用风险最高 |
| 5 | 有几个组件会在**运行时**下载二进制，pip 扫描看不到：Playwright 下载浏览器；inspect-swe 默认把**当前最新的** Claude Code / Codex CLI 下载进沙箱；uiautomator2 会往设备上装服务端组件；RapidOCR 可能在首次运行时下载模型（待核实）；Appium 及其驱动走 npm | 这些是 Python 依赖清单之外的供应链 |

## 2. 范围：什么算"第三方组件"

| 类别 | 例子 | 扫描工具 |
|---|---|---|
| Python 包，含传递依赖 | 内核依赖、各可选安装组 | pip-audit（PyPA 官方，查 PyPI 与 OSV 漏洞库） |
| 运行时下载的二进制和模型 | 浏览器、agent 命令行工具、OCR 模型、设备端组件 | 固定版本 + 校验和；登记在册 |
| 其他生态的包 | Appium 及其驱动（npm） | OSV-Scanner（覆盖多生态）或 `npm audit` |
| 容器镜像 | agent 评测的沙箱镜像、CI 镜像 | Trivy 或 Grype |
| CI 动作 | GitHub Actions | 固定到提交 SHA；Dependabot 负责升级 |
| 我们自己发布的产物 | wheel | SBOM、可溯源发布（§6） |

## 3. 准入：引入之前

每个新组件进来之前，都要在 PR 里附一份准入记录，并登记到 `docs/security/components.md`。**没有记录的依赖，CI 拒绝合入**（§5 的门禁会对比依赖清单和登记表）。

| 检查项 | 标准 | 怎么查 |
|---|---|---|
| **必要性** | 标准库或已有依赖做不到。1.11.0 删掉了 8 个从未被使用的依赖，就是这一条没把关的结果 | 人工说明理由 |
| **放在哪** | 默认放进可选安装组；进内核需要单独说明理由 | 看 `setup.cfg` |
| **漏洞** | 选定版本及其传递依赖没有未修复的高危或严重漏洞 | pip-audit / OSV-Scanner |
| **许可证** | 白名单：MIT、BSD、Apache-2.0、ISC、MPL-2.0、PSF。GPL / AGPL 不能进内核，可选组需单独评审 | PyPI 元数据 + pip-licenses |
| **维护状态** | 12 个月内有发布；由组织维护或有多名维护者；参考 OpenSSF Scorecard | PyPI、GitHub |
| **发布冷却期** | 选定版本发布满 **14 天**；紧急安全修复可以例外，但要写明理由 | PyPI 上传时间 |
| **来源** | 名字和官方文档一致（防仿冒包名）；提供 wheel；有 PyPI 来源证明（attestation）的，验证它 | PyPI、pypi-attestations |
| **安装期行为** | 优先只用 wheel；只有源码包的，要审查 `setup.py` 会执行什么 | 看发布文件 |
| **运行期行为** | 会不会联网下载、起子进程、往设备装东西、读写家目录。有的话写明，并固定版本和下载源 | 读文档和源码 |
| **体积** | 记录传递依赖的数量 | 解析依赖树 |

## 4. 版本与完整性

| 对象 | 做法 |
|---|---|
| 发布给用户的包 | `setup.cfg` 里的版本上下限都锁住（已有）。不锁死到精确版本，否则用户会和自己的其他依赖冲突 |
| 我们自己的 CI 和开发环境 | 用锁文件加哈希：`scripts/update_locks.py` 调 `uv pip compile --universal --generate-hashes --exclude-newer <今天-14天>` 生成，一份覆盖 Python 3.10–3.12 和所有平台；安装时加 `--require-hashes`。**冷静期由解析器执行，不靠人记**。已删掉过时的 `requirements.txt`，`make install` 改为安装锁文件 |
| 运行时下载的二进制 | 一律固定版本：Playwright 的浏览器跟随 Playwright 版本走；inspect-swe 显式指定 agent 的版本，**不用"当前最新"**；设备端组件随 uiautomator2 的版本固定；OCR 模型在仓库或制品库里存一份，附校验和 |
| 容器镜像 | 按 digest 引用，不按标签 |
| GitHub Actions | 固定到提交 SHA，注释里写明对应的版本号 |

## 5. 持续扫描：进来之后

漏洞是在组件被引入**之后**才公开的，所以只在 PR 时扫一次不够。

| 时机 | 做什么 | 失败时 |
|---|---|---|
| **每个 PR** | 对每份锁文件跑 pip-audit；检查依赖清单和登记表是否一致；用 bandit 扫我们自己的代码；密钥扫描（已有） | 有修复版本的高危或严重漏洞：拦下。没有修复版本：可以登记一条例外，必须写明理由和到期日 |
| **每天定时** | 对 main 分支的锁文件跑同样的扫描。OSV-Scanner（npm）和 Trivy（沙箱镜像）在 M5 / E1 引入对应组件时加上 | 作业失败，GitHub 通知维护者；同时自动开 PR 更新[安全报告](../../security/report.md)，报告里列出受影响的组件和修复版本 |
| **持续** | 开启 Dependabot 的漏洞告警和安全更新（Python 依赖与 GitHub Actions） | 由 Dependabot 提 PR，走正常评审 |
| **每次发版前** | 全量扫描；生成 SBOM | 不通过不发版 |

**例外登记**：写在 `docs/security/exceptions.md`，包含漏洞编号、受影响的组件、为什么不影响我们、到期日。**过期的例外会让 CI 失败**，否则例外就会变成永久豁免。

## 6. 我们自己的产物

- **SBOM**：每个版本用 cyclonedx-bom 生成 CycloneDX 格式的软件物料清单，随版本一起发布。
- **可溯源发布**：用 PyPI 的 Trusted Publishing，从 GitHub Actions 直接发布，不在本地机器上保存 PyPI 令牌，并附上来源证明。这也顺带解决了"发版需要凭据"这个一直悬着的问题。
- **构建工具链**：打包时固定 `setuptools` 到已修复的版本（≥ 84.1，见 §1），同时补上 `pyproject.toml` 的 `[build-system]`。现在构建时用的是什么版本的 setuptools，取决于构建那台机器，而 `08` 已经吃过这个亏：wheel 里该有的文件没有打进去，原因正是不同机器上的 setuptools 版本不同。
- **wheel 内容检查**：已有（`scripts/check_packaging.py`）。

## 7. 和各里程碑的关系

| 里程碑 | 新组件 | 准入时要特别看的 |
|---|---|---|
| **M0（本专项）** | pip-audit、uv、cyclonedx-bom、bandit、build：只进开发环境，不进运行时。原计划的 pip-tools 换成了 uv（`--exclude-newer` 直接执行冷静期，`--universal` 一份锁文件覆盖所有平台）；pip-licenses 没有引入，许可证检查用标准库 `importlib.metadata` 自己实现，少一个组件 | 它们自己也要过准入，见[登记表](../../security/components.md) |
| M2a / M2b | pytest-xdist、filelock | filelock 4.2.9 不满冷却期，先用上一个满 14 天的版本 |
| M3 | Playwright、pytest-playwright | 浏览器二进制的下载源和版本 |
| M3v | Pillow、pixelmatch；可选 scikit-image、RapidOCR | Pillow 历史上图像解析漏洞多，要在每日扫描里重点关注；RapidOCR 的模型下载行为 |
| M5 | uiautomator2；可选 Appium 客户端 | 设备端组件；Appium 走 npm，用 OSV-Scanner 扫 |
| E1 | inspect-ai、inspect-swe；沙箱镜像 | **inspect-swe 必须显式固定 agent 版本**；沙箱镜像按 digest 引用并用 Trivy 扫描；inspect-ai 0.3.287 不满冷却期 |

**M0 期间顺带发现并修掉的**：

- **main 上的 CI 从 #12 起一直是红的**：`mcp` 的上限写成了 `<2`，但代码用的是只在 2.x 才有的 `mcp.server.mcpserver`；`httpretty` 测试要用，CI 却没装。本地门禁全绿掩盖了这一点。现在 `mcp>=2.0,<3`，`httpretty` 进了 `test` 可选组，锁文件包含它们。
- `crypto.py` 里有一段示例代码，带着一个邮箱密码的密文。仓库里从未提交过对应的私钥，PyPI 上已发布的版本也不含私钥，所以无法解密。示例已删除；那个密码是否需要更换，由持有者决定。

**需要仓库管理员操作的**（步骤见[开发手册](../../dev/IntelliPandora_Dev.md)「编译发布」「安全扫描」）：开启 Dependabot 告警与安全更新；配置 PyPI 的 Trusted Publishing 和 GitHub 的 `pypi` 环境；允许 GitHub Actions 创建 PR（报告自动更新要用）；为 `main` 设置分支保护，要求检查通过才能合入。

**M3 准入时补正的**（2026-11-05）：

- **冷静期差一天。** uv 把 `--exclude-newer 2026-10-22` 理解为"包括 10-22 当天"，于是当天下午发布的版本，只有 13 天多一点也能进锁文件。回查发现 M0 选入的 uv 0.13.5（发布 13 天 22 小时）就是这样进来的。现在截止时间是精确到 UTC 零点的时间戳，并加了测试；uv 改为 0.13.4。
- **人工审查过的许可证例外。** 白名单之外的许可证，经审查后接受的，登记在 `scripts/check_components.py` 的 `REVIEWED_LICENSES`，写明按哪个许可使用、为什么接受，安全报告里逐条公开。第一条是 text-unidecode（Artistic / GPL 双许可，按 Artistic 使用，只随可选组 `[web]` 进来）。
