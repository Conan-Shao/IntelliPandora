## 1. 并发 A：并行执行

### 目标

`ipandora run tests --workers 4` 跑得快，并且结果和串行**完全一致**：判定清单、零判定、基线比对都一样。

### 调研

| 候选 | 事实 | 结论 |
|---|---|---|
| **pytest-xdist 3.8.0** | 多进程；worker 的测试报告会回传主进程，再交给主进程的 `pytest_runtest_logreport` 钩子 [资料：[xdist how it works](https://pytest-xdist.readthedocs.io/en/stable/how-it-works.html)]。报告序列化用的是 `report.__dict__.copy()`，所以 `user_properties` 会跟着回传 [源码：`_pytest/reports.py` `_report_to_json`]。3.6.1 起 worker 固定在主线程执行用例 [资料：[changelog](https://build.opensuse.org/projects/home:lalala123/packages/python-pytest-xdist/files/python-pytest-xdist.changes?expand=0)] | **采用** |
| 线程并行（pytest-run-parallel 等） | pytest 文档写明 fixture 不是自动线程安全的 [资料：[pytest flaky.rst](https://testgitea.trustie.net/floraachy/pytest2/commit/b67dab9eca95a9f1c2cc98da789a4ceeb30ea425)]；Playwright 不是线程安全的，需要每个线程一个实例 [资料：[playwright-python#2001](https://www.github.com/microsoft/playwright-python/issues/2001)]；而我们的 `Runtime.Case`、证据记录器、HTTP session 全是按线程隔离的 | 不采用。UI 层会因此直接出问题 |
| 自研多进程调度 | 等于重写 xdist 的分发与负载均衡 | 不采用 |

**[实测] 现在的问题**：直接加 `-p -n 4` 跑，耗时从 5.2 秒降到 2.3 秒，但**所有判定都丢了**，4 条用例全部变成零判定。原因是判定记录在 worker 进程里，而收集结果的插件对象只存在于主进程。

### 方案

1. **插件改成模块形式，主进程和 worker 都加载。**
   - 现在 `ResultCollector` 是作为插件对象传给 `pytest.main(plugins=[...])` 的，worker 进程里没有它。
   - 拆成两部分：
     - `ipandora.core.runner.plugin`：用 `-p ipandora.core.runner.plugin` 加载，xdist 会把这个参数带到每个 worker。负责记录判定（assert 钩子、raises/warns 包装）、开关证据槽，并在每条用例结束时把判定、请求证据、声明（dims、flaky、标题、是否可判）写进 `item.user_properties`，键为 `ipandora.evidence`。
     - 主进程侧的收集器：只从报告的 `user_properties` 读取。
   - **串行和并行走同一条路径**，串行只是 worker 数为 1，不保留两套代码。
2. **跨进程传配置。**
   - `-e staging`：现在只在主进程叠加配置，改为通过环境变量 `IPANDORA_ENV` 传下去，worker 启动时自己叠加。
   - 字节码缓存：用 `PYTHONPYCACHEPREFIX` 环境变量替代 `sys.pycache_prefix`。后者是进程内状态，新进程继承不到。
3. **共享资源互斥。**
   - 用 `@pytest.mark.resource('account:vip')` 声明独占资源，用 **filelock 4.2.9** 做跨进程互斥。
   - 锁文件放在运行目录下，按资源名区分。
   - 拿锁超时视为环境问题（归因 environment），不算用例失败。
   - 不用 xdist 的 `xdist_group`：它把同组用例分到同一个 worker 串行执行，资源一多就退化成串行。锁更细，只在真正冲突时等待。
4. **入口。**
   - CLI：`--workers N|auto`；MCP：`run_tests(workers=N)`。
   - xdist 作为可选的 `[parallel]` 安装；没装时给 `--workers` 会直接报错并提示安装，而不是悄悄串行。

### 风险与先验证的

- **`-p` 参数能不能带到 worker**：方案依赖 xdist 让每个 worker 也加载我们的插件模块。我认为会带到，但目前没有实测，所以这是 M2a 的第一件事；如果带不到，退路是在 worker 启动钩子里显式注册。**不用** `pytest11` 入口点自动加载：那样会在用户直接运行普通 `pytest` 时也包装 `pytest.raises`，属于越界。
- **单条用例卡死**：一个 worker 会被挂住，而并行时更难发现。加上单条用例超时：用 pytest-timeout，或者自己做一个，M2a 里选定。超时归因为环境问题。手册里评测框架的运行器也把超时列为必备。
- **资源锁的范围**：filelock 只管同一台机器。多台机器、多个 CI 作业共用测试账号时，需要分布式锁（例如 Redis），这不在本步范围内，在文档里写明。

### 验收

- 同一套件串行和 `--workers 4` 跑，判定清单逐字节一致。这条作为测试写进仓库。
- 现在会丢判定的场景加上回归测试：并行跑时零判定数必须和串行一致。
- 4 个 worker 跑一个 IO 等待型套件，耗时不超过串行的 40%。
- 两条用例声明同一资源时不会同时执行（用时间戳重叠来断言）。

### 实施结果（2026-11-05）

验收四条全部通过，都写成了测试：`test/testrunner/test_parallel.py`，共 28 条。

| 验收 | 结果 |
|---|---|
| 判定清单逐字节一致 | 一致。比对范围比要求更宽：每条用例的结论、消息、判定、请求证据、dims、flaky、标题、是否可判，以及用例顺序、覆盖矩阵、被排除的用例、收集错误，全部相同 |
| 零判定数与串行一致 | 一致 |
| 耗时 ≤ 串行的 40% | 8 条各等 1 秒的用例：串行约 8 秒，4 个 worker 约 2.8 秒（约 34%）。**后续修正**：worker 启动是固定开销，本机约 0.8 秒，GitHub runner 上实测 1.3 秒；8 条用例时 CI 上一次跑出 40.2%，测到的其实是启动开销而不是并行效果。测试改为 16 条用例，阈值不变 |
| 同一资源不同时执行 | 用时间戳断言不重叠；同一套件里不声明资源的用例确实重叠，证明测到的是锁而不是串行 |

第一项验证（`-p` 能否带到 worker）实测成立：插件模块、`-o enable_assertion_pass_hook`、`user_properties`（含 bytes、元组）都能到达或回传，收集错误也会转发。

**与方案不同的三处**，都是实测后改的：

1. **被排除的用例要单独回传。** xdist 在 worker 里执行 `-m` 过滤，但**不转发** `pytest_deselected`。不处理的话，`--exclude-flaky` 承诺的"被排除的用例仍会点名"在并行时会悄悄失效。现在由 worker 写进 `workeroutput`，主进程在 `pytest_testnodedown` 里读。
2. **字节码缓存不用 `PYTHONPYCACHEPREFIX`。** 实测这个环境变量从解释器启动起就重定向所有导入，每个 worker 每次运行都要把 pytest、requests 等库从源码重新编译一遍。4 个 worker 只省下 35% 的时间，没达到 40% 的验收。改为 worker 在加载 conftest 之前、库已经导入之后，自己设置 `sys.pycache_prefix`，时机和主进程串行时一致，耗时随之降到约 34%。
3. **资源锁不引入 filelock，用标准库实现**（POSIX 用 `fcntl.flock`，Windows 用 `msvcrt.locking`）。准入时发现 filelock 7 周内发布了 26 个 4.x 版本，而且在 4.x 中途放弃了 Python 3.10。这里只需要"带超时的独占锁"，标准库就能做到，按 `15` §3 的必要性原则不引入。锁属于打开的文件，进程崩溃时自动释放。Windows 分支 CI 没有覆盖，这一点如实记录在这里。

**超时**选用 pytest-timeout：成熟，由 pytest-dev 维护，在 xdist worker 里同样可用（3.6.1 起 worker 在主线程执行用例，信号方式可用）。超时和等锁超时都归因为环境问题；超时的置信度是中等，因为被测系统自身卡死属于缺陷。

**新增组件**：pytest-xdist 3.8.0（附带 execnet 2.1.2）、pytest-timeout 2.4.0，放在可选组 `[parallel]`，已登记。两者都超过 12 个月没有新版本，不满足维护状态里"12 个月内有发布"这一条，但都由 pytest-dev 组织维护、功能稳定，登记表里写明了这一例外。

**另外做了的**：
- 并行时结果按收集顺序排列，而不是按哪个 worker 先跑完。
- 每个 worker 都会报告同一个收集错误，只记一次。
- 用户自己加了 pytest 的 `--junitxml` 时，XML 里不会混进我们的证据数据，用户自己 `record_property` 的值保留。

## 2. 并发 B：并发场景测试

### 目标

一条用例里同时发起 N 个操作，判断产品在并发下对不对：恰好一次扣款、不超卖、幂等键生效。

### 调研与结论

- **用线程，不用 asyncio**：用例和 HTTP 层都是同步代码（requests）。改成 asyncio 等于要求用户重写用例。
- **[源码] 发现的坑**：`SessionManager` 按线程名加线程 ID 区分 session（`core/schedule/session.py`）。用例在主线程登录后，新开的线程拿到的是一个**全新的 session，不带登录态和 cookie**，并发请求会以未登录身份发出去。这一点必须在原语里处理。
- **[源码]** 证据记录器是 `threading.local`，新线程里没有当前用例，请求证据会全部丢失。

### 方案

```python
from ipandora.core.concurrency import concurrently

results = concurrently(lambda: OrderApi().pay(order_id, key='idem-1'), n=20)
codes = [status_code(r.value) for r in results]          # status_code() 已有，兼容 ResponseHandler
assert_all(
    that(codes, '各请求状态').each().is_in([200, 409]),
    that(codes.count(200), '成功扣款次数') == 1,              # 恰好一次
    field(OrderApi().get(order_id), 'data.paid_amount') == 100,  # 终态
)
```

- **起跑同步**：用 `threading.Barrier(n)`，所有线程就绪后同时放行。每个结果记下起跑偏移，原语还会报告"最大起跑偏差"。偏差过大说明并发没有真正发生，这时在结果上给出警告。
- **会话传播**：每个并发线程启动时，复制调用方 session 的请求头和 cookie。不共享同一个 `requests.Session` 对象，因为 requests 不保证 Session 的线程安全。
- **证据传播**：把调用方线程当前的证据槽绑定到每个工作线程，并发请求都记进当前用例。
- **结果对象**：包含值、异常、耗时、起跑偏移。异常不会抛出来打断用例，而是交给判定去处理。
- **起跑前就失败**：某个线程在准备阶段出错时，屏障会超时、整体放弃，并明确报告"并发没有发生"，而不是退化成一组串行请求还照常判定。
- **边界**：不做 RPS 目标、不做延迟分位数，那是 Locust、k6 的事。

### 验收

- 仓库内起一个本地 HTTP 服务，故意写一个有竞态的扣款接口：`concurrently` 能稳定复现超扣，换成加锁的实现后测试通过。
- 并发请求带着登录态（服务端校验 cookie）。
- 每个并发请求都出现在报告的证据里。

### 实施结果（2026-11-05）

验收三条全部通过，都写成了测试：`test/testconcurrency/test_concurrently.py`，共 24 条，跑在进程内的真实 HTTP 服务上。

| 验收 | 结果 |
|---|---|
| 稳定复现超扣，加锁后通过 | 有竞态的接口连续 3 次都复现了多次扣款；同样的判定在加锁实现上通过，在有竞态的实现上失败 |
| 并发请求带着登录态 | 服务端校验 cookie，并发请求没有一个是 401；对照组：普通线程发出的请求确实是 401 |
| 每个并发请求都在报告证据里 | 通过 `run()` 跑一条 12 路并发的用例，12 个请求连同各自的状态码（1 个 200、11 个 409）都在用例的证据里 |

两个源码里发现的坑都实测复现过：主线程登录后，新线程请求 `/me` 得到 401；新线程的请求不在用例证据里。

**比方案多做的**：

- **并发是否真的发生，作为一条判定。** 屏障只能保证同时放行，线程被唤醒仍有先后（本机实测约 10ms）。比这还快的操作，会在最后一个起跑之前就结束。所以不是只看"起跑偏差大不大"，而是直接判断**最后一个起跑时，最早的那个是否已经结束**。`results.overlap_check()` 把它变成一条 Check，放进 `assert_all`：串行跑的并发测试永远不会重复扣款，没有这条，这样的测试会通过。没有自动加入判定，因为那样会让一条什么都没写的用例看起来"有判定"。
- **起跑期限是整组共用一个。** 最初用的是 `Barrier(timeout=)`，它对每次 `wait` 单独计时。测试发现：所有线程都同样慢的时候，整组仍然会晚到之后照常起跑。现在是整组一个期限。
- **线程结束时清掉它的 session。** session 按线程名加线程 ID 区分，而线程 ID 会被复用。不清掉的话，下一个碰巧拿到同一 ID 的线程会继承上一个线程的 cookie。
- `Runtime.Case` 的步骤记录同样传给并发线程。
- 记录器的写入加了锁，没有 GIL 的解释器上同样成立。

7 处变异全部被测试抓住：session 复制、证据绑定、步骤传递、起跑失败时放弃整组（包括"要等满超时才放弃"）、session 清理、重叠判断、整组起跑期限。

## 3. Web 自动化

### 调研

评判标准沿用框架定位：用 Python、同步写用例；集成，不封装；判定确定、不调 LLM；能放进 M2a 的多进程并行；能通过 `15` 的组件准入。

**2026-11-05 核实**：版本、日期、许可证、依赖都取自 PyPI / npm 元数据和发布包本身，不是转述。Playwright 的几条结论是装上之后实测的。

| 方案 | 核实到的事实 | 结论 |
|---|---|---|
| **Playwright**（Python，Apache-2.0） | 官方 Python 绑定，同步、异步两套 API，要求 Python ≥ 3.10。依赖 greenlet、pyee。最新 1.64.1 发布于 10-22，**未满 14 天冷静期**；可用的是 1.64.0（10-13）。定位器自动等待，断言自动重试；有 trace 和回放查看器；每条用例一个新的浏览器上下文，开销很小；内置 Chromium / Firefox / WebKit。**[实测]** Python 版的 `PageAssertions`、`LocatorAssertions` 都没有截图比对方法。浏览器另行下载，**版本跟着 Playwright 走**：1.64.0 需要 Chromium 1248 版（156.0.8078.4），本机预装的是 1243 版，不能直接用 | **采用** |
| pytest-playwright 0.10.0（Apache-2.0，10-08） | 官方 pytest 插件，依赖 playwright、pytest、python-slugify。**[实测]** 自带 `--browser`、`--browser-channel`、`--headed`、`--device`、`--base-url`、`--tracing {on,off,retain-on-failure}`、`--screenshot {on,off,only-on-failure}`、`--video`、`--output`，我们要的失败证据它都能产出 | **采用**，不另造 fixture |
| Selenium 4.52 / 4.51（Apache-2.0） | W3C WebDriver 标准，存量用例最多；有 Grid 做分布式；能驱动真正的 Safari（safaridriver）。**[核实]** wheel 里带着各平台预编译的 `selenium-manager` 可执行文件，运行时会自动下载浏览器驱动；4.x 里有 21 个 BiDi 模块，但核心命令仍走 WebDriver HTTP 协议；需要自己写显式等待；没有 trace | 不作为主选。已有 Selenium 用例、依赖 Grid、必须测真 Safari 的团队，可以自己接，判定层照样能用 |
| SeleniumBase 4.57（MIT） | 在 Selenium 上再封装一层，补了等待和报告。**[核实]** 运行时依赖 66 个，其中包括 pip、setuptools、wheel；9 月以来发布了 31 个版本 | 不采用：封装之上再封装，违反"集成，不封装"；依赖面大、发布频繁，准入成本高 |
| Helium 7.0（MIT） | 在 Selenium 上提供更口语化的 API。上一个版本是 2026-07，之前长时间没有更新 | 不采用：同上，而且维护不活跃 |
| DrissionPage 4.1 / 5.0b（自定义许可） | 国内流行，基于 CDP，能和 requests 混用，多用于数据采集。**[核实，发布包内的 LICENSE 原文]**"允许任何人以个人身份使用或分发本项目源代码，但仅限于学习和合法非盈利目的。个人或组织如未获得版权持有人授权，不得将本项目以源代码或二进制形式用于商业行为。"PyPI 元数据里没有声明许可证 | **不采用**：不是开源许可，有商用限制，过不了 `15` §3 的许可证白名单 |

| Puppeteer、Cypress、WebdriverIO | 只支持 JS/TS | 不适用 |
| Robot Framework Browser 21.0（Apache-2.0） | 底层就是 Playwright，外面套一层 Robot 关键字，经 gRPC 和 Node 进程通信；要求 Python ≥ 3.11 | 不采用：1.11.0 已经移除了 Robot Framework 支持；直接用 Playwright 更薄 |
| browser-use 0.13（MIT，Python） | 由 LLM 看页面决定下一步操作。**[核实]** 依赖 `anthropic<2.0.0`，和框架 `[ai]` 组的 `anthropic>=2.1` 冲突；要求 Python ≥ 3.11 | **不能用来执行判定**：每跑一次都调 LLM，结果不可复现，违反"判定不调 LLM"。可以让 agent 拿它探索页面、帮忙写用例，但不进框架依赖 |

**结论：选 Playwright + pytest-playwright。** 理由按重要性排：

1. 自动等待能消除大部分 UI 用例的不稳定。
2. trace 和失败截图是现成的失败证据，pytest-playwright 已经能产出，我们只需要挂进报告。
3. agent 写 Playwright 最顺，它的公开 API 在训练数据里覆盖最广。
4. 和 M2a 的多进程模型天然契合：每个 worker 一个浏览器，每条用例一个上下文。

判定层和驱动是解耦的。以后要接 Selenium，`that()`、判定清单、报告都不用改；要补的只有判定记录和失败证据这两处适配。

**Playwright 的短板，以及我们怎么补：**

| 短板 | 做法 |
|---|---|
| Python 版没有截图比对 | 第 4 节的图像判定补上 |
| WebKit 不等于真正的 Safari | 写进文档。必须在真 Safari 上验证的，用 Selenium + safaridriver |
| 浏览器运行时下载，是 pip 扫描看不到的供应链 | 固定 Playwright 版本，浏览器版本随之固定；`PLAYWRIGHT_DOWNLOAD_HOST` 可以指向内部镜像；也可以用 `--browser-channel chrome` 改用系统安装的 Chrome |
| pytest-playwright 还是 0.x | 版本上下限锁住，并加一组集成测试，专门检查我们依赖的 fixture 和选项 |
| 同步 API 不能在 asyncio 里用 | **[实测]** 在运行中的事件循环里调用会直接报错 "It looks like you are using Playwright Sync API inside the asyncio loop"。写进文档：async 用例请用异步 API |

### 方案："集成，不封装"在 Web 层的具体做法

| 问题 | 做法 |
|---|---|
| fixture | **直接用 pytest-playwright 的** `page` / `context` / `browser`，以及它自带的 `--browser`、`--headed`、`--tracing` 等选项。我们不另造 fixture |
| 配置 | `conf/<env>.yaml` 里的 `web.base_url`、`web.browser`、`web.viewport` 映射到 pytest-playwright 的 `base_url` 和 `browser_context_args`。用例里写 `page.goto('/orders')` |
| **判定记录** | **会出现新的零判定误报**：Playwright 的 `expect(locator).to_have_text(...)` 不是 assert 语句，assert 钩子看不到。只用 `expect` 写的用例全会被判为零判定。做法和 `pytest.raises` 一样：运行期间包装 `playwright.sync_api.expect`，每个成立的 expect 记为一条判定，比如 `expect #amount to_have_text '100.50'` |
| 失败证据 | 失败时自动截图，保留 trace（相当于 `retain-on-failure`），路径记进证据，报告里给出截图和 `playwright show-trace` 命令 |
| 归因 | **复审修正**：原文写"定位器失效一律算用例自身"，太武断。元素找不到，可能是选择器过时（用例的问题），也可能是按钮真的没了或被挪走（产品缺陷）。把后者当成用例问题，正是 ARTEMIS 式"自愈"会掩盖回归的那个坑。做法：先用确定性的方法区分。失败时在页面里按无障碍名称或文本找同名元素：找到了，说明元素还在、只是选择器变了，归为用例自身；找不到，归为"待确认：可能是产品缺陷"，并附上截图。不确定的时候，不往"不是产品的问题"那边归 |
| 数据判定 | 页面上的值用 `that(page.locator('#amount').inner_text(), '页面金额') == field(r, 'data.amount')`，和接口用同一套判定 |
| 视觉 | Python 版 Playwright 没有截图比对，由第 4 节的图像判定补上。截图前统一关掉动画、固定视口和设备像素比，避免无谓的差异 |
| 安装 | 可选的 `[web]` 安装；浏览器用 `playwright install chromium`。CI 文档里给出缓存浏览器的配方 |

### 风险

- pytest-playwright 还是 0.x，API 可能变动：版本上下限锁住，并加一组集成测试，专门检查我们依赖的那几个 fixture 和选项。
- 同步 API 底层用 greenlet，和已在运行的 asyncio 事件循环会冲突 [资料：[DEV](https://dev.to/deepak_mishra_35863517037/integrating-playwright-with-flask-resolving-the-async-conflict-2d9o)]：文档里写明，不支持在 async 用例里使用同步 API。

### 验收

- 对一个公开站点写一组示例用例，串行和 `--workers 4` 都能跑通。
- 只用 `expect` 的用例不会被判为零判定。
- 失败用例的报告里能看到截图，trace 文件可以打开。
- 选择器过时（页面上仍有同名元素）的失败归为用例自身；元素真的不见了的失败归为"待确认"，并附截图。两种情况各有一条测试。

### 实施结果（2026-11-05）

验收四条全部通过。`test/testweb/test_web.py` 共 19 条，用进程内 HTTP 服务提供页面；公开站点示例另算。

| 验收 | 结果 |
|---|---|
| 公开站点示例，串行和 `--workers 4` 都能跑通 | `examples/web/test_todomvc.py`，对 https://demo.playwright.dev/todomvc 写了 4 条用例，只用 `expect`，串行和 4 个 worker 都通过，没有零判定。这组用例要访问外网，CI 里默认不跑，设置 `IPANDORA_PUBLIC_SITE=1` 才跑 |
| 只用 `expect` 的用例不是零判定 | 是。每个成立的 `expect` 记为一条判定；失败的 `expect` 只记一条失败判定，不会再叠加一条通用的 "assert (failed)"；期望值被改弱时，基线比对能看出来 |
| 报告里能看到截图，trace 能打开 | 截图以 data URI 嵌进报告；trace 文件是能被 `playwright show-trace` 打开的 zip（测试里检查了它的内容）；串行和并行时都会回传 |
| 选择器过时与元素消失各归各的 | 过时 → harness（高）；消失 → defect（低），以"待确认"开头并附截图；从没记录过 → unknown，同样是"待确认"；元素还在、只是状态不对 → 不当作定位问题 |

**和方案不同、或方案里没写到的：**

1. **"同名元素"的"名"从哪来。** 方案只写了"按无障碍名称或文本找同名元素"，没说名称从哪里来：一个 `#pay` 选择器本身不带名称。做法是在用例**通过**时，用 Playwright 的 aria 快照记下每个选择器指向的元素（角色和无障碍名称），存进运行目录旁的 `locators.json`，失败时拿出来查。这个文件只由主进程写，worker 只读；失败的用例不会覆盖已有的记录。
2. **按类打补丁，不替换 `expect` 函数本身。** `LocatorAssertions` / `PageAssertions` / `APIResponseAssertions` 和 `Locator` 的动作方法，是在类上打补丁的。这样无论用例是怎么导入 `expect` 的（包括在 conftest 里先导入），都能记到。
3. **每次运行单独的 `--output` 目录。** pytest-playwright 会在会话开始时清空它的输出目录。如果用默认的 `test-results`，下一次运行就会删掉归档报告还指向着的截图。
4. **嵌套会话。** pytest-playwright 把每条用例包在 Playwright 的 soft assertion 作用域里，这个作用域是进程级的全局变量，不能嵌套。于是在一条测试里调用 `run()`（框架自己的测试就是这样写的）会报 "nested soft assertion scopes are not supported"。`run()` 期间会先把外层作用域挪开，结束后再放回。
5. **截图和 trace 怎么回到主进程。** pytest-playwright 本来就会把截图和 trace 的路径以 `playwright_<kind>` 写进 teardown 报告的 `user_properties`，这正是 M2a 用来回传判定的通道，所以并行时不需要另想办法。
6. **测量 identity 不拖慢用例。** 记录前先用 `count()`（不等待）确认恰好匹配一个元素，然后才取 aria 快照。点击后页面跳走、元素已经消失的情况，不会白等超时。

**准入时发现的问题**（都已处理，见 `15`）：

- 锁文件冷静期差一天：uv 把 `--exclude-newer 2026-10-22` 理解为"包括 10-22 当天"。于是 10-22 下午发布的 playwright 1.64.1（13 天 20 小时）进了锁文件；回查发现，M0 选入的 uv 0.13.5 也是同样情况。截止时间改为精确到 UTC 零点后，playwright 用 1.64.0，uv 降到 0.13.4，pycparser 从 3.12 回到 3.11。
- 传递依赖 text-unidecode 是 Artistic / GPL 双许可，许可证白名单会拒绝它。它只随可选组 `[web]` 进来（pytest-playwright → python-slugify），作用是把用例 id 转写成产物目录名。按 Artistic License 使用，作为人工审查过的例外，写进 `scripts/check_components.py` 的 `REVIEWED_LICENSES`，理由在安全报告里公开。

## 4. 图像维度判定

### 调研

| 用途 | 候选 | 事实 | 结论 |
|---|---|---|---|
| 逐像素比对 | **pixelmatch 0.4.0** | mapbox pixelmatch 的 Python 移植，带抗锯齿识别和感知色差，阈值默认 0.1，要求两张图尺寸一致 [资料：[PyPI](https://pypi.org/project/pixelmatch/0.3.0)] | **采用**。配 Pillow 13 读写图片 |
| 感知相似 | scikit-image 0.26（SSIM）、imagehash 4.3.2（感知哈希） | SSIM 依赖 numpy/scipy，体积大；imagehash 轻 | 可选：`[visual-ssim]` |
| 遮罩 | — | 没有找到单独的遮罩库，现有工具都是自己实现 [资料：[visual-guard](https://pypi.org/project/visual-guard/)] | 自研：比对前把两张图的遮罩区域填成同一颜色 |
| OCR | RapidOCR 3.10（onnxruntime + PaddleOCR 模型）、pytesseract 0.3.13 | pytesseract 需要系统里装 tesseract；RapidOCR 用 pip 就能装，中文效果好 | 可选：`[ocr]`，用 RapidOCR；固定模型版本，保证结果可复现 |
| 图像定位 | opencv-python-headless 5.0 模板匹配 | 给拿不到控件树的界面（游戏、Canvas）用 | 可选，放到 App 层再看 |

### 方案

```python
that(page.screenshot(), '结算页').matches_golden('checkout', tolerance=0.001, mask=[(0, 0, 200, 40)])
that(page.locator('#price').screenshot(), '价格区').matches_golden('price')
```

- **基准图存放**：`tests/__goldens__/<名字>-<浏览器>-<平台>.png`，跟用例一起提交。**复审补充**：同一个页面在 macOS 和 Linux 上的字体渲染不同，一张基准图不能跨平台共用，否则本地生成的基准图到了 CI 上必然失败。Playwright 的 JS 版也是按平台区分基准图的。建议统一在 CI 的容器镜像里生成基准图。
- **基准图更新**：`ipandora run --update-baseline` 同时更新基准图；判定清单里记一条 `screen 'checkout' matches golden <sha>`。基准图被替换会被识别为"改变"，从而被门禁拦下，agent 无法悄悄换图让测试变绿。
- **失败证据**：报告里并排展示基准图、实际截图、差异图。图片超过大小上限时缩略内联，原图放在报告目录。
- **基准图缺失**：判定失败，提示用 `--update-baseline` 生成。不会自动生成一张新图后判为通过。
- **布局与对比度**：基于元素包围盒和 WCAG 对比度公式，纯计算，不需要额外依赖。

### 验收

- 抗锯齿、字体渲染这类细微差别在默认容差内不报错；改动一个按钮颜色时报错，并且差异图上能看出位置。
- 遮罩区域内的变化不报错。
- 替换基准图后，`--fail-on-weakened` 会拦下。

### 实施结果（2026-11-05）

验收三条全部通过。`test/testvisual/test_visual.py` 共 24 条，其中一条用的是真实的 Chromium 截图。

| 验收 | 结果 |
|---|---|
| 抗锯齿、字体渲染的细微差别默认不报错；按钮换色报错，差异图上能看出位置 | 子像素边缘、换一种抗锯齿滤波、±3 色差、同一页面再渲染一次，默认设置下都通过；按钮换色失败，差异图上有红框，判定信息里给出坐标范围。**CI 上发现的修正**：真实页面上一段中文平移 0.4px，本机过滤后是 0 个像素，GitHub runner 上是 18 个（0.0075%），结果取决于机器怎么栅格化字形。默认值不放宽，手册建议整页截图用 `tolerance=0.001`，测试验证了这个容差能吸收文字平移，同时按钮换色（0.39%）仍会失败 |
| 遮罩区域内的变化不报错 | 通过；同时验证了遮罩不会掩盖遮罩之外的变化 |
| 替换基准图后 `--fail-on-weakened` 会拦下 | 通过：重新录制基准图的那次运行本身是绿的，但基线比对把它标为判定变弱 |

**实测后改的方案：**

1. **默认用"成块差异"判定，而不是像素比例。** 只用 pixelmatch 时，两次渲染之间的抗锯齿差异仍有 151–286 个像素，而金额 100.50 → 100.60 只差 **7** 个像素，因为 pixelmatch 把字形边缘当作抗锯齿。任何像素计数阈值都分不开这两种情况。所以：
   - 默认 `noise='edges'`：对差异做一次 3×3 腐蚀，只有成块的差异才计数。抗锯齿和子像素偏移归零，换色仍有 900–12000 个像素。
   - `noise='strict'` 留给要求像素级一致的场景。
   - 用户手册写明：**文字用文字断言来判，不用截图判**。这是度量出来的结论，不是建议。
2. **只比对有差异的包围盒。** pixelmatch 是纯 Python 实现，1280×720 的整图比对要 0.6–0.9 秒，整页都变了时要 7.5 秒。改为只在字节有差异的包围盒上运行，外扩 3 像素（它的抗锯齿检查会看到 2 像素之外）。局部变化时降到毫秒级。400 个随机场景实测：外扩 0 或 1 像素时约 5% 计数不一致，外扩 2 或 3 像素时全部一致；这一点写成了测试。
3. **SSIM、OCR、布局与对比度这次没有做。** 方案里它们本来就是可选项，验收也没有覆盖，留到确实需要时再做，不提前引入 numpy、scipy 和 onnxruntime。

**已知限制**：pixelmatch 会把纯粹 1 像素的位置平移当作抗锯齿，不计入差异；已写进用户手册。

**新增组件**：Pillow 13.0.0（Python 3.10 上是 12.3.0）、pixelmatch 0.4.0，放在可选组 `[visual]`，已登记。Pillow 的图像解析漏洞多，已在登记表里标明由每日扫描重点关注。

## 5. Android

### 调研

| 候选 | 事实 | 结论 |
|---|---|---|
| **uiautomator2 3.7.1**（openatx） | Python 直接和设备通信；Appium 的 Android 驱动底层同样是 UiAutomator2，区别在于 Appium 多了一层服务端和 WebDriver 协议 [资料：[Kobiton](https://kobiton.com/mobile-testing-guide/mobile-test-automation/ui-automator-vs-appium-android-ui-testing/)]。有厂商测得单次操作 uiautomator2 为 30–100ms、Appium 为 100–500ms，但测试方自己卖同类工具，只能参考 [资料：[Handsets](https://handsets.dev/blog/tapping-android-in-5ms-vs-appium-uiautomator2/)] | **主选** |
| Appium 3（UiAutomator2 驱动）+ Appium-Python-Client 6.1.4 | 跨平台（Android、iOS）；Appium 3 主要是清理遗留代码、更严格遵循 W3C [资料：[HeadSpin](https://www.headspin.io/blog/appium-3-guide)]；BrowserStack、Sauce Labs 这类云真机平台普遍使用 Appium 协议 | **备选后端**：要上云真机，或者要和 iOS 共用一套写法时使用 |
| Espresso | 运行在 App 进程内，用 Java/Kotlin 写 | 不适用（不是 Python） |
| Airtest 1.4.3 / Poco | 网易出品，基于图像识别，擅长游戏 | 不作为主选；图像定位的思路放进第 4 节的可选能力 |
| Maestro | 用 YAML 写流程 | 不采用：与"用例是 Python"的原则冲突 |

**结论**：Android 用 uiautomator2；需要云真机或跨平台统一时，可以切换到 Appium 后端。两种后端在 fixture 里分别给出各自的原生对象（`d` / `driver`），不抹平成一套统一 API，遵守"集成，不封装"。

### 方案

| 问题 | 做法 |
|---|---|
| fixture | `device` 返回 `uiautomator2.Device`；配置 `conf/<env>.yaml` 里的 `android.serial`、`android.package`、`android.app_path` |
| 生命周期 | 每个会话安装一次 App；每条用例前启动或清理数据（可配置）；用例结束后停止 App |
| 设备池 | 复用第 1 节的资源锁：每台设备是一个资源 `device:<serial>`，worker 按空闲设备分配 |
| 失败证据 | 截图、控件树导出、按包名过滤的 logcat（`adb logcat -d --pid`）、发生崩溃时的 ANR / crash 记录 |
| 归因 | App 崩溃（logcat 里出现 FATAL EXCEPTION 或 ANR）归为产品缺陷，这一条是确定的；找不到元素的处理同 Web（§3）：控件树里有同名元素，归为用例自身；没有，归为"待确认" |
| 安装 | 可选的 `[android]`；要求本机或 CI 上有 adb |

### 风险与需要你提供的

- 需要一个测试 App 和一台真机或模拟器。CI 上跑模拟器需要 KVM 硬件加速，能不能在你的 CI 上用要先实测。
- 厂商测出的速度数据未经独立验证：在你的 App 上做一次实测对比再最终定（规模小，半天）。

## 8. 文档体系与 `ipandora init`

### 调研

- **Material for MkDocs 已进入维护模式**（2025 年 11 月宣布），官方后继项目是 Zensical，可以读取现有的 `mkdocs.yml` [资料：[squidfunk/mkdocs-material#8523](https://github.com/squidfunk/mkdocs-material/issues/8523)、[Duerrenberger](https://scour.ing/p/https://duerrenberger.dev/blog/2025/11/06/material-for-mkdocs-is-no-more-long-live-zensical)]。Zensical 还很新。
- 脚手架工具 copier 9.19 支持模板升级，但会多出一串依赖。

### 结论与方案

- **以仓库里的 Markdown 为唯一来源**：GitHub 直接渲染，agent 也能直接读。**暂不引入站点生成器**，等确实需要对外的文档站时再评估 Zensical。
- 按 `12` §6 的目录重组：`guide/`（给人，按任务组织）、`reference/`、`design/architecture.md` 加 `design/decisions/`（现在的 00–14 收进这里）。
- **参考文档从代码生成**：CLI 参数从 argparse 生成，配置项从 `config.yaml` 的注释生成。一个门禁检查生成结果和仓库里的文件一致，避免文档过期。
- **文档里的代码要能跑**：使用手册的代码块抽出来，在测试里执行，和代码一起测。
- **给 AI 的文件**：
  - 仓库根目录 `AGENTS.md`：写给开发框架本身的 agent，内容是分层、门禁、提交规范。
  - `llms.txt`：文档索引，方便 agent 检索。
  - `ipandora init` 生成给使用方的 `AGENTS.md`：写给编写用例的 agent，内容是判定怎么写、不许改弱判定、UI 优先用稳定定位符。**每条规则对应一个门禁或一个报告信号。**
- **`init` 用内置模板实现**（`importlib.resources`），不依赖 copier。生成的内容：`conf/config.yaml`、`conftest.py`、示例用例、`AGENTS.md`、CI 配置样例（含 `--fail-on-weakened`）、`.github/CODEOWNERS` 样例（保护 `conf/judgements.json`）。

### 实施结果（2026-11-05）

| 交付 | 结果 |
|---|---|
| 目录重组 | `docs/guide/`（11 篇，按任务组织）、`docs/reference/`（生成）、`docs/design/architecture.md`、`docs/design/decisions/`（00–15 原样迁入）。全仓库 44 个文件里的引用随之更新，由链接检查保证没有遗漏 |

## 9. agent 验证（第三期）

完整设计见 `13`。本节只记录选型。

### 调研

| 候选 | 事实 | 和我们的关系 |
|---|---|---|
| **Inspect AI 0.3.287**（英国 AISI，MIT） | 内置 Docker、K8s 等沙箱；有 epoch（重复试验）、scorer、超时等机制 [资料：[AISI](https://aisi.gov.uk/blog/the-inspect-sandboxing-toolkit-scalable-and-secure-ai-agent-evaluations)]。日志有公开的读取接口：`read_eval_log`、按样本流式读取的 `read_eval_log_samples`、转成数据表的 `samples_df` [资料：[Inspect 日志文档](https://inspect.aisi.org.uk/eval-logs.html)、[inspect_ai.log](https://inspect.aisi.org.uk/reference/inspect_ai.log.html)] | **编码类 agent 的执行引擎** |

| Harbor（Terminal-Bench 团队） | 每次试验开一个容器沙箱，跑 agent，再用 verifier 判分 [资料：[cognee 对比](https://www.cognee.ai/llm-agent-evaluation-tools)] | 了解即可；需要 Terminal-Bench 任务时再评估 |
| promptfoo | 长于提示词对比与红队测试 | 安全评测（`13` §8）可借用它的注入语料 |
| DeepEval 4.3 | pytest 风格，偏 LLM 评委类指标 [资料：[DeepEval](https://deepeval.com/blog/top-5-llm-evaluation-frameworks)] | 判分以模型为主，和"确定性优先"相反 |
| τ-bench | 用对话结束时的数据库状态判分；定义了 pass^k [资料：[arXiv 2406.12045](https://arxiv.org/abs/2406.12045?context=cs)] | 业务 agent 的方法直接采用 |
| Claude Code 无头模式 | `-p` 配合 `--output-format stream-json`、`--resume` [资料：[官方文档](https://docs.claude.com/en/docs/claude-code/headless)]；有社区报告称退出码总是 0 [资料：[zenn](https://zenn.dev/akira_cloudjob/articles/c10c321801f66d)，单一来源] | 走 inspect_swe 时不直接用它；pytest 路径下的命令行适配器不依赖退出码 |

### 结论（复审后修改）

原结论是"不引入现成评测框架作引擎，在 pytest 上自研一层"。**复审认为这一点错了，改为两条路径**：

| | Inspect 路径 | pytest 路径 |
|---|---|---|
| 用于 | 编码类 agent：需要容器沙箱，需要在沙箱里跑命令行 agent | 业务 agent；和产品测试放在一起的回归评测 |
| 执行 | Inspect + inspect_swe | 参数化 pytest 用例 + xdist |
| 我们提供 | 评分器包（把我们的评分器包成 Inspect scorer）；日志接入（读 Inspect 日志，转成试验判定） | 全部 |
| 两条路径共用 | 判定（`Check`）、统计（配对比较）、基线门禁、报告、MCP | |

**为什么改**：
1. **原结论违反了我们自己的"集成，不封装"原则。** 沙箱编排、在沙箱里运行命令行 agent、记录轨迹，Inspect 和 inspect_swe 都已经做好且成熟。自研只会落后，而且还要维护。
2. **原来的理由"换成别人的运行器，判定层就没了"不成立。** 判定层可以接在 Inspect 的日志和 scorer 上，不必拥有运行器。
3. **和你的手册对齐。** 手册把 Inspect 定为主力框架，练手项目 2 本来就是用 Inspect + Docker 跑三个外壳。
4. **业务 agent 仍然走 pytest**：它们不需要容器沙箱，需要的是对话驱动和业务终态检查，这些和产品测试共用同一套能力。

## 12. 追加（2026-11-05）：分布式被测对象与规模化

起因：对"测试对象是分布式系统"和"评测要在集群上跑到几万次"两类需求，逐项核对了框架现有能力。两件事要分开看。

### 被测对象是分布式系统

已有：多服务 HTTP 测试；`that()` 跨数据源核对（写 A 节点、读 B 节点）；`concurrently()` 测竞态并判断并发是否真的发生；`@pytest.mark.resource` 互斥共享数据；归因把"连不上 / 超时"归为环境、把"答错了"归为产品缺陷。

缺口与做法：

| 编号 | 内容 | 做法 | 状态 |
|---|---|---|---|
| **D1** | **最终一致性的等待判定** `eventually(probe, within, every)` | 在截止时间内反复读，结果是一个 Check；证据写明读了几次、用了多久、依次读到了什么。`within` 进入判定清单，放宽等待时间会被 `--fail-on-weakened` 拦下 | 本轮做 |
| **D3** | **一致性检查** | `concurrently()` 已记录每个操作的起止时间，扩展为操作历史，交给现成的检查器判定线性一致或可串行化（Jepsen 一类），不自研算法 | 先出方案 |
| **D4** | **故障注入** | 集成 Toxiproxy、Chaos Mesh、`tc netem`，不自研。框架负责把"注入了什么故障"写进证据，归因据此区分"故意制造的故障"和真实的环境问题 | 先出方案，与 D3 同一里程碑 |
| D5 | 依赖环境编排 | 集成 testcontainers 或 docker compose | 按需 |
| D6 | gRPC、消息队列 | 新的协议适配，判定与证据沿用现有结构 | 按需 |
| D7 | 跨服务链路证据 | 请求带 `traceparent`，报告链接到 Jaeger / Tempo | 按需 |

### 测试自身要跑到很大规模

**调度器、消息队列、结果数据库、K8s 编排是平台的事，框架不做**（与 `16` §3 同一原则）。

- 单机内：pytest-xdist 多进程（M2a），几百到几千条用例。
