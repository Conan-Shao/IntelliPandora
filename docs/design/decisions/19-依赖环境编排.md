# 19 依赖环境编排（D5）

> 状态：**已实现**（2026-11-06），见第 7 节。`14` §12 把 D5 列为"按需"；D3、D4 合入后，用例要在本地和 CI 上起一套带 Toxiproxy、数据库、被测服务的环境，按需的条件已经满足。

## 1. 要回答的问题

一个分布式被测系统的用例，开跑前要有：被测服务、它依赖的数据库和消息队列、故障注入用的 Toxiproxy。现在这些靠用例作者自己写脚本起、自己记得关，CI 上和本地各一套。要解决的是：

- 用例能声明"我需要这套环境"，框架负责起、等它就绪、无论如何都关掉；
- 环境起不来时，归因为环境问题，而不是用例出错或产品缺陷；
- 用例失败时，报告里能看到那段时间各个服务自己的日志。

## 2. 选型

| 方案 | 形态 | 依赖 | 结论 |
|---|---|---|---|
| **docker compose（命令行）** | 用户已有的 `compose.yaml`，`up --wait` 按健康检查等就绪，`port` 查随机映射的端口，`logs --since` 取日志，`down -v` 清理 | Docker Engine 和 Compose v2（≥ 2.20，`--wait-timeout`）；外部工具，和 git、kubectl 一样由用户安装 | **采用** |
| testcontainers-python | 用 Python 代码描述容器 | 新的运行时依赖（docker SDK、wrapt 等），要按 `15` 准入 | 不采用：要把已有的 compose 文件改写成 Python；"集成，不封装" |

框架不下载、不分发 Docker 或 Compose，不钉哈希：它们是系统工具，版本由用户的环境决定，框架只检查最低版本。登记在 `docs/security/components.md` 的"外部工具"一节，写明这一点。

## 3. 接口

```python
from ipandora.core import stack

@pytest.fixture(scope='session')
def shop():
    with stack.compose('compose.yaml', wait=120) as s:
        yield s

def test_order(shop):
    base = shop.url('api', 8080)        # http://127.0.0.1:<随机端口>
```

- `compose(file, services=None, env=None, wait=秒)`：`docker compose -p <项目名> -f file up -d --wait`，产出一个 `Stack`；离开时 `down -v --remove-orphans`，异常、失败也一样。
- 项目名 `ipandora-<主机>-<进程号>-<文件名>`，同一台机器上的多次运行、xdist 的多个 worker 互不干扰（每个 worker 起自己的一套）。
- `Stack.port(service, 容器端口)` / `url(...)`：查实际映射到宿主机的端口。compose 文件里只写容器端口（`"8080"`），由 Docker 分配宿主端口，并行时不冲突。
- `Stack.logs(service=None, since=None)`：服务日志。

## 4. 保证

- **一定关掉**：`with` 退出时 `down`。进程被杀留下的项目，在这台机器上下一次起环境时清理：项目名是 `ipandora-<主机>-<进程号>-<名字>`，只清本机、进程已不在的。不在每次运行开始时清理：不用 Docker 的运行不该为此多调一次 docker。
- **起不来就是环境问题**：`up --wait` 失败（健康检查不过、镜像拉不下来、端口冲突）时抛 `StackError`，消息带标记和失败服务的最后几行日志；归因规则据此归为"环境"，高置信度。
- **失败现场**：用例失败时，框架把这条用例运行期间（从用例开始到失败）每个服务的日志存成产物，报告里列在"失败现场"下。日志按报告的规则去掉凭据。
- **没有 Docker 时跳过并说明原因**，不报成通过。本仓库的 CI 设置 `IPANDORA_REQUIRE_DOCKER`，测试里没有 Docker 就失败。

## 5. 安全

- 只执行用户自己的 compose 文件，参数由框架拼成列表，不经 shell。
- `DOCKER_HOST` 指向哪台 Docker 主机由用户决定，框架照用、不改；指向远程主机时，用 `stack.host` 写明从哪里访问映射出来的端口。
- 日志可能含凭据：存成产物前经过与报告相同的去凭据处理。

## 6. 验收

一个 compose 文件起一个带健康检查的 HTTP 服务和一个 Toxiproxy（D4 的故障注入经它作用于服务）：

1. 用例拿到随机端口访问服务，通过；离开后项目被删除。
2. 健康检查不过时，用例报错并归为"环境"，消息里有服务日志的最后几行。
3. 用例失败时，报告里有该服务在用例期间的日志。
4. 一个被杀掉的进程留下的项目，在下一次起环境时被清理。

## 7. 实现

`ipandora.core.stack`，用法见 [`docs/guide/stack.md`](../../guide/stack.md)。验收用例 `test/teststack/test_stack.py`，四条都过，另外用真实的 Toxiproxy 镜像验证了 D4 的故障注入经 compose 里的代理生效。

- 测试用的两个镜像（busybox、toxiproxy）按摘要钉住，登记在 `docs/security/components.md` 新设的"测试用容器镜像"一节；有测试核对 compose 文件里的镜像都按摘要钉住且已登记。busybox 是 GPL-2.0，不在许可证白名单内，按"只在测试里作为容器运行、不链接、不分发"单独评审接受。
- busybox 从 `mirror.gcr.io` 拉取：Docker Hub 对匿名拉取限流，在共享出口的 CI 和沙箱里会拿到 429。
- 日志按用例开始时间截取（`logs --since`），只留最后 80 行，去凭据后既存文件、也写进报告。
