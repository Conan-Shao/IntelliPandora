# 18 一致性检查与故障注入（D3 / D4 方案）

> 状态：**已确认**（2026-11-06，决定见第 7 节）。`14` 把 D3、D4 定为"先出方案，同一里程碑"，本文是那份方案。

## 1. 要回答的问题

`concurrently()`（M2b）能让 N 个操作同时发出，再由用例判定"只扣了一次款""没有超卖"。这类判定要用例作者事先想到具体的不变量。还有两类问题它回答不了：

- **D3**：并发读写的结果，和"操作一个一个按某种顺序执行"是否对得上（线性一致）；一组事务的结果，是否符合声称的隔离级别（可串行化、快照隔离……）。这要看完整的操作历史，靠人写断言写不全。
- **D4**：网络变慢、断开、被重置时，系统是否还守得住同样的不变量。故障要能注入、能撤销、写进证据，归因要能分清"故意制造的故障"和"真实的环境问题"。

两者合起来就是 Jepsen 的做法：在故障下记录历史，再用检查器判定历史。

## 2. 原则

- **集成，不自研算法**（`14` 的约定）。线性一致检查是 NP 完全问题，现成的检查器做了多年的优化；我们负责记录历史、转换格式、调用检查器、把结论变成 Check。
- **结论是确定性的**：检查器给出"符合 / 不符合 / 无法判定"。"无法判定"（超时、内存不够）记为无结论，和零判定一样不计入通过。
- **故障一定撤销**：注入放在上下文管理器里，异常、超时、进程被杀之后的下一次运行都会清理。只清理框架自己创建的东西。
- **不对生产环境注入**：环境配置里没有显式允许的，拒绝注入。

## 3. D3：操作历史与一致性检查

### 3.1 记录历史

```python
from ipandora.core import consistency

history = consistency.History()

def write(v):
    return history.call('write', v, lambda: KvApi().put('k', v), ok=lambda r: r.status_code == 200)

def read():
    return history.call('read', None, lambda: KvApi().get('k'),
                        ok=lambda r: r.status_code == 200, value=lambda r: r.json()['value'])

concurrently([lambda i=i: write(i) for i in range(5)] + [read] * 5)
assert_all(history.check('register'))
```

- 每次操作记两条：`invoke`（发出时）和完成时的 `ok` / `fail` / `info`。`info` 表示结果不确定（超时、连接断开：可能执行了，也可能没有），检查器会把两种可能都考虑进去。这是历史和普通日志的关键区别，分类由用例给出（`ok=`、`fail=`），框架不猜。
- 进程号用 `concurrently()` 的线程序号；时间用它已经记录的单调时钟起止时间。
- 历史作为证据附在用例上（JSON），报告里能看到每个操作的时间线。

### 3.2 检查器

| 检查器 | 能判定什么 | 形态 | 许可证 | 代价 |
|---|---|---|---|---|
| **elle-cli**（[ligurio/elle-cli](https://github.com/ligurio/elle-cli)） | Knossos：register、cas-register、mutex 的线性一致；Elle：list-append、rw-register 的事务隔离异常（G0、G1c、G-single……）；Jepsen：bank、counter、set | 独立 jar，命令行读 EDN / JSON 历史，输出 true / false / unknown | Elle、Knossos、Jepsen 为 EPL-1.0（**不在白名单内**，需单独评审） | 需要 JVM |
| **Porcupine**（[anishathalye/porcupine](https://github.com/anishathalye/porcupine)） | 线性一致，比 Knossos 快几个数量级 | Go 库，模型要用 Go 写 | MIT | 每种模型要一段 Go 代码，要 Go 工具链编译 |

**建议**：先用 elle-cli。一个命令行覆盖线性一致和事务隔离两类问题，模型现成，不需要我们写任何算法；框架只做"历史 → EDN → 调用 → Check"。Porcupine 留作历史规模大到 Knossos 跑不完时的第二选择。elle-cli 不是 Python 依赖，作为外部工具调用（和 git、kubectl 一样），但按 `15` 仍要准入：钉住版本和 jar 的哈希，登记，评审 EPL-1.0。

### 3.3 结论怎么进报告

- `history.check(model)` 返回一条 Check，`src='consistency'`；不符合时证据写检查器给出的反例（Knossos 的最小不可线性化片段、Elle 的异常类型和涉及的事务）。
- `unknown`：无结论，报告单独列出，不算通过也不算失败。
- 没装 JVM 或 elle-cli 时，用例跳过并说明原因（和 `web` 安装组缺失时一样），不报成通过。

## 4. D4：故障注入

### 4.1 接口

```python
from ipandora.core import faults

with faults.injected(faults.latency('orders-db', ms=800, jitter=200)):
    results = concurrently(pay_twice, n=10)
assert_all(that(charged_count(), '扣款次数') == 1)
```

- `faults.injected(*fault)` 注入、产出、无论如何都撤销；可以嵌套，也可以在 `concurrently()` 期间按时间表注入（第 N 毫秒起断开 2 秒）。
- 每个注入写进证据：什么故障、作用在哪、起止时间。报告的时间线上和请求画在一起。
- **归因**：用例的证据里有正在生效的注入时，故障时间窗内的连接错误、超时归为"按设计注入的故障"，不归为"环境问题"；判定失败（比如重复扣款）照样是产品缺陷。这是 `14` 对 D4 的要求。

### 4.2 后端

| 后端 | 能做什么 | 依赖 | 建议 |
|---|---|---|---|
| **Toxiproxy** | 延迟、带宽、超时、连接重置、半开连接，按方向、按比例 | Toxiproxy 服务（Go 二进制或容器，MIT），HTTP API 在 8474 端口；框架用已有的 requests 调用，**不加 Python 依赖** | **第一个做** |
| **Chaos Mesh** | Pod 杀死、网络分区、时钟偏移、IO 故障 | K8s 集群和 kubectl；框架生成 CRD 清单并 apply / delete（Apache-2.0） | 第二步，K8s 环境才有意义 |
| **tc netem** | 主机或容器网卡上的延迟、丢包、乱序、分区 | Linux、NET_ADMIN 权限，通常经 `docker exec` | 第三步，权限要求高 |

被测服务要经过 Toxiproxy 才能被注入：环境配置里把下游地址指向 Toxiproxy 的代理端口。框架提供 `faults.toxiproxy.proxy('orders-db', listen=..., upstream=...)` 在会话开始时创建代理。

### 4.3 安全

- 环境配置 `faults.allowed: true` 才允许注入，默认关闭；`ipandora init` 生成的 `prod` 环境写死为 false。
- 框架创建的代理和故障都带前缀（`ipandora-<run_id>-`），清理只删带前缀的；会话结束、以及下一次会话开始时都清理一遍，防止上次被杀的进程留下故障。
- 注入是进程外的、全局的（同一个代理上的所有连接都受影响），并行运行（`--workers`）时，用到同一个代理的用例自动加 `@pytest.mark.resource('fault:<proxy>')` 串行执行。

## 5. 里程碑与验收

| 阶段 | 内容 | 验收 |
|---|---|---|
| **D4a** | `faults` 接口、Toxiproxy 后端、证据、归因规则、安全开关和清理 | 一个演示服务经 Toxiproxy 访问下游；注入"连接重置"时，没有重试的用例失败并被归为"注入的故障"，有幂等重试的用例通过；进程被杀后下一次运行清理残留 |
| **D3a** | `History`、EDN 导出、elle-cli 调用、Check 与反例 | 一个故意有"读-改-写"竞态的计数器服务，`concurrently()` 下 `history.check('counter')` 判为不一致并给出反例；修好后判为一致 |
| **D3b + D4a** | 故障下的历史 | 注入延迟时，一个最终一致的 KV 服务被 `register` 模型判为不可线性化；声明为最终一致的读用 `eventually()` 判定则通过 |
| D4b / D4c | Chaos Mesh、netem | 视需要 |

每个阶段合入后照例做一次代码审查。

## 6. 需要决定的事项

1. **elle-cli 的准入**：需要 JVM，Elle / Knossos / Jepsen 为 EPL-1.0，不在许可证白名单内。作为外部工具调用、不随包分发，是否接受？不接受的话，D3 只能用 Porcupine（MIT），每种模型要写一段 Go，并要求评测环境有 Go 工具链。
2. **后端顺序**：建议 Toxiproxy → Chaos Mesh → netem。是否有已经在用的故障注入平台（公司内部的、云厂商的）需要优先接入？
3. **允许注入的环境**：默认只有本地和 CI 的测试环境；是否有共享的预发环境也要允许？
4. **先做哪一半**：建议先做 D4a（不引入任何新组件，归因规则马上就有用），D3 等第 1 条决定后再做。

## 7. 决定（2026-11-06）

| 事项 | 决定 |
|---|---|
| D3 检查器 | **elle-cli**。接受 JVM 和 EPL-1.0：作为外部工具调用，不随包分发；按 `15` 准入，钉住版本和 jar 的 SHA-256，在登记表里写明评审理由 |
| D4 后端 | **Toxiproxy 先做**（D4a）。Chaos Mesh、netem 以后视需要 |
| 允许注入的环境 | **只有本地和 CI**。共享环境（预发、生产）一律不注入；环境配置不写 `faults.allowed: true` 就拒绝 |
| 顺序 | D4a → D3a → D3b，每一步合入后做代码审查 |

## 8. 进展

- **D4a 已实现**：`ipandora.core.faults`，用法见 [`docs/guide/faults.md`](../../guide/faults.md)。与方案的差异：
  - 方案写的是"用到同一个代理的用例自动加资源锁"。收集阶段无法知道一条用例会用到哪个依赖，所以改为：注入期间持有 `fault:<代理名>` 锁；不能被故障影响的用例自己声明同名资源。
  - Toxiproxy 没有给代理或故障加元数据的地方。`down()` 停用代理时同时加一个以 `ipandora-` 开头的空故障作为标记，清理时据此重新启用。
  - 归因按时间判断：故障生效期间抛出的传输错误带标记，只有带标记的才归为"注入的故障"（CR7，`docs/design/reviews/07-CR7.md`）。
  - 测试用一个写在测试代码里的 Toxiproxy 替身（真实转发 TCP，支持延迟、重置、超时、停用）；设置 `TOXIPROXY_URL` 时同样的接口测试也对真实的 Toxiproxy 跑一遍。
- **D3a 已实现**：`ipandora.core.consistency`，用法见 [`docs/guide/consistency.md`](../../guide/consistency.md)。elle-cli 0.1.11 按 `15` 准入，登记在 `docs/security/components.md` 新设的"外部工具"一节：jar 的 SHA-256 写在代码里，每次运行前核对；CI 下载 release 的 zip，核对 zip 和 jar 两个哈希后才使用。与方案的差异：
  - "无法判定"用 gap 表示：它不是判定，只有它的用例会显示为"未判定"，不会被当成通过。
  - `info` 之后同一线程换一个新的进程号继续，这是 Knossos 的要求（一个结果不明的操作可能还在执行）。
- **D3b 已实现**：故障下的历史，用法见 [`docs/guide/consistency.md`](../../guide/consistency.md#在故障下检查)。验收用例 `test/testconsistency/test_under_faults.py`：主库立即确认写入、经 Toxiproxy 代理 `replication` 异步复制到副本，读走副本；注入上行延迟后 `cas-register` 判为不可线性化，反例写出当时生效的故障，同一个读用 `eventually()` 判定则通过。与方案的差异：
  - 3.1 写的"历史作为证据附在用例上（JSON），报告里能看到每个操作的时间线"：存的是 EDN（拿同一个 elle-cli 就能复查，报告里附了命令）和检查器的完整结论（JSON），列在用例的"操作历史"下；没有画时间线。字符串值先去掉凭据。
  - 每个操作记下发出和完成时正在生效的故障（`:faults`），由此在结论里写明"N 个操作发生在注入的故障期间"。不一致仍归为产品缺陷：故障是测试条件。
  - 实现中发现：Knossos 把读到 `nil` 当作"不知道读到什么"，和任何顺序都不矛盾，所以还没写过的键读到空这种旧值查不出来。验收用例先把初始值写进历史；`cas-register` / `mutex` 判定成立时，结论里写明有几个读到空值、没有据此判定。
