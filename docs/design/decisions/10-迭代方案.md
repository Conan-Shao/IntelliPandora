## 第二期：测试能力拓展

### 现在能测什么

断言层的 `Source` 维度已经把「测了哪一面」编码进了每一条判定：

```
api      接口答了
schema   结构对
derived  业务结果对
authz    权限对        ← 已定义，尚无人产出
onchain  链上状态对    ← 已定义，只在 gap() 里用过
diff     与基线一致
```

这不是装饰。报告里的 `by_source` 会直接暴露「这套用例只会检查接口答没答」——一个全是 `api` 的套件，测的是端点活着，不是它对。

### 要补的

**UI。** 规划写「对于产品/业务系统的测试，如接口/UI 等」，而仓库零 UI 能力。做法不是把 Playwright 塞进框架，而是让 UI 驱动成为 `core/protocol/` 下与 `http/` 并列的一层，共用同一套东西：

- 同一个 `Check` / `assert_all` / `gap`——UI 断言也该是「收集后一次性抛」而不是第一个失败就停
- 同一个 evidence recorder——UI 的证据是截图和 DOM 快照，模型一样
- 同一个 report / JUnit XML——CI 不该为 UI 另开一条管线
- 同一个 triage——「元素找不到」是 `harness` 还是 `defect`，这个判定逻辑是共用的

**其他协议。** gRPC / WebSocket 按业务需要排，机制同上。`websockets` 依赖先删掉，要用时再加回来并真的用。

**业务语义层**（Flow / Invariant / 账号池）仍卡真实业务域输入，照原规划。

## 第三期（前瞻）：agent 测试能力

这一层的对象不是接口和页面，是**一个会自己做决定的系统**。它和前两期最大的差别：**同样的输入，两次运行可以给出不同且都正确的输出**。断言「返回值等于 X」在这里直接失效。

### 三件事决定这层能不能立住

**1. 判定方式要从「相等」换成「满足」。**

断言层现成的两个东西正好对上：

- `Check` 是**值**不是异常——一条 agent 轨迹可以同时产出「意图识别对了」「但多调了一次工具」「没有越权」三条独立判定，`assert_all` 一次全报，而不是在第一条停下。
- `gap()` 声明「这里应该有判定而现在没有」——评测 agent 时大量维度一开始没法自动判，`gap()` 让这些空缺**出现在报告里而不是消失**。

缺的是两类新 `Source`：

```
intent     意图识别对不对
trajectory 工具调用序列合不合理（多调、漏调、死循环）
```

**2. 用户得是模拟出来的。** 单轮输入评不出「中途改主意」「取消」「追问」。规划里引的 τ²-bench 就是这个路子：模型扮演用户，多轮交互后判终态。

**3. 判分必须在沙箱外。** 这一条属于安全，见下。

### 和 LLM 成本边界的关系

`03-LLM接入边界.md` 定的是「LLM 只在编写时和运行后，绝不在运行时」。

**评委模型属于运行后**，所以评测层不违反这条约束，**不需要改架构**。但有一条要补进边界文档：评测层的 LLM 调用量随**数据集规模**增长，而不是随测试规模增长——跑 10000 次业务用例仍然是 0 次调用，跑一次 50 题的评测集是 50 次。这两件事要分开记账，否则「成本不随测试规模增长」这句话会被误读。

## 安全：两个方向，不要混为一谈

### 方向一：测试框架自身的安全（防投毒）

**威胁模型**：谁能让一次测试**报出与事实不符的结果**？

框架已经做对的：

| | 现状 |
|---|---|
| YAML 加载 | 两处全是 `yaml.safe_load` ✅ |
| 反序列化 | 无 `pickle` ✅ |
| 动态执行 | 无 `eval` / `exec` / `os.system` / `shell=True` ✅ |
| 子进程 | `src/` 零 `subprocess`；MCP 的 `run_tests` 走库调用而非 shell ✅ |
| 磁带路径穿越 | `_blob_file` 拒绝含 `/` `\` 的 ref ✅ |
| 凭据 | 写入时脱敏；密钥 `~/.ipandora/crypto`，0700/0600 ✅ |

**已查出的缺口**：

**(a) 磁带回放零完整性校验。** blob 以 `sha256-<hash>` 命名，但 `get_blob()` 读文件后**不验证内容是否真的哈希到那个值**：

```python
def get_blob(self, ref):
    _file = self._blob_file(ref)      # 路径校验有
    with open(_file, 'r', encoding='utf-8') as fh:
        return fh.read()               # 内容校验没有
```

后果具体：能写 `~/.ipandora/cassettes` 的人，或者提供一份 HAR 让你导入的人，可以让套件**对着从未出现过的响应跑绿**。磁带的 `recorded_from` 是自由文本，没有签名也没有校验和。

这正是本仓库反复出现的那个形状——**失败长得和成功一模一样**。修法很便宜：读时验哈希，不符就拒绝并指名磁带。

**(b) 供应链面是白送的。** 7 个从未被 import 的依赖，每一个都是安装期执行代码的机会，换来零收益。这和「版本锁死」是同一件事的两半：先删掉不需要的，再锁住需要的。

**(c) 测试文件本身是可执行代码。** 这是测试框架的固有属性，消不掉——`pytest` 导入用例就是执行它。能做的是让**改动可见**：规划阶段 3 的「用例文件的改动单独 review，防止 agent 为了变绿去改断言」正是这条的对策，属于流程不属于代码。

**(d) 评测时的隔离。** 规划的安全要求已写清：agent 只在 Docker 里跑、不挂载本机目录、私钥不进 agent 能读到的环境、**判分脚本和隐藏测试放在沙箱外**。

有一条要说明白：`08` 那轮把密钥移到了 `~/.ipandora/crypto`（0700/0600），解决的是「密钥被提交进公开仓库」。**它不满足「agent 读不到」**——同一用户下运行的 agent 完全读得到那个目录。要达到规划的标准，得走签名服务 + 额度那条路，密钥根本不在 agent 的文件系统视野里。

### 方向二：对被测系统的安全测试能力

这是**测试能力**，不是框架自身加固，两者不该混在一起讲。

断言层已经留好了挂点：**`Source.AUTHZ` 已定义但至今无人产出**。也就是说，「这条判定检查的是权限」这个概念框架已经认识，只是还没有谁去产出这类判定。

可以长出来的能力，按与现有机制的贴合度排：

| 能力 | 怎么长在现有机制上 |
|---|---|
| **越权检测**（水平/垂直） | 用账号池取两个不同权限的账号跑同一条 Flow，比对结果 → 产出 `Source.AUTHZ` 的 Check。依赖账号池（第二期） |
| **敏感信息回流** | 证据采集已经记下每个响应体，而 `redact.py` 已有一套凭据形状正则。把「脱敏命中」从**遮蔽动作**改成也产出一条**判定**：响应里出现凭据形状 = 一条失败的 Check |
| **契约层面的安全** | schema 校验已有。补「响应里不该出现的字段」这类否定式断言 |
| **重放与幂等** | 磁带已经能重放一次请求。重复提交是否被正确拒绝，是现成能测的 |
| 注入类扫描（SQLi/XSS 等） | 属于专用扫描器的地盘，框架该做的是**接入并把结果变成 Check**，而不是自己实现扫描器 |

一条设计约束：安全测试的结论必须和功能测试走**同一条报告与归因管线**。另开一份安全报告，等于没人看。

## 排期与依赖

```
第一期（整改）        ────────────  不依赖任何外部输入，可立即全部完成
第二期（能力拓展）
  ├─ UI 驱动          ────────      不卡业务域，卡的是选型与人力
  └─ Flow/Invariant/账号池  ░░░░░░  卡真实业务域的接口与测试环境
第三期（agent 评测）         ░░░░░░  卡数据集、链上环境、模型通道审批
安全
  ├─ 框架加固         ──            磁带校验 + 依赖清理，小且立即可做
  └─ 被测系统安全测试      ░░░░      越权检测卡账号池；敏感信息回流不卡
```

**不卡任何外部输入、现在就能做的**，按优先级：

1. 第一期全部 7 项
2. 磁带读时验哈希（框架加固里唯一有实证缺口的一条）
3. 敏感信息回流检测（复用现有脱敏正则，把遮蔽改成也产出判定）
4. UI 驱动的接入层设计（选型可以先定，不必等业务域）

**卡外部输入的**，照原规划，不在这份方案里重复排期。
