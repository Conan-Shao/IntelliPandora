# 17 · 登录态与用例组织

> 2026-11-05 · 方案，含自审（§4）和对照代码实测的第二轮评审（§7）；实现排进计划（§6）。

两个问题：

1. 接口测试要 token，UI 测试要 cookie。登录态怎么拿、怎么保持、怎么在并行和多角色下不出错？
2. 用例和用例库怎么组织？样例里接口定义和用例写在一个文件里，合不合适？UI 自动化又该怎么组织？

## 1. 现状（核对过代码）

| 事实 | 位置 | 影响 |
|---|---|---|
| HTTP 会话按**线程**区分，一个线程一个 `requests.Session`，cookie 自动保留 | `core/schedule/session.py` | 同一线程里登录一次，后续请求自动带 cookie；但**一个线程只有一个身份**，同一条用例里切换买家和卖家只能手工换 header |
| `concurrently()` 会复制调用方的会话（header、cookie、auth） | `SessionManager.clone` | 并发请求带着登录态出去，这个已经对了 |
| 端点和 token 写在 `ENDPOINTS` 变量里，由插件提供 | `utils/variable.py`、`docs/guide/config.md` | **token 只是存着，没有任何代码把它放进请求**；要用户自己写请求插件 |
| 请求插件可以改每个请求 | `PluginInterface.request` | 签名类鉴权（每个请求现算签名）可以挂在这里 |
| 报告对 `Authorization`、`Cookie`、`Set-Cookie` 头和 `token` 等字段脱敏 | `core/report/redact.py` | 登录接口的响应体里的 token 不会进报告 |
| Web 只把 `web.base_url` 等映射成 pytest-playwright 的选项，**没有登录态** | `core/web.py` `ContextDefaults` | 每条 UI 用例都要自己登录，慢，而且容易被登录频率限制 |
| 样例：接口类和用例函数写在同一个文件，`base_url` 经 `other_params` 传进路径 | `templates/project/tests/test_example.py.tmpl` | 接口类没法被别的用例、UI 用例的造数复用 |

## 2. 登录态

### 2.1 三个概念

- **身份**（identity）：用例里说的"谁"，比如 `buyer`、`seller`、`admin`、`anonymous`。只是名字，不含凭据，可以出现在用例、报告、日志里。
- **凭据**（credential）：身份在被测系统里的通行证：token、cookie、API key、签名密钥、客户端证书。只出现在请求里，报告里脱敏。
- **提供者**（provider）：怎么为一个身份拿到凭据，在 `conftest.py` 里用 Python 写，因为每个系统的登录方式都不一样。

用例只写身份，不碰凭据：

```python
def test_buyer_cannot_see_other_orders():
    with identity('buyer'):
        r = OrderApi().get(order_of('seller'))
    assert_all(status_is(r, 403))
```

### 2.2 凭据形态与做法

| 形态 | 例子 | 怎么放进请求 | 过期 |
|---|---|---|---|
| Bearer token | 登录接口返回 JWT | `Authorization: Bearer …`，放在该身份的会话头里 | 提供者返回过期时间；提前刷新 |
| 会话 cookie | 登录后服务端 `Set-Cookie` | 登录请求就用该身份的会话发，cookie 自动留在会话里 | 服务端决定；遇到 401 重新登录 |
| API key | 固定 key，放头或查询参数 | 会话头或 `params` | 不过期 |
| 请求签名 | HMAC(时间戳 + 路径 + 体) | 每个请求现算，挂在请求插件上 | 每次都新算 |
| OAuth2 client credentials | 服务间调用 | 提供者向令牌端点要 token，同 Bearer | 同 Bearer |
| 客户端证书 | mTLS | `session.cert` | 证书有效期 |

### 2.3 生命周期

| 规则 | 理由 |
|---|---|
| **用到时才登录**，每个进程每个身份一次 | 不用的身份不登录；登录接口常有频率限制 |
| **提前刷新**：剩余有效期不到 60 秒，或不到总有效期的五分之一（取较小者），就重新获取 | 长套件跑到一半 token 过期，是"偶发 401"的主要来源；有效期很短的 token 不能一直处在刷新中 |
| **判定为"未登录"时重新获取一次，并重放这一个请求一次**；重放后仍未登录就照实返回 | 未登录表示请求被拒、没有被处理，重放安全；两次请求都进报告证据 |
| "未登录"默认指 HTTP 401；**提供者可以自己定义判断**，例如 HTTP 200 加业务码 `code=401` | 很多系统用业务码表示登录失效，只认 401 会让刷新永远不发生 |
| 请求体是文件或流时不重放，照实返回第一次的结果 | 流已经被读过一次，重放会发出空的请求体 |
| 有刷新令牌（refresh token）的，提供者可以实现 `refresh()`，否则重新登录 | 刷新比重新登录快，也不触发登录频率限制 |
| **只对提供者管理的身份刷新**。用例自己构造的凭据（比如故意传过期 token）从不刷新 | 否则"过期 token 应返回 401"这类用例会被框架悄悄修好 |
| `anonymous` 身份不带任何凭据 | 未登录访问要能测 |
| 一次运行结束时清空缓存 | MCP 服务是常驻进程，上一次运行的 token 不能带到下一次 |

**并行**（xdist 多进程）：

- 默认每个 worker 进程各登录一次。
- **单会话账号**（同一账号在别处登录会把前一个踢下线）：在身份上声明 `single_session=True`，所有 worker 共用一份凭据。第一个 worker 登录后，把凭据写进这次运行的私有目录（权限 0600），其他 worker 读它；读写用已有的文件锁（`ResourceLock`）保护。
- **账号池**：一个身份配多个账号（`buyer` → `buyer01…buyer08`），每个 worker 租用一个，数据互不干扰。这也是 Playwright 推荐的"每个并行 worker 一个账号"。账号不够分时，借用 `@pytest.mark.resource` 的排队机制。

**同一账号既用接口登录又用页面登录**，在单会话系统里也会互相踢下线：这种账号的 Web 登录态用接口登录转换（§2.5），或者给 Web 单独配账号。

**跨运行缓存**默认关闭：凭据落盘有泄露风险，过期凭据也会让结果依赖上一次运行。本地调试可以用 `auth.cache: persistent` 打开，凭据存 `~/.ipandora/auth/<env>/`（0600，带过期时间）。

### 2.4 和现有机制的结合

- **会话**：从"每线程一个会话"改为"每线程每身份一个会话"。`identity('buyer')` 切换当前线程的活动会话；不指定时是 `default` 身份，现有用例行为不变。
- **`concurrently()`**：已经复制当前会话，复制的就是当前身份的会话，并发请求带同一身份。
- **证据**：每次请求的证据里记下身份名（不记凭据）。越权类失败一眼能看出是谁发的请求。提供者在用例里触发的登录请求也进证据，标为"登录"，和用例自己的请求分开显示。
- **凭据文件不进报告目录**：跨 worker 共享的凭据和浏览器登录态放在单独的私有临时目录（0700），不放在报告或失败现场的目录里，因为 CI 会把那些目录作为制品上传。
- **归因**：提供者抛出的登录失败归为"测试数据"（账号或口令不对），登录接口连不上归为"环境"，都不算产品缺陷。
- **凭据来源**：口令只从环境变量或不提交的 `conf/local.yaml` 读（`auth.secret('BUYER_PASSWORD')`）。`ipandora init` 生成的 `.gitignore` 加上这两项。

### 2.5 Web：同一个身份，变成浏览器的登录态

浏览器的登录态就是 Playwright 的 `storage_state`：cookie 加 localStorage，可选 IndexedDB。获取方式两种，提供者选一种：

| 方式 | 做法 | 适合 |
|---|---|---|
| **接口登录**（推荐） | 用该身份的 HTTP 会话登录，把会话里的 cookie 用 `context.add_cookies()` 放进新的浏览器上下文 | 登录走接口、凭据在 cookie 里的系统。最快，不打开登录页。不经 `storage_state` 文件，因为 requests 的 cookie 不带 SameSite，按 `web.base_url` 补全域名和路径 |
| **页面登录** | 每个身份在每个 worker 里用浏览器登录一次，`context.storage_state()` 存下来复用 | 只能走页面登录（SSO 跳转、token 存在 localStorage 的单页应用） |

用法：

```python
def test_buyer_pays(page_as):
    page = page_as('buyer')              # 带 buyer 登录态的新页面
    page.goto('/orders/7')
    page.get_by_role('button', name='付款').click()
    expect(page.get_by_text('支付成功')).to_be_visible()

def test_seller_sees_the_payment(page_as):
    buyer, seller = page_as('buyer'), page_as('seller')   # 一条用例两个角色，两个独立的上下文
```

- `page_as` 用 pytest-playwright 的 `new_context` 建上下文并传入 `storage_state`，**不靠覆盖 `browser_context_args`**：按用例覆盖它传 `storage_state` 有已知问题（playwright-python #2151，只有第一条用例是登录状态）。
- **限制要写进手册**：`storage_state` 不保存 sessionStorage；token 存在 sessionStorage 的应用，提供者要在页面打开前用初始化脚本写回去。token 存在 IndexedDB 的（例如 Firebase），保存时加 `indexed_db=True`（Playwright 1.51 起）。
- 接口和页面共用同一个身份：用接口给 `buyer` 造数，再用 `page_as('buyer')` 在页面上检查。
- **怎么知道"已登录"**：提供者声明一个检查，登录页的 URL 规则或一个只有登录后才有的元素。`page_as` 打开页面后做这个检查，被跳回登录页就重新获取一次并重开页面；仍然失败就判为"测试数据"问题。没声明检查的，`page_as` 不做这一步，手册里说明这样发现不了"登录了但页面没登录"。
- **反方向也要支持**：只能在浏览器里完成的登录（SSO、OAuth 授权码），登录后从浏览器上下文取出 cookie 或 localStorage 里的 token，交给同一身份的 HTTP 会话，接口用例也能用。
- **trace 里有凭据**：Playwright 的 trace 记录网络请求的头和体，没法脱敏。失败现场的 trace 和截图只应作为私有制品保存；对敏感环境可以用 `web.trace: off` 关掉。

### 2.6 不做的

- **不破解验证码和 MFA。** 测试环境给测试账号关掉，或者提供者用 TOTP 种子现算验证码（种子按凭据管理）。
- **不自己实现 OAuth 授权码的浏览器流程。** 用页面登录方式走一遍，或者在测试环境用 client credentials。
- **App（M5）先只预留。** 同一个身份模型，凭据怎么注入 App 到 M5 再定。

## 3. 用例组织

### 3.1 接口定义和用例要分开

样例把接口类和用例写在同一个文件里，只适合"一个文件就能看完"的演示。实际项目里应该分开：

| 写在一起的问题 | 分开以后 |
|---|---|
| 同一个接口被几十条用例调用，每个文件各写一份，接口一改要改很多处 | 接口在 `apis/` 只写一次 |
| UI 用例要用接口造数，只能复制接口代码 | UI 用例直接 import `apis/` |
| 接口类里混进判定，用例看不出自己在判什么 | 判定只在 `tests/`，用例读起来就是需求 |
| 接口类里的 `test_` 方法、`self` 状态会被 pytest 收集，生命周期混乱 | 接口类不含测试，用例是普通函数 |
| 代码审查分不清"接口改了"和"判定改了" | 两类改动在不同目录，`CODEOWNERS` 可以分别指定负责人 |

用例写成**函数**，不写成类；只有需要共用 fixture 或标记时才用类分组。

### 3.2 目录结构

```
my-tests/
├─ conf/
│  ├─ config.yaml          公共配置                                   提交
│  ├─ staging.yaml         环境：服务地址、账号名（不含口令）            提交
│  ├─ local.yaml           本机覆盖与口令                              不提交
│  ├─ judgements.json      判定基线                                    提交，CODEOWNERS
│  └─ eval_baseline.json   评测基线（有评测时）                         提交，CODEOWNERS
├─ apis/                   接口层：每个服务一个模块，每个资源一个类，每个接口一个方法。不写判定
│  ├─ auth.py
│  └─ orders.py
├─ pages/                  页面层：每个页面或组件一个类，提供定位器和操作。不写判定
│  ├─ checkout.py
│  └─ components/cart.py
├─ flows/                  业务步骤：组合接口完成多步造数（下单 → 支付），接口用例和 UI 用例共用
├─ data/                   造数工厂、参数化数据（YAML / CSV）、JSON Schema
├─ tests/
│  ├─ api/orders/test_refund.py
│  ├─ web/checkout/test_pay.py
│  └─ conftest.py          身份、客户端、页面的 fixture
├─ conftest.py             身份提供者的注册
├─ pytest.ini              pythonpath = .（见 §7 第 1 条）
├─ AGENTS.md
└─ .github/{workflows/tests.yml, CODEOWNERS}
```

### 3.3 各层的规则

| 层 | 做什么 | 不做什么 |
|---|---|---|
| `apis/` | 声明接口：路径、方法、参数；返回响应 | 不判定，不登录（登录在提供者里），不写死地址（地址来自 `conf/<env>.yaml`） |
| `pages/` | 定位器（优先 `get_by_role` / `get_by_label` / `get_by_test_id`）和操作（`pay()`、`add_to_cart(sku)`）；可以等页面加载完 | 不判定。等待用 Playwright 的自动等待，不 `sleep` |
| `flows/` | 多步造数，返回造出来的数据 | 不判定；造数失败用 `require()` 报前置条件不满足，而不是让用例失败 |
| `data/` | 工厂函数为每条用例生成唯一数据，方便并行 | 不放口令 |
| `tests/` | 一条用例一个行为；第一行文档字符串是标题；`assert_all` / `expect` 做判定；`require` 做前置；`gap` 声明没测的；`@pytest.mark.dims` 落进覆盖矩阵 | 不直接调 `requests`，不 `sleep`（用 `eventually`），不在用例里拼 URL |

**为什么判定只放在 `tests/`**：判定清单在运行时记录，写在页面类里的 `expect` 也会被记下，不会漏。但判定放在用例里，读用例就知道它在验证什么；评审判定的改动也只用看 `tests/` 的 diff。

### 3.4 用例模板

接口用例：

```python
from apis.orders import OrderApi
from flows.orders import paid_order
from ipandora.core.assertion import assert_all, field, status_ok


@pytest.mark.dims(role='buyer', channel='api')
def test_refund_of_a_paid_order_returns_the_full_amount():
    """已支付的订单全额退款，退款金额等于实付金额"""
    order = paid_order(identity='buyer', amount='100.50')          # 造数
    with identity('buyer'):
        r = OrderApi().refund(order.id)                            # 动作
    assert_all(                                                    # 判定
        status_ok(r),
        field(r, 'data.refund_amount').decimal() == order.amount,
        field(r, 'data.status') == 'REFUNDED',
    )
```

Web 用例：

```python
from pages.checkout import CheckoutPage


@pytest.mark.dims(role='buyer', channel='web')
def test_paying_shows_the_success_page(page_as):
    """付款成功后显示成功页，金额与订单一致"""
    order = paid_order(identity='buyer', pay=False)
    checkout = CheckoutPage(page_as('buyer')).open(order.id)
    checkout.pay()
    expect(checkout.result).to_have_text('支付成功')
    expect(checkout.amount).to_have_text(order.amount)
```

### 3.5 数据驱动：用 Python 写用例，用数据文件给参数

不做 YAML 用例 DSL。用 YAML 写步骤，等于发明一门更弱的编程语言：判定只能用预设的几种，调试、重构、IDE 支持都没有，agent 写 Python 也比写自定义 DSL 可靠。而且判定清单、零判定检测都基于 Python 的运行时记录。

同一个行为要用很多组输入时，用参数化，数据放在 `data/`：

```python
@pytest.mark.parametrize('case', cases('data/refund_amounts.yaml'))
def test_refund_amount(case):
    ...
```

`cases()` 是要加的小工具：读 YAML / CSV，每行变成一个 `pytest.param`，`id` 取自数据里的 `id` 字段，`dims` 字段直接转成覆盖矩阵的标记。

### 3.6 Web：Page Object 要不要

要，但要薄：页面类只放定位器和操作，判定留在用例里；一个页面里重复出现的部分（购物车、导航）做成组件类。Playwright 官方对 Page Object 的建议也是这样。不推荐更重的 Screenplay 模式，它在 pytest 里的收益抵不上多出来的抽象。

框架的定位器记忆（`core/web.py`）对任何选择器都生效；用 `get_by_role` 时，选择器失效的判断最准，因为记下的就是角色和名称。

## 4. 自审

| # | 风险 | 处理 |
|---|---|---|
| 1 | 401 自动重放会把"token 过期应该被拒"这类用例悄悄修好 | 只对提供者管理的身份刷新；用例自己构造的凭据从不刷新；重放前后两次请求都进证据 |
| 2 | 401 重放非幂等请求（POST 下单）有重复提交的担心 | 401 表示请求被拒、没有被处理，重放一次是安全的；可以按身份关掉（`refresh_on_401=False`） |
| 3 | 单会话账号在并行时互相踢下线，表现为随机 401 | `single_session=True` 让所有 worker 共用一份凭据，或者配账号池 |
| 4 | 凭据落盘泄露 | 默认只在内存；跨 worker 共享时写进这次运行的私有目录（0600），运行结束删除；跨运行缓存必须显式打开 |
| 5 | 登录接口被并行登录压垮或触发限流 | 每个进程每个身份只登录一次；单会话或共享模式下整个运行只登录一次 |
| 6 | MCP 常驻进程把上一次运行的 token 带到下一次 | 运行结束清空身份缓存，和清理测试模块的机制放在一起 |
| 7 | sessionStorage 里的 token 不会被 `storage_state` 保存 | 手册写明；提供者用初始化脚本写回 |
| 8 | 把接口登录拿到的 cookie 转成浏览器 cookie 时，域名或路径不对，表现为"登录了但页面还是未登录" | 转换时按 `web.base_url` 补全域名；`page_as` 打开页面后检查是否被跳回登录页，被跳回就报"测试数据"问题，不让用例在未登录状态下继续跑 |
| 9 | "判定只在 `tests/`"没有门禁，只是建议 | 加可选检查 `ipandora check layout`：`apis/`、`pages/`、`flows/` 里出现判定时给出警告；AGENTS.md 模板里的规则和这个检查对应 |
| 10 | 目录结构是建议，老项目不一定能照搬 | 框架不依赖目录名；`ipandora init --layout full` 生成完整结构，默认的最小结构保持现状 |

## 5. 和已有计划的关系

- 不改变判定、报告、并行的任何结论；身份只是选择用哪个会话。
- `concurrently()`、证据、脱敏、归因都只需要小改。
- E0/E1 的评测里，业务 agent 走 pytest 路径（E2），同样用身份模型。

## 7. 第二轮评审：对照代码实测

第一轮自审（§4）只看方案本身。第二轮逐条核对方案依赖的代码行为，能跑的就跑。

| # | 发现 | 怎么核实的 | 改动 |
|---|---|---|---|
| 1 | **分层以后 `ipandora run` 导入不到 `apis/`。** 运行器用 `--import-mode=importlib`，它不把项目根目录放进 `sys.path`。在项目根目录用 `python -m` 跑能过，只是因为 `-m` 碰巧把当前目录加了进去；用 `ipandora run` 或在别的目录跑，就报 `No module named 'apis'` | 建了 `apis/` + `tests/` 的最小项目，两种方式各跑一次；加上 `pytest.ini` 的 `pythonpath = .` 后，两种方式都通过 | 目录结构加 `pytest.ini`；L1 的生成器带上它，并在收集错误里给出提示 |
| 2 | **表单格式的请求体不脱敏。** `username=alice&password=hunter2` 原样进报告。JSON 体按字段名脱敏，表单体只做了值形状的匹配，认不出 `password` | 直接调用 `redact_body` | 新增 A0，排在最前 |
| 3 | 401 重放对文件上传、流式请求体不安全 | 读 `RequestWrapper` 的参数传递：文件对象原样交给 requests | §2.3 加"请求体是文件或流时不重放" |
| 4 | 很多系统用 HTTP 200 加业务码表示登录失效，只认 401 的刷新永远不会触发 | 方案假设，不需要实测 | §2.3 加"提供者可以自定义未登录的判断" |
| 5 | 接口登录拿到的 cookie 转成浏览器登录态时，requests 的 cookie 不带 SameSite，直接写成 `storage_state` 文件可能被浏览器拒绝 | 对照 Playwright 的 cookie 字段 | §2.5 改为用 `add_cookies()`，按 `web.base_url` 补全域名和路径 |
| 6 | "被跳回登录页"没有通用的判断方法 | 方案假设 | §2.5 改为提供者声明登录检查；没声明的，手册说明后果 |
| 7 | 只能在浏览器里完成的登录（SSO），接口用例拿不到凭据 | 方案遗漏 | §2.5 加"从浏览器取凭据给 HTTP 会话" |
| 8 | 凭据文件和浏览器登录态如果放进报告目录，会随 CI 制品一起上传 | 核对报告目录与失败现场目录（`IPANDORA_ARTIFACTS_DIR`）的用途 | §2.4 规定放在单独的私有临时目录 |
| 9 | Playwright trace 记录请求头和请求体，里面有 token 和 cookie，而且没法脱敏。这个风险现在就存在，登录功能会让它更常见 | 核对 `web.pytest_args` 默认打开 `--tracing retain-on-failure` | §2.5 写明；计划在 A3 加 `web.trace` 开关 |
| 10 | 单会话账号同时用接口登录和页面登录，同样会互相踢下线 | 方案遗漏 | §2.3 写明做法 |
| 11 | 提供者在用例里触发的登录请求会进这条用例的证据，第一条用到该身份的用例会显得多了一次请求 | 核对证据记录器：用例执行期间的请求都会被记录 | §2.4 规定登录请求进证据但单独标出 |
| 12 | 有效期很短的 token（例如 30 秒）配上固定 60 秒的提前量，会一直处在刷新中 | 方案假设 | §2.3 改为"60 秒或有效期的五分之一，取较小者" |

确认成立、不需要改的：

- `concurrently()` 复制的是调用线程当前的会话（`SessionManager.getSession()`），改成按身份区分会话以后，复制的就是当前身份的会话，不用另外改。
- 请求头里的 `Cookie`、`Set-Cookie`、`Authorization` 已经脱敏（实测）。
- 并发线程里可以各自 `with identity(...)`，因为身份按线程切换，"两个买家同时抢购"这类用例写得出来。
- pytest-playwright 的 `new_context` 可以按上下文传参数，`page_as` 用它，不依赖有已知问题的按用例覆盖 `browser_context_args`。
