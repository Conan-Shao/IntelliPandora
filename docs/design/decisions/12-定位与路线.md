# 定位与路线：可信判定 + 开箱全栈

> 2026-11-05 · 接替 `10-迭代方案.md` 里第二期之后的排期。第一期整改已完成；本文定下框架的两条腿、一条设计原则，以及接下来五步的路线。

## 1. 两条腿

为什么用户不直接用 pytest？两个理由，缺一个都立不住：

| | 解决什么 | 对谁有用 | pytest 生态里有没有 |
|---|---|---|---|
| **开箱的全栈方案** | 装上就能测 HTTP、Web、App，配置、证据、报告、归因都已就位 | 让团队愿意采用 | 没有。要自己把 requests、Playwright、uiautomator2、Appium、报告、配置拼起来，每个团队拼一遍，拼出来的还各不一样 |
| **可信的判定** | 这次通过可不可信：验证了什么、没验证什么、比上次少验证了什么、失败该谁修 | 让人在 AI 时代离不开 | 没有。pytest 的断言是异常，通过的断言不留记录，结构上就答不了 |

单有第一条，就是又一个"一整套"框架，Robot Framework、Karate、Airtest 都是这个定位。单有第二条，只是一个 pytest 插件。两条合起来是：**全栈是可信判定的覆盖面**。别人的一整套是"什么都能测"，我们的一整套是"什么都能测，而且每一端的绿灯都同样可信"。

论证和资料来源见 [`docs/guide/why.md`](../../guide/why.md)。

## 2. 设计原则：集成，不封装

全栈不等于把每个驱动重新包一层。

**为什么不封装**：

1. **agent 最会写的是公开 API。** Playwright、uiautomator2 在训练数据里大量出现，而我们自造的 `click_element(locator)` 一次都没出现过。封装层会让 agent 写得更差，还得先学我们的 API。
2. **封装层永远落后于上游**，而且只能提供各家驱动的最小公倍数。用户一碰到天花板，就会绕回原生 API，封装层反而成了负担。Selenium 换成 Playwright 时，所有包装 Selenium 的框架都得跟着重写。
3. **组装本身在贬值。** 以前搭好 pytest 加 Playwright 要人花几天，现在 agent 几分钟就搭好。不能被 agent 轻易替代的，是贯穿各端的统一判定语义。

**所以框架只提供驱动不管的那部分**：

| 框架提供 | 原样使用驱动 |
|---|---|
| fixture 给出 `page` / `device`；生命周期、超时、重试策略和 HTTP 层一致 | 点击、输入、定位、等待：直接用 Playwright / uiautomator2 / Appium 的 API |
| 配置统一放在 `conf/<env>.yaml`：base_url、浏览器、设备序列号、包名 | 不发明 DSL 或关键字语言 |
| 失败时自动采集证据：截图、Playwright trace、logcat，挂进同一份报告 | |
| 同一套判定：`field` / `that`、判定清单、基线门禁，在三端用法完全一样 | |
| UI 专属归因：元素找不到时，先在页面或控件树里找同名元素——找到了说明只是选择器过时，算用例问题；找不到则可能是产品缺陷，标为"待确认"，不武断地算成用例问题 | |
| 按需安装：`[web]` `[android]` `[ios]` `[visual]`，内核仍是 8 个依赖 | |

每一块的选型与技术方案见 [`14-技术方案与实施计划.md`](./14-技术方案与实施计划.md)。

**为什么把并发提到 Web 之前**：并行跑用例要改的是 runner 的核心——判定和证据怎么从 worker 回到主进程。Web 要按 worker 分浏览器上下文，App 要管设备池，agent 验证要把一个任务跑 k 次，这些都建在它上面。先做它，后面每一层就不用再返工一次。

第 1 步的实现见 §7。

## 4. 图像维度的判定

断言层现在适合接口和数据。UI 需要补上"看起来对不对"这一维，但必须守住一条线：**运行时的判定保持确定性，不调 LLM / VLM。** "让模型看图说对不对"既不可复现，又按张计费，而且会被说服，所以它不能做裁判。VLM 可以用在编写时（帮忙圈出动态区域）和运行后（解释一张差异图为什么不同），这和 LLM 的成本边界一致。

| 判定 | 做法 | 适合 |
|---|---|---|
| **与基准图一致** | 逐像素比对，可设容差：单像素色差阈值 + 允许的差异像素比例；支持遮罩，盖住时间戳、广告、头像这类动态区域；也可以只比某个元素的截图 | 视觉回归：改样式之后页面有没有被改坏 |
| **感知相似** | 感知哈希 / SSIM，对抗锯齿、字体渲染的细微差别不敏感 | 跨设备、跨分辨率比对 |
| **布局关系** | 元素的包围盒：可见、在视口内、不被遮挡、A 在 B 左边、间距不小于 N | 响应式布局、"按钮被挡住了" |
| **可访问性** | 文字与背景的对比度（WCAG 公式，确定性） | 合规检查 |
| **OCR 文本** | 本地 OCR 引擎；固定引擎版本，结果就是确定的 | Canvas、Flutter、游戏这类拿不到文本节点的界面 |

**基准图和判定基线走同一套流程**：基准图放在仓库里，用 `--update-baseline` 更新，PR 里就能看到图片的 diff；判定清单里记一条 `screen 'checkout' matches golden <sha>`，基准图被换掉也会被标出来。所以 agent 没法悄悄换一张基准图让测试变绿。

**接口形态**（草案）：`that(page.screenshot(), '结算页').matches_golden('checkout', tolerance=0.001, mask=[...])`。输入是 PNG 字节，所以 Playwright、uiautomator2、Appium 的截图都能直接用，不依赖具体驱动。失败时报告里并排展示基准图、实际截图和差异图。依赖 Pillow，作为可选的 `[visual]` 安装；OCR、OpenCV 再单独分出 extra。

## 5. 报告产出优化

现在的报告已经有：判定、证据、归因、覆盖矩阵、未覆盖点、判定变化。接下来按读者分三层：

| 读者 | 要什么 | 补什么 |
|---|---|---|
| **决策者**（PR 评审人、发版负责人） | 一眼看出能不能放行，以及为什么 | 首屏一张"可信度"卡片：结果、判定强度（和基线比）、零判定数、未覆盖数、产品缺陷数；用一句话结论代替一堆数字 |
| **排障者**（开发、测试） | 失败的现场 | UI 失败时并排展示截图、trace、差异图；接口失败时可复制 curl（已有）；和上次运行对比，指出"这次新红的"；按归因分组 |
| **agent** | 精简、结构化、可行动 | JSON 里每条失败带上 `next_step`（已有）；判定变化、零判定以列表形式给出（本轮已有）；保证单份报告的体积上限 |

另外两项：
- **历史趋势**：通过率、判定数、零判定数随时间的走势。判定数下降本身就是一个信号。
- **单文件可分享**：截图内联进同一个文件，CI 产物下载下来就能打开。

具体版式和取舍会单独出设计稿，和你确认后再做。

## 6. 文档体系：给人看的、给 AI 看的分开

现在的文档是按时间堆起来的：`docs/design/` 里 00 到 15 是一份份决策和返工记录，使用手册是一份长文。这对追溯历史有用，但新用户不知道该从哪里读起，agent 也找不到它真正需要的那部分。改成按读者组织：

```
README.md                    一页：是什么、为什么不直接用 pytest、五分钟上手
docs/
  guide/                     给人：按任务组织
    quickstart.md            装好、跑第一条、看报告
    http.md / web.md / app.md
    judgements.md            判定、零判定、基线与门禁
    ci.md                    接进 CI：JUnit、--fail-on-weakened、基线文件的评审
    agents.md                接 agent：MCP、约定文件
  reference/                 给人查：CLI 参数、配置项、API，尽量从代码生成，避免过期
  design/
    architecture.md          当前架构，只有一份，随代码更新
    decisions/               现在的 00-15 收进这里，作为决策记录，不再改动
AGENTS.md                    给在本仓库开发框架的 agent：分层、门禁、提交规范
src/ipandora/templates/      `ipandora init` 生成给使用方的文件：
  AGENTS.md                    给写用例的 agent：判定用 assert_all/field；改判定要写理由；
                               不许为了变绿去改弱判定；UI 优先用稳定定位符
```

给 AI 看的文档有三条要求：**短、可执行、和代码一起测**。约定文件里的每条规则都要对应一个门禁或一个报告信号，例如"不许改弱判定"对应 `--fail-on-weakened`，否则规则就只是一句愿望。

## 7. 第 1 步的实现（已完成，PR #17）

**记录原生 assert。** `run()` 打开 pytest 的 `enable_assertion_pass_hook`。每个成立的 `assert` 都被记成一条判定：源码表达式加实际值，写在辅助函数里的也算。`pytest.raises` / `pytest.warns` 在运行期间被包了一层，成立时记成判定。字面量 assert（`assert True`）不算判定，因为它不可能失败。

实测踩到一个坑：钩子是编译进改写后的字节码里的，而 pytest 复用 `__pycache__` 时不检查当初是用什么选项编译的。所以一个文件只要先被普通 `pytest` 跑过一次，之后就再也记不到 assert。解决办法是运行期间把 `sys.pycache_prefix` 指向单独的目录，两种缓存互不共用。

**零判定检测。** 用例通过了，却一条判定都没有，状态记为 `UNVERIFIED`：不计入通过率，JUnit 里写成 `skipped type="unverified"`。unittest 和 doctest 的用例除外，它们的 `assertEqual` 不是 assert 语句，框架看不见，所以不下这个结论。

**判定清单对比。** 基线文件是 `conf/judgements.json`，设计成要提交进仓库的。比对的是运行时实际执行过的判定，能区分这几类变化：

| 变化 | 是否触发门禁 |
|---|---|
| 删除 | 是 |
| 放宽（数值上下限变宽） | 是 |
| 改变（期望值不同，方向判断不了） | 是 |
| 改为跳过 / 被排除 | 是 |
| 零判定 | 是 |
| 用例删除 | 是 |
| 收紧 / 新增 / 新用例 | 否 |

`--fail-on-weakened` 是门禁开关；`--update-baseline` 接受这次的判定，基线文件的 diff 就是给评审人看的东西。给这一个文件设 CODEOWNERS，agent 仍然可以随便改用例，但没法在没人看见的情况下把判定改弱。

**顺带修掉的问题。** 同一个进程里连续调用 `run()` 时（MCP server 就是这样），测试模块一直留在 `sys.modules` 里。所以测试文件改过之后，再跑执行的还是旧版本：agent 改了用例重新跑，拿回来的却是旧结果。现在每次运行结束，都会把这次运行导入的项目模块清掉。框架自身、标准库和已安装的包不清，否则跨运行的类型身份会对不上。

## 8. 并发

"并发"在产品测试里有两层意思，要分开做：

| | 解决什么 | 例子 |
|---|---|---|
| **A. 并行执行** | 套件跑得快 | 500 条用例从 20 分钟缩到 3 分钟 |
| **B. 并发场景测试** | 产品在并发下对不对 | 同一订单并发提交只扣一次款；库存不超卖；幂等键生效；限流按约定返回 429 |

### A. 并行执行

**现状有个坑，实测出来的**：现在用 `ipandora run tests -p -n 4`（pytest-xdist）并行跑，**所有判定都会丢失**，每条用例都变成零判定。原因是判定记录在 worker 进程里，而汇总结果的插件只在主进程。所以并行不能简单套用 xdist，要做成正式能力：

| 要解决的 | 做法 |
|---|---|
| 判定和证据回到主进程 | 改成一个模块形式的插件，主进程和每个 worker 都会加载它。worker 在每条用例结束时，把判定、请求证据和声明（dims、flaky、标题）塞进 `report.user_properties`，随测试报告一起回传。**串行和并行走同一条路径**，不另写一套 |
| 环境配置 | `-e staging` 的叠加现在只发生在主进程；改为通过环境变量传给 worker，worker 启动时自己叠加 |
| 字节码缓存 | worker 是新进程，继承不到 `sys.pycache_prefix`；改用 `PYTHONPYCACHEPREFIX` 环境变量 |
| **共享资源冲突** | 产品测试并行时真正的麻烦在这里：两条用例同时用同一个测试账号、同一条数据，互相把对方搞挂。提供 `@pytest.mark.resource('account:vip')` 声明独占资源，跨 worker 用文件锁互斥；以后的账号池、设备池、浏览器上下文都挂在这套机制上 |
| 结果一致 | 判定清单按用例 ID 归档，和执行顺序无关；并行跑和串行跑得到的清单必须一致（作为测试） |
| 入口 | `ipandora run tests --workers 4`；MCP `run_tests(workers=4)`；xdist 作为可选的 `[parallel]` 安装 |

### B. 并发场景测试

这是很多产品缺陷藏身的地方，而 pytest 没有现成的写法。框架提供一个原语（接口为草案）：

```python
from ipandora.core.concurrency import concurrently

results = concurrently(lambda: OrderApi().pay(order_id, key='idem-1'), n=20)
codes = [status_code(r.value) for r in results]
assert_all(
    that(codes, '各请求状态').each().is_in([200, 409]),
    that(codes.count(200), '成功扣款次数') == 1,                 # 恰好一次
    field(OrderApi().get(order_id), 'data.paid_amount') == 100,  # 终态
)
```

- **用屏障同步起跑**：所有请求同时放行，尽量把冲突窗口压到最小，否则"并发"可能只是一个接一个地跑。
- **证据不丢**：每个并发请求都记进当前用例的证据。现在的证据记录器是按线程隔离的，新开的线程拿不到当前用例，要显式传过去。
- **登录态不丢**：HTTP session 也是按线程隔离的，新线程拿到的是不带登录态的新 session，要把调用方的请求头和 cookie 复制过去。细节见 `14` §2。
- **判定看两样东西**：每个请求各自的结果，以及操作结束后的终态。并发缺陷通常只在终态里暴露。

**边界**：这不是压测。不做 RPS 目标、不做延迟分位数的 SLA，那是 Locust、k6 的事；结果里附上耗时作为证据即可。
