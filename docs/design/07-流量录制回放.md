# P6 流量录制回放 · 设计方案

> 2026-08-02 · 设计阶段，无实现代码

---

## 0. 先拆词

「流量录制回放」在不同语境下指三件完全不同的事。三个疑点的答案在三者之间是**相反**的，所以必须先分开。

| | 录的是谁的流量 | 采集点 | 需要改被测服务吗 | 主要价值 |
|---|---|---|---|---|
| **A · 出向录制** | **测试自己**发出的请求 | 测试进程内 | ❌ 完全不需要 | 测试离线可跑、快、稳 |
| **B · 生产流量回放** | **真实用户**的请求 | 生产入口 | ⚠️ 通常改配置，不改代码 | **重构护栏** |
| **C · 服务端录制** | 打到被测服务的请求 | 服务前面的代理 | ❌ 但要部署 | 造用例素材 |

原方案标「重构场景 ROI 最高、与 AI 无关」的是 **B**——我要重写一个服务，怎么保证行为不变？答案是拿真实流量同时打新旧两版，比对响应差异。

**A 不是 B 的简化版，是另一件事。** 但 A 在本框架里几乎是白捡的（见 §2），而且 A 和 B 共用同一套磁带格式、匹配规则和差异引擎。所以路径是：**先做 A 把引擎跑通，再把 B 的流量导进同一个引擎。**

## 1. 疑点一：Python 能实现吗

**分两半回答，因为这两半根本不该由同一个东西承担。**

### 能，而且是 Python 该干的那一半

**回放引擎、匹配、差异判定、报告集成**——这些是纯计算，Python 完全胜任，而且正是测试框架的本职。业界同类（VCR.py、betamax、responses、pytest-recording）全是 Python 写的，跑了十年。

### 不能，也不该假装能的那一半

**生产流量的采集不在 Python 里。** 流量在被测服务那边，不在测试进程里——这不是语言问题，是位置问题。用 Go 写的框架同样采集不到。

所以本方案的边界是明确的：

> **框架拥有磁带格式、匹配、回放、差异判定和报告。**
> **框架不拥有生产流量的采集，只定义「怎么把外部采到的流量导进来」。**

把采集也塞进框架，结果一定是一个既不专业又难维护的半吊子代理。业界已经有 goreplay / mitmproxy / envoy tap / nginx mirror 在做这件事，它们比框架做得好。

### 对 A（出向录制）来说，Python 不但能，而且现在就差临门一脚

`core/evidence/recorder.py` 里的 `Exchange` 已经是一条完整的磁带记录：

```python
method, url, status, reason, ms,
request_headers, request_body,
response_headers, response_body, error
```

上一轮为了报告加的证据采集，**顺手把录制的一半做完了**。缺的只有：

1. **一个更靠下的挂载点**。现在记录发生在 `NiceRequest.set_step()`，即响应已经拿到之后——录制够用，但回放必须在请求发出**之前**拦下来。
2. **磁带的读写与匹配**。

关于第 1 点有个现成的答案：**框架已经给每个 session 挂了自定义 `HTTPAdapter`**（`transport.mount()`）。`HTTPAdapter.send()` 是 requests 里请求出网前的最后一站，也是 urllib3 之上唯一能同时看到"完整的 PreparedRequest"和"完整的 Response"的地方。

**那个为了重试而挂的 adapter，就是回放的接缝。** 不需要 monkey-patch，不需要改调用方，不需要新的全局状态。

顺带一提：在 adapter 层录，录到的是**线缆上的形态**（序列化之后、压缩之前），比现在在 `ResponseObject` 层录到的"已经煮过一道"的形态更适合忠实回放。所以实现时录制点会一并下沉到 adapter，报告那条链路不受影响——`Exchange` 还是同一个。

## 2. 疑点二：需要插入开发的代码吗

### A（出向录制）：一行都不需要

不需要动被测服务，也不需要动已有用例。只在框架侧多挂一层 adapter：

```python
class ReplayAdapter(HTTPAdapter):
    def send(self, request, **kwargs):
        if mode is REPLAY:
            return cassette.match(request) or self._miss(request)
        response = super().send(request, **kwargs)
        if mode is RECORD:
            cassette.append(request, response)
        return response
```

用例代码完全不变：

```python
@api.http.get('https://api.example.com/v1/order/query')
def query_order(self):
    return {}
```

录制与回放由**运行方式**决定，不由用例决定：

```bash
ipandora run test/api/ --record      # 打真实系统，同时录磁带
ipandora run test/api/ --replay      # 只吃磁带，不出网
```

这一点很重要：**磁带模式绝不能写进用例**。一旦用例里出现 `@vcr.use_cassette(...)`，就等于把"这条用例怎么跑"焊死在"这条用例断言什么"里，之后想让同一条用例既能打预发又能离线跑就做不到了。

### B（生产流量）：**大多数情况不改业务代码，但一定要有人动基础设施**

按侵入程度从低到高：

| 采集方式 | 改代码 | 改配置 | 部署新组件 | 备注 |
|---|:---:|:---:|:---:|---|
| 网关/LB 访问日志带 body | ❌ | ✅ | ❌ | 最省事，但很多网关默认不记 body |
| Envoy / Istio `tap` filter | ❌ | ✅ | ❌ | 有 mesh 的话这是最佳解 |
| nginx `mirror` 模块旁路 | ❌ | ✅ | ⚠️ | 镜像一份到收集端 |
| goreplay / mitmproxy 旁挂 | ❌ | ✅ | ✅ | 独立进程，语言无关 |
| APM 已有的 payload 采样 | ❌ | ✅ | ❌ | 若已接 APM，成本最低 |
| 应用内中间件（ASGI/WSGI/Filter） | ⚠️ **是** | — | ❌ | 只加一层中间件，不碰业务逻辑 |

**结论**：只有最后一行需要改被测服务的代码，而且是加一个与业务无关的中间件。前五种都不用。

但要诚实说清楚两件事：

1. **成本不在 Python 侧，在运维侧。** 需要有人有权限改网关配置、需要评估镜像流量对生产的压力、需要一个地方存这些流量。这一步卡的不是技术，是协作。
2. **必须过安全评审。** 录生产流量 = 录到真实用户的手机号、地址、token、金额。**这不是可以"先做起来再说"的事**。所以本方案把脱敏定为**录制时**的硬约束（§3.4），不是回放时，也不是展示时——落盘那一刻就已经脱过。

## 3. 疑点三：录制后什么形态存储

### 3.1 一盘磁带 = 一个目录

```
cassettes/
  order-query/                      ← 一盘磁带
    manifest.yaml                   ← 元信息 + 匹配规则 + 差异容忍清单
    exchanges.jsonl                 ← 每行一次往返
    blobs/
      sha256-a1b2c3….json           ← 大 body，按内容寻址
      sha256-d4e5f6….bin
```

### 3.2 为什么是 JSON Lines 而不是一个大 JSON

| | JSONL | 单个大 JSON / HAR |
|---|---|---|
| 录制时能否边录边写 | ✅ append | ❌ 得在内存里攒完再序列化 |
| 一万条流量 | ✅ 流式读 | ❌ 全量进内存 |
| `grep` / `wc -l` / `split` | ✅ | ❌ |
| git diff 可读 | ✅ 一行一条 | ❌ 一改全文重排 |
| 现成工具能打开 | ❌ | ✅ HAR 可直接拖进 Chrome DevTools |

最后一行是 HAR 唯一的优势，但它值钱。**所以：内部格式用 JSONL，另提供 `ipandora cassette export --har` 导出。** 既能流式录制，又能用现成工具看——不必二选一。

### 3.3 一条记录长什么样

```jsonc
{
  "seq": 7,
  "at": "2026-08-02T11:41:07.482Z",
  "key": "GET|/v1/order/query|q:orderId|b:-",   // 匹配键，见 §4
  "request": {
    "method": "GET",
    "url": "https://api.example.com/v1/order/query?orderId=2607310000176847",
    "headers": {"Authorization": "***REDACTED***", "X-Trace-Id": "abc123"},
    "body": null
  },
  "response": {
    "status": 200,
    "reason": "OK",
    "headers": {"content-type": "application/json"},
    "body_ref": "sha256-a1b2c3…",              // 大 body 走 blob
    "body": null                                // 小 body 直接内联
  },
  "ms": 187,
  "source": "record"                            // record | import:nginx | import:har
}
```

**大 body 走内容寻址的 blob，有两个实打实的理由**，不是洁癖：

1. **去重。** 真实流量里同一个响应体重复出现的比例极高（配置接口、字典表、分页第一页）。一万条流量可能只有几百个不同的 body。按 sha256 存，重复的一份都不多存。
2. **jsonl 保持可读。** 一行里嵌一个 200KB 的 JSON，这文件就没法 `less`、没法 diff、没法 review 了。

阈值建议 8KB（和报告里 `MAX_BODY_CHARS` 同一个数量级，理由相同）。

### 3.4 manifest：磁带的语义在这里，不在代码里

```yaml
name: order-query
recorded_at: 2026-08-02T11:41:02Z
recorded_from: staging          # 或 prod-mirror
ipandora: 1.2.0
count: 143
blobs: 27

match:                          # 怎么算"同一个请求"
  on: [method, path, query, body]
  ignore_query: [_t, nonce, sign]
  ignore_headers: [X-Trace-Id, Date, User-Agent]
  ignore_body_paths: [requestId, timestamp, clientVersion]

diff:                           # 差异判定时忽略什么
  ignore_paths:
    - data.serverTime
    - data.traceId
    - "data.list[*].updatedAt"
  ignore_headers: [Date, X-Request-Id, Set-Cookie]
  tolerate:
    - path: data.balance
      kind: numeric
      epsilon: 0.0001

redaction:
  applied_at: record            # 硬约束：落盘时已脱敏
  rules: default                # 复用 core/report/redact.py
```

**为什么匹配规则和容忍清单必须存在磁带旁边，而不是写在用例里或代码里**：

它们是**这盘磁带的属性**，不是这次运行的属性。`data.serverTime` 每次都不一样——这是被测系统的事实，换一条用例、换一次运行都还是这样。写在用例里意味着每条用例都要重复声明一遍，而且一旦漏掉就是一条永远飘红的假失败。

而且这两份清单是**会长期演进的产物**：每发现一处新的非确定性字段就补一条。它们值得进版本控制、值得被 review，不该埋在某个函数的默认参数里。

> 原方案说「差异容忍清单需要真实流量样本才能定」——正是这个 `diff.ignore_paths`。它必须靠真实数据一条条喂出来，没法先验地写全。

### 3.5 磁带放哪

- **小磁带（< 1MB，用于单元/接口测试）**：进 git，和用例放一起。可 review、可 diff、CI 直接能用。
- **大磁带（生产流量导入）**：不进 git。放对象存储 / 制品库，manifest 里记 URI 与 sha256，`ipandora cassette pull` 拉取。
- **绝不进 git 的**：未脱敏的原始生产流量。脱敏发生在导入的第一步，未脱敏版本根本不落到框架的目录里。

## 4. 核心难点：匹配

回放时怎么判断"这个请求就是当初录的那一个"？这是整个方案里最容易做错的地方。

### 默认匹配键

```
method | path | 排序后的 query | body 的规范化摘要
```

排序、规范化都是必须的：`?a=1&b=2` 和 `?b=2&a=1` 是同一个请求；`{"a":1,"b":2}` 和 `{"b":2,"a":1}` 也是。

### 必须可插拔，因为真实请求里全是噪音

- `?_t=1754130062`（防缓存时间戳）
- `?nonce=…&sign=…`（签名）
- body 里的 `requestId` / `clientVersion`
- `Authorization` 里每次不同的 token

这些进了匹配键，**回放必然全部 miss**。所以 `match.ignore_*` 不是可选项，是能不能用起来的前提。

### 同一个键录了多条怎么办

分页、状态机（`pending → success`）都会造成同 key 多条且响应不同。

**语义：同 key 的记录按录制顺序消费一次（play-once）。** 耗尽后按策略：

| 策略 | 行为 | 适用 |
|---|---|---|
| `error`（默认） | 报 CassetteMiss | CI，必须确定 |
| `last` | 重放最后一条 | 只读接口的冒烟 |
| `passthrough` | 放行到真实网络 | 本地补录 |

**默认必须是 `error`。** 一次静默的 miss 会让测试在"回放"的名义下悄悄打真实系统，或者拿到错误的响应还判通过——这是这类方案最经典的坑，和当初那个 500 静默通过是同一种病。

### Miss 时报告要说人话

```
CassetteMiss: order-query 里没有匹配的记录
  请求   GET /v1/order/query?orderId=2607310000176847
  匹配键 GET|/v1/order/query|q:orderId|b:-
  最接近 GET|/v1/order/query|q:orderId,pageSize|b:-   （差异：query 多了 pageSize）
  磁带录于 2026-08-02（14 天前），共 143 条
  → 补录：ipandora run <selector> --record --cassette order-query
```

"最接近的键 + 差在哪"是关键——十次 miss 里有九次是某个 ignore 规则没配。

## 5. 三种模式，第三种才是 ROI 所在

| 模式 | 出网 | 用磁带 | 结论来自 | 用途 |
|---|:---:|:---:|---|---|
| `--record` | ✅ | 写 | 真实响应 | 造磁带 |
| `--replay` | ❌ | 读 | 磁带响应 | CI 离线跑，快且稳 |
| **`--verify`** | ✅ | **比** | **真实 vs 磁带的差异** | **重构护栏** |

前两个是常规能力。**第三个是原方案说 ROI 最高的那个**：

```bash
# 重写 order 服务之前，先录一盘
ipandora run test/order/ --record --cassette order-baseline

# 重写之后，拿同一盘磁带比对
ipandora run test/order/ --verify --cassette order-baseline
```

`--verify` 不看断言过不过，它回答的是另一个问题：**这次的响应和基线比，哪里变了**。输出进报告，作为一类新的判定来源 `Source.DIFF`：

```
[FAIL] 响应与基线一致 (diff) | data.list[3].status: "PENDING" → "PROCESSING"（3 处差异，2 处已容忍）
```

这正好落进现有报告的判定体系里——`Check` 有 `src`，报告有"判定构成 · 按维度"，差异会自然出现在那一栏，不需要为它另造一套展示。

## 6. 分阶段

| 阶段 | 内容 | 卡业务域 | 卡运维 |
|---|---|:---:|:---:|
| **P6.1** | 磁带读写 + `ReplayAdapter` + `--record` / `--replay` | ❌ | ❌ |
| **P6.2** | 差异引擎 + 容忍清单 + `--verify` + 报告集成 | ❌ | ❌ |
| **P6.3** | 导入器：nginx 日志 / HAR / envoy tap → 磁带 | ❌ | ✅ |
| **P6.4** | 双跑对比（新旧版本同时回放） | ✅ | ✅ |

**P6.1 与 P6.2 现在就能做**，不依赖任何外部输入：`Exchange` 已有、adapter 接缝已有、脱敏已有、报告的判定体系已有。用真实包管理器接口就能验证（和 `05` 那轮一样）。

P6.3 的**格式与导入逻辑**也不卡，卡的是"谁给我一份真实流量样本"。可以先用自己录的磁带当样本把导入器写好，等拿到真实样本再调容忍清单。

P6.4 需要能同时跑起新旧两版的环境，和 P7 是同一类依赖。

## 7. 边界：这个方案治不了什么

写在前面比事后解释强。

### 有状态与写接口

录一次「下单」，回放一百次——第二次开始就已经不是同一个语义了。录制回放**天然只对读多写少、幂等的接口可靠**。

写接口的三条路：
- 只做 `--verify`（打真实系统，比对差异），不做 `--replay`
- 配合 fork 环境（P7），每次回放前把状态复位
- 老老实实写普通用例

**不能假装磁带解决了这个问题。**

### 磁带腐化

这是 VCR 类方案最大的隐患，而且是**沉默**的：磁带录于三个月前，接口早就改了，测试还在绿——它测的是"我三个月前的假设"，不是这个系统。

对策必须是结构性的，不能靠自觉：

- manifest 里记 `recorded_at`
- 报告里显示磁带年龄，超阈值（建议 30 天）标黄
- CI 里可设 `--max-cassette-age`，超期即失败
- 定期 `--record` 重录，把重录当成一个日常任务而不是救火动作

这和 `gap()` 是同一个思路：**让"我其实没在测"这件事在报告上显形**，而不是让它藏在一片绿里。

### 加密与签名

请求体加密、或签名包含时间戳的接口，匹配键要么剔掉这些字段（那就等于降低了匹配精度），要么需要业务侧提供解密/重签的钩子。**这一条必须在真实业务域上验证，先不承诺。**

### 隐私

已在 §2 说明。补一条：**脱敏规则出错的代价是不对称的**——多脱一个字段是重录一次，少脱一个字段是数据泄露。所以沿用 `redact.py` 里那条既有原则：**宁可过度脱敏**。

## 8. 三个疑点的一句话回答

1. **Python 能实现吗？**
   回放、匹配、差异判定能，而且框架里已经有一大半零件。**生产流量的采集不能，也不该由框架做**——那是位置问题不是语言问题，换任何语言都一样。

2. **需要插入开发的代码吗？**
   出向录制（A）**一行都不需要**，挂在框架自己已经 mount 的 adapter 上。生产流量（B）**大多数情况不改业务代码**，但一定要有人动网关/mesh 配置，并且必须过安全评审——真正的成本在运维和合规，不在编码。

3. **什么形态存储？**
   一盘磁带一个目录：`manifest.yaml`（元信息 + 匹配规则 + 差异容忍清单）+ `exchanges.jsonl`（每行一次往返，可流式追加、可 grep、可 diff）+ `blobs/`（大 body 按 sha256 内容寻址、自动去重）。**落盘那一刻已脱敏。** 另提供 HAR 导出，用现成工具查看。
