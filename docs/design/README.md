## 一页纸结论

### 1. 起点选哪个？

**IntelliPandora，但不是在它上面加功能，而是把它当"容器"重写内核。**

- `pandora` 是更早的同类框架、功能重叠，架构图里本身就只是一个 Runner → 排除。
- IntelliPandora 的**架构分层是对的**（两年前的图就已经画对了"框架核心/业务工程"的边界），**包名、布局、装饰器设计也值得留**。
- 但实测下来，**唯一承载"接口自动化能力"的 `core/protocol`（1313 LOC）成熟度约 2/10**：没有任何断言层（500 静默通过）、所有 HTTPS 强制关闭证书校验、默认无超时、响应解析对常见结构返回错误数据。

所以结论不是"选哪个仓库"，而是**留容器、重写内核**。

📄 证据与三张清单（留/归档/重写）见 [`01-现状评估与起点决策.md`](./01-现状评估与起点决策.md)

### 2. LLM 接入口怎么控成本？

**LLM 只出现在"编写时"和"运行后"，绝不出现在"运行时"。**

| 时机 | 用 LLM？ | 成本随什么增长 |
|---|---|---|
| 编写时（AI 写用例） | ✅ 在框架之外，agent 直接写文件 | 人 × 编写次数 |
| 运行时（执行、断言） | ❌ **绝不** | **恒为 0** |
| 运行后（失败归因） | ⚠️ 可选，默认关 | 失败数，有上限 |

> **成本不随测试规模增长。** 一天跑 10000 次用例、0 次失败 → LLM 调用 0 次。

靠五条结构性保证落实，不靠"记得关掉"：默认安装不带 LLM SDK · 默认配置关闭 · `core/` 禁止 import `ai/` · **`rm -rf ai/ && pytest` 必须全绿** · 预算闸 + fail-open。

📄 详见 [`03-LLM接入边界.md`](./03-LLM接入边界.md)

### 3. 先做什么？

**基础自动化能力优先，LLM 靠后。** P0/P1 不依赖任何外部输入，可立即开工。

| 阶段 | 主题 | 依赖业务域 |
|---|---|---|
| P0 | 清理与止血：归档 generator、清凭据、建 CI | ❌ |
| P1 | **内核基础能力：断言层 + 可靠传输层** | ❌ |
| P2 | 业务语义层：fixture / flow / 领域 invariant | ✅ |
| P3 | 入口层：runner 库调用 + MCP | 部分 |
| P4 | LLM 接入（默认关） | ❌ |

📄 详见 [`04-实施计划.md`](./04-实施计划.md)

## 三个最关键的发现

**① 一个动作消灭三类债。**
`case.py`/`testcase.py` 双模型（同一张表两个类，调用方拿到哪个不确定）、legacy 双渲染路径（"新版"写完从没接上，实际跑的是 legacy）、39 个从未被 import 的孤儿模块——**全部集中在 `core/engine/generator` 内**，而原方案本来就要砍掉它。归档这一块，代码量 8415 → 5372 LOC（126 → 92 个模块）且全部可信。

**② 最致命的缺口是"判不出对错"。**
框架当前没有任何断言层——接口返回 500，测试照常 PASS。在补上这个之前，谈 AI 化、谈 MCP、谈归因都没有意义：归因需要有可归因的失败，而现在连失败都识别不出来。

**③ 最好的 AI 化路径成本是零。**
框架不需要内置任何 LLM 调用，就能大幅提升 AI 生成用例的质量——只要 flow / invariant / fixture 这套"词汇表"足够丰富，AI 就是在造句而不是造词。

## 与原方案的差异

本文档集基于 `00`，有两处有意偏离：

| | `00` 的主张 | 本文档集 | 理由 |
|---|---|---|---|
| `core/protocol` | 列入"留" | **重写** | 实测 2/10，是全仓库质量最低处 |
| MCP 时机 | "不要放最后" | 放在 P1 之后 | `run_tests` 需要先有判得出对错的断言层 |

并新增了 `00` 未覆盖的 **P0 清理阶段**——`00` 假定了一个健康的起点，实测不成立。
