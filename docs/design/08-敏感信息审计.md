### 为什么第一轮没查出来：两处正则缺口，都在我自己写的东西里

**缺口 1——内网域名的形状。** 第一轮的模式是 `\.(internal|intranet|corp|local|lan)\b|zentao|jira\.|gitlab\.`。`adqa.test.gifshow.com` 一个都不匹配。一个只认「长得像内网」的命名约定的规则，认不出用正常公司域名做的内网环境。

**缺口 2——`check_secrets.py` 匹配不到带引号的字段名。** 这是更要命的一条，因为它是上一节刚加固过的那道门禁：

```
token = '...'      → 抓到
"token": "..."     → 漏掉        ← dict / JSON 字面量的写法
```

正则是 `\b(token|password|…)\b\s*[:=]`——字段名后面紧跟的是**引号**而不是分隔符，整条形状就此走过去。所以那道门禁在加固之后、扫全仓库之后，对这处活凭据**仍然报零命中**。

修法是在字段名后补一个可选引号 `['"]?`，并补上 `user` / `account` / `appkey` / `app_secret`。修完之后全仓库从「零命中」变成 **12 处命中**——除去 `user_guider.md` 那一对，其余 10 处是刻意的测试 fixture 和讲脱敏的文档正文，**此前全部不可见**。也就是说这个洞藏住的不是一个值，是一整类写法。

## 二、框架自己生成的密钥会落在仓库内，且三道门禁全都抓不到

`AESCryptographer` / `FernetCryptographer` 在找不到密钥时**自动生成并写盘**，没有人选择把它放哪：

```python
self._directory = os.path.join(PathUtils().pandora_path, 'conf/crypto')
...
self.key = os.urandom(self.key_size)
self.save_key_to_pem('aes_pandora.pem')
```

`get_pandora_path()` 返回到 `ipandora` 这一级为止，仓库场景下即 `src/ipandora/`。所以密钥落在 **`src/ipandora/conf/crypto/aes_pandora.pem`——被跟踪的包目录内**，而 `.gitignore` 当时没有 `*.pem`。

三道门禁为什么同时失效：

| 门禁 | 失效原因 |
|---|---|
| pre-commit `detect-private-key` | 只认 `BEGIN RSA/DSA/EC/OPENSSH/PGP PRIVATE KEY`。AES 文件头是 `BEGIN aes KEY` |
| `scripts/check_secrets.py` | 正则要求字面 `PRIVATE KEY`；且 pre-commit 里配了 `types: [text]` |
| CI 的 inline grep | 只找 `password=` / `token=` 这类赋值语句 |

Fernet 那个更彻底——写的是**裸 bytes**，文件里连 `BEGIN` 都没有，任何基于内容的规则都描述不了它。

### 修法

新增 `core/engine/crypto/keystore.py`，把目录与权限集中到一处：

- 默认 `~/.ipandora/crypto`，可用 `IPANDORA_KEYS_DIR` 覆盖，**不再从包自身位置推导**
- 目录 `0700`，密钥文件 `0600`
- `os.open(..., 0o600)` 建文件而不是先 open 再 chmod——后者留一个密钥短暂 world-readable 的窗口
- `makedirs` 的 `mode` 只作用于它新建的那一级，且目录已存在时完全不生效，所以无论哪种情况都显式收窄一次

`.gitignore` 补 `*.pem *.key *.p12 *.pfx *.jks id_rsa* id_ed25519* *.ppk`。

`check_secrets.py` 两处补强：

- 通用 `-----BEGIN <任意> KEY-----` 头，不再只认 `PRIVATE KEY`
- **按文件名判定**：`*.pem` `*.key` `id_rsa` 等一律视为密钥材料。这是唯一能抓住无头裸 bytes 的办法

### 顺带修掉一个 bug

`conf/crypto` 这个目录从来没有人创建过（全仓库无 `makedirs`），所以 `select_key_with_tag` 的 `os.listdir` 会先抛 `FileNotFoundError`——**整条 crypto 路径在全新安装上是坏的**。

把目录移出包、并真的创建它之后，这条路径第一次变得可达，于是立刻撞上下一个 bug：

```python
self.key = pem_key   # save_key_to_pem 结尾
```

`pem_key` 是 base64 **str**，而 AES 要的是 32 个原始字节。所以全新安装的第一次运行必然在 `algorithms.AES()` 抛异常，只有第二次（读回文件、解码）才正常。两个 bug 互相掩护：前者让后者永远到不了。

补 `test/testcrypto/`（18 条）盯住：密钥目录在包外、权限位、AES/Fernet 在**全新 keystore 上**的往返、以及跨实例复用同一密钥。

变异测试：

| 变异 | 失败用例 |
|---|---|
| 还原 `self.key = pem_key` | 3 条 |
| 把 keystore 目录改回包内 | 1 条 |
| 还原 Fernet `save` 里重复生成 key | **0 条——这条是浪费不是缺陷** |

最后一行保留在文档里：那次改动只是去掉一次无用的 `generate_key()`，两种写法行为等价，用例通过是对的，不应记为修复。

## 三、门禁有两套实现，强的那套不在 CI 里

`scripts/check_secrets.py` 只挂在 `.pre-commit-config.yaml`——**本地 opt-in**，要开发者自己跑过 `pre-commit install`。CI 里的 "No hardcoded secrets" 是另写的一段 inline grep，而且只扫 `src/`，不扫 `test/` `conf/` `scripts/` `.github/`。

两套都不覆盖 `user_name` 这类字段名——当年泄漏的那个用户名，正好漏在两套的交集之外。

### 修法

删掉 inline grep，CI 直接调同一个脚本，扫**全部跟踪文件**。字段名补上 `user_name` `username` `access_token` `auth_token` `client_secret` `private_key` `credential` `secret_key`。

### 一个值得单独记下的坑

把扫描范围扩到全仓库后，第一次运行报"零命中"。**那是假的**：

```
$ git ls-files | grep design
"docs/design/01-\347\216\260\347\212\266\350\257\204\344\274\260..."
```

`git ls-files` 对非 ASCII 文件名输出转义加引号，shell 词分割把路径弄坏，`open()` 静默失败、`scan()` 返回空列表。本仓库设计文档几乎全是中文名——**一个什么都没扫的门禁，报告的是干净**。

所以 CI 里那行 `-z` / `xargs -0` 是功能性的，不是风格：

```yaml
git -c core.quotepath=false ls-files -z \
  | xargs -0 --no-run-if-empty python scripts/check_secrets.py
```

改对之后真的抓出一处：`01-现状评估与起点决策.md` 引用泄漏行作为证据。

### 刻意的假凭据怎么办

脱敏层的测试需要像真的凭据。新增 `pragma: allowlist secret` 行内标记，共标注 9 处（3 个测试文件 + `aescryptographer.py` 里写/读 PEM 头的两行 + 那份设计文档）。

这个机制本身就是目的：让"这是假的"成为**有人写下、评审能在 diff 里看见的声明**，而不是正则里的一个缺口。相应地 pre-commit 去掉了 `exclude: ^docs/` 和 `types: [text]`——前者是整块的盲区，后者会跳过二进制，而裸 bytes 密钥正是二进制。

## 五、顺带发现：已发布的包缺数据文件

不属于安全范畴，但同一次审计查出来的。

PyPI 1.1.0 的 wheel 里 `ipandora/conf/` 下**只有 `__init__.py`**：没有 `config.yaml`，没有 `conf/static/report.html` / `history.html`。也就是说 `pip install intellipandora` 装出来的副本**渲染不出 HTML 报告**。

`MANIFEST.in` 原本写的是 `recursive-include intellipandora/conf *`——**发行名**，既不是包名（`ipandora`）也不是它在 `src/` 下的真实路径，匹配不到任何文件；另外两行还指向两个不存在的目录。

**但这不是已发布 wheel 坏掉的原因。** 实测：当前 setuptools（79.0.1）的 `include_package_data=True` 会收走包目录内的全部文件，**把 MANIFEST.in 整个删掉，数据文件照样进 wheel**。所以产物正确与否取决于**发版那台机器的 setuptools 版本**，而这个版本不被仓库里的任何东西固定——它可以在没有一行代码变更的情况下再次回归。

单测看不见这件事：CI 用 editable 安装，数据文件就在源码树里，当然存在。

所以修 `MANIFEST.in` 不构成保证。保证是 `scripts/check_packaging.py`：清掉 `*.egg-info`（否则 setuptools 复用上一次正确构建留下的 `SOURCES.txt`，门禁会在该失败的仓库上通过——此处已实测踩到）、构建 wheel、断言必需数据文件在内且无密钥材料。

验证它真的有效，是拿它去打真实的坏产物：

```
$ python scripts/check_packaging.py w-1.1.0.whl
w-1.1.0.whl: 125 entries
  missing: ipandora/conf/config.yaml
  missing: ipandora/conf/static/report.html
  missing: ipandora/conf/static/history.html
退出码=1
```
