# 对齐新规划的现状复核

> 2026-11-05 · 依据《AI 时代的测试框架：迭代计划》及其两张图（整体架构四层 / 日常工作流）
>
> 前八份文档是在**没有这份规划**的前提下写的。它们的技术判断仍然成立，但目标形态不是这个。本文只做一件事：把仓库现状逐项放到新规划的架构图上，看哪些已经有、哪些没有、哪些有但图上没有它的位置。

---

## 结论先行

三句话：

1. **执行层图上列了五项能力，仓库里只有一项。** 「协议模块 · Flow · Invariant · 账号池 · JUnit XML」——只有协议模块存在。
2. **仓库里最大的子系统在图上没有位置。** 流量录制回放（cassette）src 1642 行 + test 1776 行，是单体最大的一块，新架构图四层里找不到它。
3. **入口层基本已经达成，且比图上更彻底。** 人 / CI / agent 三个入口已经共用同一套 runner 库；本轮删掉数据上报后，执行器确实是独立的了。

卡住的从来不是机制，是**业务域输入**——Flow / Invariant / 账号池三项都需要真实业务的接口与测试环境。唯一不卡业务域、又在关键路径上的缺口是 **JUnit XML**。

## 一、按图 1「整体架构」逐项核对

### 入口层：三个入口调同一条命令

| 图上 | 仓库现状 | 证据 |
|---|---|---|
| 人 | ✅ | `ipandora run <selector>`，16 个参数 |
| CI | ⚠️ 部分 | `.github/workflows/ci.yml` 有 4 个 job，但那是**框架自测**的 CI，不是跑业务用例的 CI。PR 触发有，定时任务没有 |
| agent（Claude Code + 测试插件） | ✅ | `core/mcp/server.py` 暴露 5 个 tool |

**一处比图上更好**：MCP 的 `run_tests` 走的是 `core.runner.api.run()` **库调用**，不是 subprocess 起 pytest 再解析 stdout。所以「三个入口」共用的不只是一条命令，是同一个函数——CLI 和 MCP 都是它的薄壳。原规划的阶段 1 把这件事列为待办，实际已经完成。

MCP 现有的 5 个 tool：`run_tests` · `explain_failure` · `list_runs` · `build_report` · `get_test_report`。最后一个是 Robot Framework `output.xml` 解析器，属于遗留（见第三节）。

### 执行层：IntelliPandora 执行器（独立 CLI）

| 图上列的能力 | 现状 | 说明 |
|---|---|---|
| 协议模块 | ✅ | `core/protocol`，传输层已重写：默认超时、重试仅限幂等方法、`verify` 默认 True、错误语义可辨 |
| Flow | ❌ | 全仓库无此概念 |
| Invariant | ❌ | `invariant` 零命中 |
| 账号池 | ❌ | `pool` 的命中全是连接池 |
| JUnit XML | ❌ | `junit` / `allure` 全仓库零命中 |
| 独立 CLI | ✅ | 本轮删掉上报链路后，`config.yaml` 只剩 `http` / `ai` / `mcp` 三段，不指向任何服务器 |

**五项里只有一项。** 这是本次复核最重要的数字。

Flow / Invariant / 账号池三项的共同前提是真实业务域（接口契约、测试环境、可借还的账号），不是工程量问题。JUnit XML 不同——它零外部依赖，`pytest --junitxml` 底层就有。

### 资产层

| 图上 | 现状 |
|---|---|
| 私有仓库（用例 · 业务 Flow · 配置） | ❌ 未拆分，仓库仍是单体且 public |
| 测试数据和账号池（固定账号 · 状态归一） | ❌ |

仓库拆分这件事和另一份文档有交叉：`08-敏感信息审计.md` 记录了本仓库的历史与已发布 wheel 中仍含前雇主内网信息。**拆分前需要先回答公司审批问题**，这也是规划「待确认的问题」里的一条。

另有一个具体前置条件：拆分后私有仓库会把 IntelliPandora 当依赖装，而 PyPI 上当前全部版本**装了渲染不出报告**（`conf/` 下只有 `__init__.py`）。这个已在 `08` 里修好并加了门禁，但**还没发版**。

### 评测层（Python + Inspect，跑在 Docker 里）

| 图上 | 现状 |
|---|---|
| 评测试插件（生成的用例能不能抓住注入的错误） | ❌ 无框架；但**方法已在用**——见下 |
| 评 agentic wallet（意图 · 执行结果 · 安全 · 信息准确） | ❌ |

「能不能抓住注入的错误」就是**变异测试**。本仓库从 P1 起每一轮修复都手工做了一遍，并记录在各文档里（例：还原 `self.key = pem_key` → 3 条失败；`header_is` 恒真 → 1 条失败；还原 Fernet 重复生成 key → **0 条失败，该项是浪费不是缺陷**）。

所以这一层缺的不是方法，是**自动化和打分**：`mutmut` / `cosmic-ray` 能直接产出 mutation score，正好填上规划阶段 3 完成标准里那个「比例（待定）」。

### Java 接口平台

图上是虚线「按需对接」。未做，符合规划。

## 二、按图 2「日常工作流」核对

`PR 或需求 → AI 写或改用例 → 人 review 后合入 → CI 调 CLI 执行 → 全部通过？`
`否 → AI 分析失败原因 → 用例写错？ → 是：改用例 / 否：提 bug 给开发`

| 环节 | 现状 |
|---|---|
| AI 写或改用例 | ✅ 外部 agent 写文件；框架不在运行时生成用例（这是 `03-LLM接入边界.md` 的硬约束） |
| 人 review 后合入 | ⚠️ 无 review 清单；但 `gap()` 和覆盖矩阵是现成的抓手（见下） |
| CI 调 CLI 执行 | ⚠️ CLI 和退出码都有，缺 JUnit XML 让 CI 能读 |
| AI 分析失败原因 | ✅ `core/triage` + `ai/`，且 **LLM 只在运行后调用，运行时恒为 0 次** |
| 用例错 / 产品错 分流 | ✅ 这正是 `core/triage` 的 `blames_system_under_test` 做的判定 |

**两个现成的 review 抓手**，对应规划阶段 3 的清单：

- `gap()` —— 第三种 Check：声明「这里应该有一条断言，但现在没有」。不会让运行失败，也不计入通过。正对「断言有没有查业务结果」。
- **覆盖矩阵的空格子**（`@pytest.mark.dims` + 模块级 `COVERAGE`）—— 空格子本来就是设计意图，正对「有没有跳过校验」。

## 三、图上没有、仓库里有的——这是复核真正要逼出的取舍

按规模排：

| 子系统 | 规模（src + test） | 图上位置 | 建议 |
|---|---|---|---|
| 流量录制回放 cassette | 1642 + 1776 | **无** | 需要你定，见下 |
| 测试报告 report | 923 + 596 | 图上是 JUnit XML | 并存，不是二选一 |
| 断言层 assertion | 642 + 415 | 隐含在执行层 | 保留 |
| runner | 621 + 419 | 执行层核心 | 保留 |
| 失败归因 triage + ai | 628 + 467 | 图 2「AI 分析失败原因」 | 保留 |
| 证据采集 evidence | 217 + 186 | 支撑报告与归因 | 保留 |
| crypto | 485 + 186 | **无** | 保留：`ai.api_key` 仍需加密存放 |
| Robot Framework 残留 | 126 + 0 | **无** | 建议清理 |

### 需要你定的第一件：cassette 留不留

这是仓库里最大的一块（约 3400 行），实现了 `--record` / `--replay` / `--verify`、差异引擎、HAR/nginx/envoy 导入导出。原规划（`00-原始设计方案.md`）标它「重构场景 ROI 最高，和 AI 无关」，但**新架构图四层里没有它的位置**。

三种处置，我的看法：

1. **保留并明确定位**（倾向这个）。它不属于图上任何一层，但它服务图 2 的「CI 调 CLI 执行」：`--replay` 让用例不依赖真实环境就能跑，正好解决「别人很难直接跑」。这需要在图上给它加个位置，而不是删。
2. 拆成独立包。代价是维护两个仓库。
3. 删除。3400 行已验证的代码，且 P6.4 双跑对比还没做。

### 需要你定的第二件：Robot Framework 残留

`setup.cfg` 仍声明 `robotframework` 依赖，`utils/robotlogparser.py`（126 行）仍在，MCP 还暴露着 `get_test_report` 这个解析 `output.xml` 的 tool。`01-现状评估` 里 RobotFramework 适配是「降级」项。要清就一起清掉这三处。

## 四、迭代计划（对齐规划的五个阶段）

标注现状，只列**不卡业务域**的部分；卡业务域的照原规划。

### 阶段 1：把执行器从插件里拆出来（规划估 2 周）

| 规划条目 | 现状 |
|---|---|
| 盘点现有用例 | ⬜ 需要插件仓库，不在此仓库 |
| 以 IntelliPandora 为内核，补 `run` 命令、JUnit XML、统一退出码 | `run` ✅ · 退出码 ✅ · **JUnit XML ❌** |
| 保留协议模块、账号池、Flow、Invariant、覆盖矩阵 | 协议模块 ✅ · 覆盖矩阵 ✅ · 其余三项**不存在**，不是「保留」是「新建」 |
| 仓库拆开（公开 / 私有） | ⬜ 卡公司审批；且需先发版修掉打包缺陷 |
| 用例落盘、账号与环境配置抽出 | ⬜ |
| 插件改成调 CLI 再读报告 | ⬜ 需要插件仓库 |

**本仓库这一阶段只剩一件可做的事：JUnit XML 输出。**

### 阶段 2：接 CI 和报告（规划估 2 周）

| 规划条目 | 现状 |
|---|---|
| CI 加定时任务和 PR 触发 | PR 触发 ✅（框架自测），业务用例的 CI ⬜ |
| 报告出 JUnit XML，qa-report-visualizer 展示 | ❌ 同上 |
| 不稳定用例单独标记，修好前不进门禁 | ❌ |
| Java 平台先不动 | ✅ 符合 |

「不稳定用例标记」不卡业务域，可以做：一个 `@pytest.mark.flaky` 加上 `run` 的 `--exclude-flaky`，配合报告里单列。

### 阶段 3：管住 AI 写的用例质量（规划估 2 周）

| 规划条目 | 现状 |
|---|---|
| 定 review 清单 | ⬜ 清单要写；`gap()` + 覆盖矩阵是现成抓手 |
| 注入错误抽查 | **方法已在用，缺工具化**。接 `mutmut` 出 mutation score |
| 用例文件改动单独 review | ⬜ 流程约定，非代码 |

完成标准里那个「比例（待定）」，接上工具就有数了。

### 阶段 4 / 阶段 5：评测层

整层不存在。阶段 4（评测试插件）需要历史 PR 样本；阶段 5（评 agentic wallet）需要 Anvil 分叉链、业务数据集和签名服务隔离。都卡外部输入。

一个结构性的好消息：`03-LLM接入边界.md` 定的边界是「LLM 只在编写时和运行后，绝不在运行时」。**评委模型属于运行后**，所以评测层不违反这条约束，不需要改架构。

## 五、建议的下一步

按「不依赖外部输入」排序：

1. **JUnit XML 输出**——阶段 1 和阶段 2 的共同卡点，唯一既不卡业务域又在关键路径上的缺口
2. **发一个版本**——把 `08` 修好的打包缺陷推到 PyPI，否则仓库拆分后私有仓库装不到可用的包
3. **变异测试工具化**——阶段 3 完成标准需要这个数，方法已经在用
4. **依赖版本锁死**——`setup.cfg` 21 个依赖只有 1 条有版本约束，而规划的安全要求明写「版本锁死」
5. **不稳定用例标记**——阶段 2 条目，不卡业务域
6. **文档与架构图重做**——README 仍写着 `src/intellipandora`（实际 `src/ipandora`）、死链 `docs/dev/AI_Framework_Design.md`、以及已归档的代码生成与 RobotFramework；两张旧架构图画的是有平台上报的时代

其余全部卡在：业务域的接口与环境、公司对公开/私有边界的审批、历史 PR 样本、链上评测环境。
